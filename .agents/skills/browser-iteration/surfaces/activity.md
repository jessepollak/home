### `activity`
- **Entry context**: activity · `/activity` · same · signed-in seed + `/api/activity`, `/api/actions`, `/api/activity/orders` fixtures · goto path (Home renders the same feed inline since #789).

- **Live**: read-only
- **Owned paths**: `apps/web/app/(shell)/activity/**`, `apps/web/client/activity/**`, `apps/web/client/home/activity-panel.tsx`, `apps/web/app/api/activity/**`
- **Reach**:
  1. `goto "/activity"`
  2. `expect "Activity"`
  3. `expect "Converted USD to EUR"`
- **Notes**: The fixture-session helper seeds signed-in state and API fixtures; `/api/activity/orders` defaults to an empty owner-fenced list. The `activityOrdersFixture` set in `tests/browser/feature-map/fixtures.ts` exercises pending, received and unconfirmed funding plus cash-out action reconciliation. Add `/api/activity` fixture rows when exercising populated transfer states; the Home Activity card is the interactive entry point. The replay fixture (`tests/browser/feature-map/conversion-fixture.ts`) supplies one confirmed USD→EUR trade action on `/api/actions`, synthetic and not live provider routing.
- **Expect**: `Activity` heading (`#activity-title`, client/activity/activity-panel.tsx `DefaultActivityHeader`); empty state `No activity yet`; end marker `End of activity`; whole-panel error `Try again` button; per-source page errors use `Retry onchain transfers`, `Retry recorded actions` or `Retry orders`; later-page failure shows a concise inline `Try again`; ledger rows expose `View <direction> <symbol> transaction details` activation labels and brand/curated icons, provider logos, or ≤2-character initials as row marks; an indexed Home action retains its action row (title and status) instead of generic transfer rows. A confirmed cash-to-cash trade row shows `Converted <from> to <to>` (`Converting <from> to <to>` while pending, `Convert <from> to <to> failed` on failure), classified from trade metadata rather than the raw asset name. On the page, Pending and Recent groups each use a card; on Home, the Pending header and list precede the Recent header and list inside the single Activity section card. Eligible customer actions announce `Action needed`; funding and cash-out orders use Pending/Recent with owner-fenced details and allowed actions, deduplicating funding receipts and matching cash-out actions; consecutive confirmed incoming same-token transfers appear as ordinary-height summary rows (`Received ×4`, one-line date range, stacked marks, fiat/native value), whose individually virtualized, inset children open the ordinary detail sheet; collapsed children have no DOM and closing the detail returns focus to its child; detail sheets show the asset amount, a secondary value line, an Asset row, status Badges, and pending Home action confirmation stages. An owned non-cash Asset row opens its exact holding detail; Back restores the same activity detail without a stacked sheet.
- **States**: Asset row is read-only for unowned and cash assets; header or browser Back from an owned holding returns to the originating `/activity` or `/home` detail. Loading shimmer (`ActivityPage`, client/home/activity-panel.tsx `ShimmerRows count={4}`); empty (`No activity yet`); whole-panel error (`Try again`), or onchain failure with action rows (`Retry onchain transfers`); success ledger with Pending and Recent groups, grouped transfer expansion/collapse by keyboard and child detail focus return, action-needed announcements and detail-sheet badges; recorded-actions failure keeps transfer rows under `Recorded Home actions are unavailable.` with its own `Retry recorded actions` that refetches only actions (Home feed: `Some activity is unavailable` with `Reload activity`), shown only after up to two automatic retries of a transient failure, or once a failed refetch persists more than two minutes after the last successful read (one scheduled re-evaluation, even on a focused tab); orders failure keeps existing rows (page: `Add money and cash-out orders are unavailable.` with `Retry orders`; feed: `Some activity is unavailable`), pending orders poll while visible and settle without blanking loaded rows; automatic continuation while the sentinel is visible (client/activity/use-activity.ts: bounded 3-page bursts with a 250 ms yield), with a reserved loader-height continuation area between requests and on failure; settled Home actions join the timeline only when transfer pages reach their time, while pending ones are never hidden; later-page failure keeps rows and automatically retries the exact cursor up to twice (after 1 s and 3 s) before showing `Try again`; authoritative exhaustion only at a null cursor; cyclic cursors stop without further requests, while non-advancing cursors fail after the bounded retry budget; offscreen, unmounted, or owner-changed continuation stops and fences stale work.
- **Latest-window refresh failure**: A mounted Home pull-to-refresh uses the same latest-window path as after-action refreshes, and pull and after-action requests coalesce. A failed or timed-out latest-window read keeps earlier rows and the existing window visible (page: inline `Latest activity didn't load. Earlier activity is still shown.` status with `Retry latest activity`; Home feed: `Some activity is unavailable` with `Reload activity`) and reports the pull as not refreshed. Retry fetches the latest window before advancing it. This differs from a silent same-window background refetch failure, which keeps loaded rows without the latest-window warning.
- **Card purchases:** The owner-scoped first `/api/activity` page may include Stripe card purchases within the 31-day window, merged into Pending/Recent with the existing card mark and detail sheet. Rows show merchant, amount, and Pending, Declined (with reason when supplied), Completed, Reversed, or Refunded. A card refresh failure preserves recorded card rows and shows `Card purchases may be out of date.`; the standard fixture has no card rows until an `/api/activity` response is supplied. A first-page onchain failure returns a partial response only when card rows exist; transient errors and onchain-unavailable partial pages retry automatically up to twice (after 0.5 s and 1.5 s) before any warning. After retries, a first-load partial retains available card rows with an onchain-unavailable state and retry action. A failed or partial background revalidation preserves previously loaded onchain rows without a warning; a partial revalidation of the same window also shows its fresh card rows, even when its retries end in a transient failure, while a refresh that cannot advance the window during an onchain outage keeps the previous window's card rows.
- **Funding checkout cancellation**: awaiting-payment details keep Continue/Complete payment plus `Cancel deposit`; Cancel is available even outside the resumable region. The awaiting-payment step shows `Pay by <time>` only while that time is still ahead. The pressed button alone loads. Home cancellation updates the sheet and Recent row to `Cancelled` / `Deposit cancelled`, and checkout timeouts show `Timed out` / `Checkout timed out`; both preserve the warning that money already paid can still arrive and stop client polling. Owner cancellation also says `Don't complete it in <provider>.`, the same sentence the Add money status screen uses. An order still being created or with an unknown first provider status (no checkout shown yet) says `Checking with <provider>` and `Home will update this when <provider> confirms it.` Funding chronology and loaded-through filtering use `movedAt ?? updatedAt`. The credential-free `installApiFixtures(page, { activityOrders: true })` fixture implements awaiting-payment POST cancellation; `activity-orders.pw.ts` verifies it from both Home and Activity.
