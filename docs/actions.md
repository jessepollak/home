# Actions

Subsystem design under [architecture.md](architecture.md), Jesse-locked September 11, 2026 and revised September 12. The record rule below (write-once facts) replaces the earlier "no stored result" rule and is re-locked by #915. Architecture owns the cross-cutting principles, client architecture, performance rules, and test policy; this document owns the action contract.

An action is the onchain flow: Home prepares calldata, the user signs, Home tracks one id to a receipt. The `actions` table is a **record** (architecture.md principle 2): a confirmed action is the one thing a provider cannot give back to Home.

## Data model

Database drivers expose `jsonb` differently: `pg` returns parsed objects while Bun SQL may return JSON text, so action metadata is normalized at the query boundary. JSON-RPC error envelopes may carry `id: null`; they remain RPC errors and retain their provider message.

Neon Postgres stays. The full table inventory is in [architecture.md](architecture.md#data-model); this document owns `actions`. Cash-out actions also retain a linked `cashout_orders` record with their last provider observation and settled end state; it is deleted with its action. Native Base SIWE challenges are stateless: the signed HttpOnly challenge cookie carries the address, origin, message hash, nonce, issue time, and five-minute expiry, so challenges create no nonce database row (verified sign-ins separately resolve the customer and credential without blocking the response).

```sql
create table actions (
  id                 uuid primary key,          -- CDP idempotencyKey and EIP-5792 id
  owner_key          text not null,             -- verified subject + smart account + provider
  provider           text not null,             -- 'cdp-embedded' | 'base-account'
  kind               text not null,             -- 'send' | 'card-allowance' | 'savings-deposit' | 'savings-withdraw' | 'trade' | 'borrow' ...
  summary            jsonb not null,            -- what to render: amounts, asset, target, label, typed product metadata
  pending            jsonb,                     -- server-built calls and (trades) permit fields for unconfirmed actions; cleared on confirm, except a trade keeps only its committed calls until a handle or outcome is recorded
  created_at         timestamptz not null default now(),
  confirmed_at       timestamptz,               -- set by POST /confirm; unconfirmed rows are invisible
  confirmed_call_data_hash text,                -- exact confirmed executeBatch commitment for the paymaster callback
  provider_handle    text,                      -- CDP userOperationHash, or the wallet-returned EIP-5792 bundle id for Base
  transaction_hash   text,                      -- a hint from the client, or read server-side from Base wallet status; never a result by itself
  handle_recorded_at timestamptz,               -- first handle or hash post; duplicates do not move it
  account_address      text,                    -- lowercase smart account, so a chain event can find its open actions
  declined_reported_at timestamptz,             -- browser claim of a wallet decline for the current attempt
  dispatch_attempt    integer not null default 0, -- first dispatch is 0; incremented before each retry that follows a rejection
  outcome              text,                    -- 'succeeded' | 'reverted' | 'not_submitted'
  outcome_source       text,                    -- 'chain' | 'wallet'
  settled_at           timestamptz,             -- block time of the including block (chain outcomes)
  outcome_recorded_at  timestamptz,
  observed_receipt_transaction_hash text,
  observed_receipt_block_number numeric,
  observed_receipt_block_hash text,
  observed_receipt_outcome text,                 -- 'succeeded' | 'reverted'
  observed_at timestamptz
);
create index actions_owner_recent on actions (owner_key, confirmed_at desc) where confirmed_at is not null;
create index actions_open_by_account on actions (account_address) where confirmed_at is not null and outcome is null;

```

- **Card allowance exception.** `card-allowance` has `amounts: []`: changing an approval does not spend USDC. After an optional exact per-Action paymaster fee approval, its one call is the server-encoded Base USDC `approve(registeredSpender, amount)`. Set requires a production crypto-wallet Bridge card, a finite customer-chosen amount within the configured maximum, and an eligible fresh card state; revoke permits the current or registered retired spender with amount zero even when the card journey is disabled. Issuance checks the spender registry and maximum again; confirmation of an unconfirmed set rechecks that its spender and configuration remain enabled. All other kinds retain exact same-Action spend approvals and cannot approve a registered card spender. No maximum-uint approval is permitted.
- **Store facts, not a changing status.** Final result and wallet reference facts have one authority and are written once, only while empty; receipt observations can refresh or clear as canonical chain evidence changes. Dispatch attempts increment, and a retry clears the prior decline claim. Evidence that conflicts with a stored result is logged as an `action-outcome` event and never written over it. There is still no `status` column and no `plan_hash` (the server never observes the dispatch, so a hash enforces nothing); status is derived from the facts at read time.
  - Intent and consent: the server, at prepare and confirm (`confirmed_at`).
  - Wallet decline: the browser, labelled as a claim (`declined_reported_at`) for the matching `dispatch_attempt`. The retry route atomically increments the attempt and clears the claim before another dispatch; a late claim for an earlier attempt cannot hide the retry. A declined row with nothing else is not shown in Activity.
  - Wallet reference: the wallet, relayed by the browser (`provider_handle`).
  - Result: the chain, or the wallet when nothing reached the chain (`outcome`, `outcome_source`, `settled_at`, `outcome_recorded_at`). The browser never sets the result: a posted `transactionHash` is only a hint. Both providers are ERC-4337 smart accounts, so the result is the `UserOperationEvent` emitted by a canonical EntryPoint (v0.6, v0.7, or v0.8) in that transaction's receipt whose sender is `account_address` (and, for CDP, whose `userOpHash` equals `provider_handle`), not the bundle transaction's status; a same-signature log from any other contract is ignored. A receipt without such an event writes nothing and reads `unknown`. An attributable receipt reads `confirmed` or `failed` before finality, but the chain outcome is written only after a finalized head at or above its block and a matching canonical block hash. A wallet outcome and a transaction hash cannot coexist: whichever is recorded first excludes the other atomically. A Base wallet status 4xx (never reached the chain) is recorded as `not_submitted` from the wallet; a 5xx/6xx records the wallet's transaction hash and the chain read records `reverted`, or the wallet's `reverted` when no hash is returned.
- Status at read time:
  - `confirmed_at` null → not shown; lazily deleted after 1h by `GET /api/actions`.
  - `outcome` set → `succeeded` reads `confirmed`; `reverted` and `not_submitted` read `failed`. No further provider or chain reads happen for that row.
  - confirmed, no outcome, no `transaction_hash`, younger than 15 min → `pending`; older → `unknown` (never "not sent"). The window starts at `handle_recorded_at` when a handle was recorded, otherwise at `confirmed_at`, so a wallet approval left open past 15 minutes still gets its grace period once submitted. `unknown` rows without a hash are dropped from Activity after 24h because they can never be matched to a chain row. Cash-out rows are the exception described under [Cash-out retention](#cash-out-retention): their Activity item follows the linked provider order, and that order keeps refreshing after the action's own outcome is written.
  - `transaction_hash` set, no outcome → the server reads the receipt; an attributable receipt reads `confirmed` or `failed`, persists its transaction hash, block number, block hash, outcome, and observation time, and writes the immutable chain outcome only after finality. A recorded outcome always wins; otherwise a fresh attributable receipt wins, while an unattributable receipt reads `unknown`. A null receipt clears a prior observation only when the finalized head reaches its block (verified reorg drop); before then, and on read failure or deadline, the prior observation retains its `confirmed` or `failed` status. Without an observation, a null receipt reads `pending`, and an unreadable receipt follows the 15-minute window: `pending`, then `unknown`. A transaction hash by itself never confirms an action. The action `summary` still wins **kind and label** over the chain row (a savings deposit is "USDC → 0xVault" on chain; Home says "Deposited to Savings").
- Balances are an observation, not a record; their table and rules live in [balances.md](balances.md).
- The version-1 `CashoutProgress` projection optionally includes `depositBlockNumber` from the deposit action's persisted successful receipt observation only when the receipt's outcome is finalized as succeeded and its transaction hash matches the action's hash. An observed but unfinalized receipt deliberately keeps its observation, so projecting that block early could count escrow beside wallet USDC restored by a reorg; before finality the estimate stays indeterminate. Older cached progress without the field remains valid. Home uses that block to avoid counting Peer escrow alongside a pre-deposit wallet snapshot; see [pending cash-out](balances.md#pending-cash-out). The projection also carries `progressConfirmed`, which is true when this request wrote a confirmed progress row for the order (from a provider order read or a verified withdrawal receipt); a record returned from storage without a successful write this request is unconfirmed, and Home treats unconfirmed in-progress progress as indeterminate rather than exact. Progress writes are revision-conditional on the provider observation time: an older observation cannot overwrite a newer persisted record and is never marked confirmed, so two concurrent refreshes cannot persist a stale higher remainder; an equal-time observation is only accepted when it does not regress filled, returned or remaining. A receipt or local write does not advance the provider revision and applies only when the row still matches the revision the request read, an undated provider observation is treated the same way because it has no ordering basis, and no write applies once the deposit link has been reassigned. Older cached progress without `progressConfirmed` remains valid. A same-owner cash-out or cash-out-withdrawal row that the client parser rejects (a missing required summary field, a malformed amount entry, an unrecognized kind carrying cash-out progress, or a withdrawal whose deposit link is blank) is reported as incomplete rather than silently absent, so the pending estimate becomes unreadable instead of dropping escrow.
- Ponder or any self-hosted indexer: no. Home's data is defined by users, not contracts; CDP SQL API and Token Balances already provide indexed data as a service. Revisit only if Home ships its own contracts or CDP's data APIs hit a measured limit.

## Flow

1. `POST /api/actions/prepare` `{kind, params}` → server verifies scope, builds calldata, inserts an unconfirmed `actions` row, and stores the draft calls in `pending` for every kind. Borrow summaries also store typed operation and market identity so compound actions render without title parsing. Savings summaries store typed operation, exact amount, configured vault identity/name, Base chain, current source-block fee/limit/share preview, deposit minimum-shares bound, expiry, exchange constraint, and discovery-rate freshness; issuance validates and normalizes that typed savings schema before persistence, and owner-scoped reload/list parsers retain only metadata that still passes the same validation. Clients never recover these facts by parsing warnings. Save deposits go through Morpho Bundler3/GeneralAdapter1 `erc4626Deposit` with a 10 bps share-price bound and an exact USDC approval to the adapter. It returns `{id, calls, summary, expiresAt}`. Trades return `{id, calls, summary, signing, expiresAt}` and additionally store the permit hash, swapCallIndex, and quote expiry in `pending`.
2. Client shows review. `GET /api/actions/:id` is owner-scoped and returns the unconfirmed summary plus `pending.calls`, so a reload mid-review can resume. On confirm: `POST /api/actions/:id/confirm` (sets `confirmed_at`, returns the final `calls`, and clears `pending`; for trades the body carries the Permit2 `signature`, the server verifies the signer is the owner and splices it — this is the kept half of `finalize`). The first confirm records an `action.confirmed` operator event, idempotent by action id and unable to affect the response. The client dispatches only on 2xx. It parses the confirm response with the shared parser, which requires a nonempty batch of well-formed calls (20-byte `to`, even-length hex `data`, uint256 decimal `value`, and well-formed `approval`) and lowercases address and hex data; a response that fails parsing is unavailable and dispatches nothing. Reload-resume is intended only before confirm; after confirm the tab owns dispatch and any live retry.
3. Dispatch: CDP `sendUserOperation({ idempotencyKey: id, calls })` → `provider_handle = userOperationHash`. For Base Account, confirm attaches a gas hint only to nonempty batches where every intermediate call is an exact ERC-20 `approve(address,uint256)` or `transfer(address,uint256)` with two encoded 32-byte words; an intermediate transfer also requires every earlier call to be such an independent approval or transfer. The wallet estimates non-overridden calls independently of earlier calls in the batch, while the first sees true state and the last receives the override. A sell whose swap sits between an approval and the fee transfer therefore skips the hint; a sell batch of only the swap and fee transfer keeps it. Eligible batches are estimated as the exact finalized ordered Coinbase smart-account `executeBatch` against `latest`, with bounded headroom returned as the optional aggregate budget; other batches omit the hint and use the wallet's own full-batch estimate. Estimation or capability failure is non-blocking and simply omits the hint. The Base connector maps a present budget to `capabilities.gasLimitOverride.value` on only the final `wallet_sendCalls` call. When the action carries a USDC [network fee](#network-fees), the request-level `capabilities.paymasterService` names the action's paymaster callback; calls and request fields are otherwise unchanged. Base `wallet_sendCalls({ id, calls, atomicRequired: true })` → `provider_handle` = the bundle id the wallet returns (not the request `id`; Base generates its own, and `wallet_getCallsStatus` only accepts that one). Provider-authenticated validation remains required because keys.coinbase.com honoring this call-level override as a full-batch budget is not yet verified.
4. `POST /api/actions/:id/handle` `{providerHandle}` and later `{transactionHash}` once the client resolves it from `getUserOperation` / `wallet_getCallsStatus`. Retried while the tab lives; late posts are accepted, and a duplicate post changes nothing. The hash is a hint: the server writes the result only from its own receipt read. The server follows the action to its result itself once the handle arrives (see [Follow-through](#follow-through)), so the browser may stop right after this post. On an explicit wallet rejection the client fires one detached, best-effort `POST /api/actions/:id/decline` `{version: 1, attempt: n}` (first attempt is 0); the rejected result never waits for this report. Before redispatch after rejection, the client awaits the bounded decline report and calls `POST /api/actions/:id/retry` `{version: 1, attempt: n + 1}`. The retry must succeed before provider dispatch; if it fails nothing is dispatched and the customer may try again, while an ambiguous provider failure remains cached and cannot be retried. A response reports only a persisted outcome; if the outcome write fails, the action stays unresolved until a later read records it.
5. `GET /api/actions` returns up to 100 of the owner's confirmed rows with derived status: the last 24h, plus the cash-out rows under [Cash-out retention](#cash-out-retention). Activity = chain activity ∪ those rows, deduped by `transaction_hash`. `ConnectedActivityPanel`, `action-toasts.tsx`, and the money result read this route through one shared query policy (`client/actions/recent-actions-query.ts`). When the action store cannot be read, this route and `GET /api/actions/:id` return `503 ACTIONS_UNAVAILABLE` and record an `action-read` `ACTIONS_STORE_UNAVAILABLE` event rather than an empty 500. The client retries only transient failures (network, 429, 5xx) at most twice (after 0.5 s and 1.5 s), and refetches a failed read on focus or reconnect. Activity and toasts do not poll to recover a failed read; they poll only for an unsettled cash-out (below), and the money result keeps its pending-status poll. A failed refetch within 2 minutes of the last successful read keeps the loaded rows without a warning; Activity schedules one re-evaluation at that boundary, so a persisting failure then shows the outage warning and "Retry recorded actions" on a focused tab. A response without an `actions` array is a contract failure, not empty history; individually malformed or foreign-owner items are skipped so valid records stay visible. The recent-recipient route separately reads up to 100 successfully dispatched send rows across the owner's full action history, then returns at most three distinct recipients.

### Cash-out retention

A cash-out can wait in escrow far longer than a day, so `GET /api/actions` keeps these rows beyond the 24h window, hash or not:

- `cash-out` whose `cashout_orders` record is unsettled, or that has no record yet (created lazily on the next list): kept until the order settles, with no age limit.
- `cash-out-withdraw` (product `cashout`, operation `withdraw`) whose `depositId` matches an unsettled `cashout_orders` deposit: kept while that order is unsettled, so an in-flight cancel stays visible.
- Any `cash-out` or `cash-out-withdraw`: kept for 30 days after confirm, so a settled item still shows its end state ("Paid to …", "Returned") after Home was closed.

The 100-row cap applies to the combined set. Rows kept for an unsettled order sort ahead of everything else when the cap is applied, so a pending cash-out is never pushed out by newer actions; the returned rows are then ordered by `confirmed_at` descending.

Cash-out order refresh runs after the list's 3 s reconcile deadline, under its own separate 3 s deadline, so a list can spend about 6 s on reconcile plus refresh. Every cash-out provider order read and chain receipt read stops waiting when the refresh deadline passes, the response returns the last stored progress, and the next list resumes the refresh. Each list refreshes at most two cash-outs and spends at most two provider reads, giving both to the cash-outs whose last refresh began longest ago. A cash-out's refresh is stamped and counted before its first deposit or withdrawal receipt read or provider read, so a refresh receipt read that settles or fails still spends one of the two refreshes, the refresh never reads receipts for every cash-out in one list, a slow or failed read of either kind still rotates, and every unsettled order eventually gets a provider read. The per-row outcome read under "Status at read time" in [Data model](#data-model) is separate and stops once the outcome is written.

The recorded hash alone never settles a cash-out, because `/handle` checks only hash syntax and row ownership. A linked order always follows its provider state. An unlinked one links from the receipt only after the action's outcome is finalized and the receipt's deposit order matches the action. While the receipt is included but not yet finalized, a matching order updates the displayed status only: it is not linked, cannot be cancelled, and never settles, so a reorganized block cannot leave a stale link behind. Receipt proof replaces a same-owner link inferred by listing provider orders, releasing the displaced action to resume recovery; it never replaces another receipt-proven or another owner's link, and an action whose receipt proof is refused that way is a duplicate and settles as failed. When the receipt reverted, its status or its deposit logs cannot be read, it has no deposit, or it names an order that does not match, the owner's provider orders are listed instead: a single unclaimed order that matches the action's amount, platform, currency, and payee hash, and changed after prepare is linked. An action recorded before the payee hash was stored first derives it from its recorded canonical handle through the provider; if that fails, the action stays unlinked and unsettled until a later refresh. Settling as failed needs a finalized reverted outcome, or a hashless action with no handle past the 15-minute window, and also that no unclaimed order matches the amount, platform, currency, and payee, and none is undated. A provider that cannot be read leaves the order unsettled, so it keeps its recovery path.

Terminal return waits for finality. A cancel withdrawal's receipt settles the cash-out as returned only after the withdrawal action has a finalized succeeded outcome, and a provider order that reads returned stays refreshable while any Home withdrawal for that deposit is unresolved: it has a transaction hash or wallet handle without an outcome, or it was confirmed within the last 15 minutes and the wallet has not declined it. The list projects that same dispatch rule as `withdrawing` for each linked deposit; Activity uses it to show "Returning" and hide Cancel, not the linked withdrawal's pending/unknown display status. A hashless, handleless cancel past the window or marked declined no longer blocks Cancel. Provider `delivered` takes precedence over unresolved or confirmed-but-unverified withdrawal display states and reads "Paid to …". An included but unfinalized receipt never makes a cash-out terminal, so a reorganized block cannot leave Activity claiming a return that did not happen. Activity and the toast observer keep refreshing every 15 seconds while the tab is visible and any non-failed cash-out is unsettled, including one that already reads "Returned".

Named send recipients are resolved server-side before issuance. Base `.base.eth` names use the configured Base RPC; standard `.eth` names use `ETHEREUM_RPC_URL` (or the documented public local fallback). Both paths disable CCIP Read and fail closed, so ENS gateway URLs can never trigger server-side fetches.

After a savings handle or transaction hash is recorded, the existing fresh-until-moved run matches action amount `assetId`s against either a balance holding registry `id` or its CAIP `key`. This lets USDC and vault-share movement converge the shared Home/Cash/Savings balance snapshot before Actions, Activity, and other indexed scopes are refreshed again. A failed refresh retains no invented value; owner-generation changes cancel the old owner's run. Confirmed, failed, and hashless unknown records continue to use the status rules above rather than a Save-specific execution path.

### Follow-through

The server follows every identifiable action to its result without the customer present. It uses three triggers and no scheduled job ([architecture.md](architecture.md) rule 3): a scheduled re-check is added only if the unresolved count shows a measured gap. Every trigger runs the same step and writes only through the write-once rules above, so triggers that race change nothing twice.

- **The step.** Without a transaction hash, the handle is resolved to one. Base Account asks the Coinbase Wallet status RPC (`BASE_ACCOUNT_STATUS_RPC_URL` override for tests/staging): a completed (2xx) or reverted (5xx/6xx) response fills the transaction hash, and an offchain failure (4xx) records `not_submitted`. CDP embedded, and a Base handle shaped like a 32-byte hash when the status RPC cannot answer, read the chain directly: `eth_getLogs` on the configured Base RPC for the canonical EntryPoints' `UserOperationEvent` whose `userOpHash` is the handle and whose sender is `account_address`. The log search covers the action's own window: the hour after its estimated confirm block and, when the wallet reference arrived later, the hour after that arrival as well, newest window first. Both windows are always scanned in full within a budget of three requests: when they need more chunks than that, a window's oldest chunks merge into one request, so no covered block is dropped and a wallet approval left open for hours stays resolvable without losing a log that landed near confirmation. Exactly one match fills the transaction hash; anything else leaves the row open, reading `pending` while a covered window is still open and `unavailable` once every covered window has elapsed without a match. With a hash, the receipt read above observes and, after finality, records the outcome. Provider errors, malformed responses, and timeouts leave the stored action unchanged; a response that conflicts with a stored fact is logged and leaves it unchanged. These calls are status-only and never recreate, alter, or dispatch calldata.
- **When the handle arrives.** A `/handle` post for an action that is still unresolved schedules the step after the response (Next `after`), repeating with a short backoff for up to 45 s until the row has an outcome or an attributable receipt observation. At most one attempt is scheduled per action every 15 s per server instance, so a retried post never stacks work but a duplicate post after 15 s retries the step when an earlier attempt did not run. The chain outcome is still written only after finality, which usually comes later; the observation already reads `confirmed` or `failed`, and a later trigger or read records the outcome.
- **When the chain reports activity.** Every address that confirms an action is subscribed to the CDP wallet-activity webhook, as a balance read already does ([balances.md](balances.md)). A verified activity delivery schedules the step for up to 10 open, identifiable actions (a handle or hash, confirmed in the last 7 days) per matched wallet address (`matchedAddress`, or the activity's own `address`), most recent first for each wallet, capped at 200 in total across at most 50 addresses, under a 25 s deadline, after the 200 response. The cap is allocated per wallet, so a busy wallet cannot crowd out the action that triggered the delivery for another matched wallet. Rows run four at a time, each with its own 15 s budget alongside the shared deadline, so a slow row does not hold up the others; a step cut short never invents a result, keeps the write-once facts it already recorded, and leaves an unfinished row open for the next trigger. Counterparties (`from`/`to`) still invalidate balances but never enter settlement; a payload with no matched field settles the extracted addresses instead.
- **When an operator opens the overview or customer list.** An authorized operator page view schedules the step for up to 10 open, identifiable actions confirmed in the last 30 days, rotating over the 200 newest, under a 20 s deadline and at most once per server instance every 30 s. Rows run four at a time, each under a 15 s budget alongside the shared deadline.
- **Owner reads.** Owner-scoped action reads still run the step for up to 5 rows past a 20 s client grace period, for both providers.

A confirmed action with no handle and no hash cannot be identified by any trigger. It stays open and is counted as unresolved; Home does not guess a match from chain activity.

### Retry semantics

Verified against the installed SDKs:
- **Shared rule:** an explicit user rejection is definitely not submitted by that invocation. Return a typed `rejected` result, evict only that rejected dispatch promise, and permit another user-initiated attempt in the same tab. An ambiguous provider or transport failure stays cached and is never dispatched again. The executor reports it as `dispatch-unknown` (the provider may have received it) and a lost confirm or handle response as `submission-unknown`. Send, Save, Borrow, Card and Trade show both as the "can't confirm, check Activity" result without Retry; only Trade offers same-action Retry, and only for `submission-unknown`.
- **Concurrency:** Home does not serialize money actions per owner: several actions, including trades, may be in flight at once. A separately prepared and signed action is a new intent. Duplicate protection is per action: a repeated trade confirm returns only the same committed call data; same-action Retry, cached ambiguous dispatch that is never redispatched, and the CDP idempotency key prevent duplicate submission. Stock eligibility and execution-deadline checks still apply on replay and retry. A guard across actions exists only where Home could not tell a new action from an unresolved one: Peer cash-out refuses a new cash-out whose amount, platform, currency, and payee match an unresolved local one, and one whose amount, platform, and currency match an in-flight provider order (the payee hash cannot be derived before preparation without registering the payee). Onramp `AMBIGUOUS_ORDER_OPEN` stays provider-scoped because the identity of an ambiguous external fiat order at the provider is unknowable.
- **Pending-trade compatibility:** `GET /api/actions/trade-pending` remains only for trade dialogs loaded from an earlier bundle, which check it on open and keep Continue disabled when it fails. It authenticates the owner and always answers `{ version: 1, trade: null }`. Current clients do not call it; remove it once earlier bundles are no longer served.
- **CDP:** `sendUserOperation` is one `POST …/smart-accounts/{addr}/send` carrying `X-Idempotency-Key` (`@coinbase/cdp-core` web build; `@coinbase/cdp-api-client`). Prepare, sign, and broadcast happen inside CDP under that key; a replay with the same id returns the identical `userOperationHash`. Replay is therefore the handle-recovery path while the tab lives. The body must be byte-identical (the wallet secret id changes after re-auth); treat `idempotency_error` as sent-unknown and stop. An explicit SDK user cancellation (`MfaError` with `CANCELLED`) is retryable; a transport abort or other ambiguous failure is not. There is no lookup-by-key or list endpoint, so a lost handle after the tab dies stays `unknown` until the chain shows it.
- **Base Account:** the SDK forwards `wallet_sendCalls` to the popup unchanged; there is no SDK-side dedup, and duplicate-id behavior at keys.coinbase.com is unverified. A provider `4001`, normalized to `BaseAccountConnectorError("cancelled")`, is retryable. Any ambiguous failure remains single-dispatch; `wallet_sendCalls` is not invoked again automatically.

## Owner fence

One `ownerGeneration` counter replaces the four-field fence in `cdp-session-lifecycle.tsx`. It is sufficient with these rules:
1. It is a synchronous `useRef`, never React state.
2. It is captured at prepare and re-checked before every provider call and every server POST, not only on results.
3. It bumps on sign-in, sign-out, provider switch, Base `accountsChanged` / `chainChanged` / `disconnect`, and loss of server-session verification.
4. Sign-out awaits SDK cleanup before a new sign-in may begin.

## Failure modes we accept

- Send succeeded, handle post lost, tab closed: no trigger can identify the row, so it stays unresolved and reads `unknown`; Activity shows the transfer when indexed; the row ages out of Activity at 24h.
- Owner switch mid-flight: the generation fence drops the work before the next call.
- Provider outage: show the provider's error; there is no local state to reconcile.
- Indexer latency bounds the `unknown` window; measure it on preview and tune the 15 min / 24h constants.

## Constants

| Constant | Value | Why |
|---|---|---|
| Unconfirmed row retention | 1 h | a draft the user never confirmed is noise; deleted lazily by `GET /api/actions` |
| Confirmed without hash → `unknown` | 15 min | bounds how long "pending" can be claimed without provider evidence |
| Hashless `unknown` dropped from Activity | 24 h | can never be matched to a chain row; cash-out rows excepted |
| Settled cash-out retention | 30 d | the end state stays readable after Home was closed |
| Unsettled cash-out retention | until settled | escrowed money must stay visible and cancelable |
| Post-action hot window (balances) | 60 s | set by `/confirm` and `/handle`; see [balances.md](balances.md) |

## Unverified assumptions (verify on preview, once)

Balances-side assumptions (CDP Token Balances index lag after a send, CDP Node request budget, `wallet.activity.multi` payload and address packing) live in [balances.md](balances.md).

- The stock guard runs before trade preparation and before confirmation, including a confirmed trade replay: a stock buy requires a trusted, valid non-US/non-US-territory edge request country; a stock sell to Base USDC is reduce-only and always allowed. It ignores the customer's country preference and client-supplied country. Restricted buys return `TRADE_STOCK_RESTRICTED` (403). An exact token-authorization provider refusal returns `TRADE_NOT_ROUTED` (422), without exposing provider text. The current any-token trade path excludes tokenized stocks.
- The cash-out region gate runs before cash-out preparation and again before confirming an unconfirmed cash-out deposit, using the region persisted in the action metadata rather than client input. The confirmation also re-reads the operator corridor offering for that persisted provider, region, and direction under a 3-second deadline. An operator removing the region or pausing the corridor between prepare and confirm refuses the confirmation with `CASHOUT_UNAVAILABLE` (502); settings that are unreadable, or a read that exceeds its deadline, fail closed with `CASHOUT_SETTINGS_UNAVAILABLE` (503). Cash-out withdrawal, recovery and trade replay never read the region policy or the corridor setting.
- Cash Convert reuses this USDC trade route, not a separate swap path: USD/USDC → EUR/EURC, USD/USDC → IDR/IDRX, EUR/EURC → USD/USDC, and IDR/IDRX → USD/USDC. EUR ↔ IDR is not offered. These supported entry pairs are not a guarantee of live executability; each amount still depends on the swap provider returning a valid executable quote. The currency picker checks trade availability, and prepare reports an actionable no-route state when the provider cannot quote a pair.
- The trade prepare path supports exact Base ERC-20 ↔ USDC pairs except USDC itself and tokenized stocks using the existing action flow. It requires the verified smart account signer, requests an executable quote under a fresh provider-only request key, reads the current Base block and registry Settler, and validates every quote and Settler action before review. Prepare rejects a quote whose Permit2 nonce is already used at the pinned block, reads the from-token balance and Permit2 allowance from chain at that block, and rejects insufficient balance. RFQ maker output-token balances and Permit2 allowances must each cover the maker's permitted amount at that same pinned block; an unavailable read fails closed. The server reads the audited `fees` settings domain before quoting; an unreadable or invalid policy returns `TRADE_UNAVAILABLE` and no draft. A zero rate, absent recipient, amount that rounds to zero, or recipient equal to the taker omits the operator fee, since a self-transfer cannot collect it. For buys, the input is gross USDC: the swap and exact Permit2 authorization spend gross minus the floor-rounded operator fee, while the customer review and balance check use gross. The server-authored USDC `transfer` fee call precedes Permit2 approvals and the swap; any paymaster approval goes first. For sells, the swap spends all quoted tokens and is followed by a USDC fee transfer computed from the guaranteed minimum output; the customer review shows estimated output minus the fee and guarantees minimum minus the fee. Both fee calls are in the same atomic batch as the swap, and issuance rejects a missing or altered fee call. The collection strategy currently uses in-batch transfer because CDP Swaps has no integrator fee parameter; a provider-native seam is inactive until the provider can actually bind the same fee during quoting. Settings changes affect new quotes only; prepared calls stay fixed. Exact Permit2 approval, if chain allowance is short, precedes the swap; the paymaster fee approval, if selected, precedes both. Unknown selectors fail closed. Confirm verifies the reviewed owner signature and appends its wrapper to the exact pre-signature swap calldata. A repeated confirm of a confirmed, undispatched trade (no provider handle, transaction hash, outcome, reported decline or later dispatch attempt) returns the exact committed calls, matched against the stored call-data commitment, without re-signing, so a lost confirm response can still dispatch the same signed trade; it is refused once the effective execution deadline (earliest of taker and RFQ maker permit deadlines) is within 30 seconds. Lost confirm or handle responses can retry the same action, but an ambiguous provider dispatch is cached and shown without a Retry affordance. The client first tries that replay after an unanswered signed confirm and signs again only when the server reports that the action was never confirmed. Retry is refused once the effective execution deadline is within 30 seconds. No pool allowlist is applied: recipient, buy token, minimum receive and Permit2 scope bind the trade, and Settler reverts atomically if the minimum is unmet. A funded buy/sell and wallet-provider compatibility still need live confirmation.

- CDP idempotency window (documented 24h) and same-key-different-body behavior are documented, not observed live.
- keys.coinbase.com duplicate-id behavior for `wallet_sendCalls` is unverified; mitigated by never auto-retrying.
- Indexer latency is unmeasured.
- Result attribution assumes both CDP smart accounts and Base Accounts settle through an EntryPoint that emits the standard `UserOperationEvent`, and that a Base 5xx status returns the reverted transaction's hash. A live confirm on preview must show the action as `confirmed`, not `unknown`.
- Follow-through settles four questions on one preview check: which EntryPoint version CDP accounts log (`USEROP_LOG_V06`/`V07`/`V08` `action-reconcile` codes), whether a Base batch id is itself a user-operation hash (`BASE_USEROP_LOG_*` codes), whether a revert that moves no tokens still fires the activity webhook, and the webhook's production delivery format (`WEBHOOK_ACTION_*` codes).

## Network fees

When the server-only HTTPS `CDP_PAYMASTER_URL` is configured, Home quotes the CDP ERC-20 paymaster on Base with a forced USDC-only ERC-7677 context. Only EntryPoint v0.6 is supported. The quote uses `pm_getPaymasterData`'s real `tokenPayment.maxFee`, never the stub's placeholder; this is the exact `approve(paymaster, maxFee)` prepended to the same smart-account batch. Trade gas estimates using a provider swap gas limit also include explicit allowances for each approval and the operator USDC transfer; both USDC and ETH network-fee paths cover that leg. Undeployed CDP embedded accounts are quoted with the verified owner's factory `createAccount` initCode and extra deployment verification gas; undeployed Base Accounts without a verified owner retain the native-fee fallback. The customer pays the fee: Home never requests sponsorship. The approval is specific to that prepared action, not a standing allowance. Home uses USDC only if the current USDC balance covers the action’s USDC spend plus the quote; otherwise it uses native ETH when the account can cover estimated gas, including the deployment verification gas for an undeployed account. The USDC balance, ETH balance, and deployment reads are independent: a failed read disables only the path that depends on it. If neither can pay, prepare returns `NETWORK_FEE_UNFUNDED` (409), with an ETH funding recovery message for undeployed accounts without a USDC path; if the paymaster quote or a required read is unavailable and native gas cannot be verified, prepare fails (502) instead of issuing unquoted USDC calldata. With the variable unset, existing ETH-only actions are unchanged.

The wallet calls `POST /api/actions/:id/paymaster` without a Home session or the deployment-access cookie, so the access gate exempts exactly this UUID-shaped path; the action binding below remains its authorization. The callback is covered by the required [Vercel Firewall rate-limit rule](vercel-deploy.md#pre-release-production-access). The callback accepts only a recent UUID action with a persisted USDC fee, approved sender, Base chain ID, EntryPoint v0.6, and allowlisted ERC-7677 methods. The paymaster callback only serves confirmed actions and only the exact confirmed `executeBatch` calldata. Its sole upstream transport overwrites the request context with USDC. Sponsored or non-USDC results and fees above the stored per-action approval fail as JSON-RPC errors; callers must prepare again when a quote changes. `GET /api/actions/network-fee` is session-authorized and returns a Max reserve of 0.10 USDC for a deployed account or 0.50 USDC for one not yet deployed or whose deployment state cannot be read; it returns null when the paymaster is off, the session has no smart account, or an undeployed Base Account must pay its deployment fee in ETH. Prepare accepts a USDC quote only up to the reserve for its deployment state, so Max leaves room for the fee; a larger quote falls back to ETH when the account holds enough, and otherwise prepare reports the fee as unavailable. Policy request failures or malformed responses leave the USDC Max and percent controls unavailable rather than exposing the full balance; only a successful null reserve means the policy is disabled. The paymaster URL contains a credential and is never exposed to the browser.
