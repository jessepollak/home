# Cards

Status: design of record for [#821](https://github.com/jessepollak/home/issues/821), September 24, 2026; the Immersve + Bridge event seam is implemented against offline fixtures, not live-provider credentials or a card program. Providers: **Immersve** (self-custodial Mastercard program, built first) and **Bridge** (Bridge + Stripe Issuing), behind one [provider seam](#provider-seam). Decision: [product strategy](product-strategy.md#implementation-questions-still-open). This page authorizes synthetic public-sandbox probes only; it does not authorize a private sandbox, production program, mainnet approval or deposit, or live card spend.

## Customer model

A verified, eligible customer gets a virtual card that spends USDC directly from their Home smart account. The card balance and the cash balance are the same balance (Jesse, September 24, 2026).

- **Approval-based funding is the target.** Immersve documents approval-based funding on Base: the customer grants a standard USDC approval and spends from their existing wallet with no deposit transaction ([Immersve funding protocols](https://docs.immersve.com/guides/funding-protocols/)). USDC stays in the smart account until a purchase draws it, so Home shows one cash balance and the card's available spend is `min(wallet USDC, remaining allowance)`, subject to Immersve limits. The approval mechanics (funding type, approved contract, whether the draw happens at authorization or clearing, refund path) are not publicly documented yet (Q6).
- **The allowance is the card's spend limit.** The customer chooses a finite USDC allowance for the Immersve spender, sees it on review, and can raise, lower, or revoke it at any time. This is the first standing allowance under the bounded-approval rule below.
- **Deposit-based funding is the fallback** if approval-based funding is unavailable for Home's program. It moves USDC into a separate card balance, which Home would count inside the cash total as a non-sendable component with its own provenance, plus the double-count guard. Its prepare gate is kept below.
- **Purchases** are Immersve payment events (`Holding`, `Cleared`, `Reversed`) projected into Activity. With approval-based funding the onchain draw is also an ERC-20 transfer from the customer's account, so Activity must join the payment event and the transfer into one row instead of showing both.

Refresh tokens rotate once; compare-and-swap the prior envelope on replacement; failed rotation means re-login, never retry. |

| Events | Provider-scoped webhooks | Immersve: register `…/api/cards/webhooks/immersve` as the listener URL; Immersve POSTs to that URL plus `/<topic>`. Reject unknown URL topics and require the signed envelope topic to match the segment. RSA-SHA256 over `{X-Delivery-ID}:{X-Key-ID}:{raw body}` against the configured-mode JWKS, verified before trusting parsing; issuer pinned to the mode's host. Test and Live JWKS published identical signing keys when checked on September 24, 2026, so the signed issuer check is essential. Dedupe on `(provider, mode, eventId)` with insert-on-conflict; out-of-order events only invalidate provider observations and never apply deltas. JWKS fetches are allowed for signature verification; no transaction or Funding Source fetch occurs in the handler. 3DS/OTP material and KYC payload bodies are never persisted. Handled and deliberately rejected deliveries (including disabled/misconfigured ingress, malformed bodies or signatures) receive 202; disabled ingress returns `accepted:false`. JWKS failures or unknown signing keys, database failures, and the 14-second processing deadline return retryable 503 so Immersve can redeliver. Provider/mode/event-ID dedupe makes retries safe. Bridge customer/KYC deliveries use `/api/cards/webhooks/bridge`, and Stripe Issuing deliveries use `/api/cards/webhooks/stripe`; both are inert unless all Bridge settings are valid. Bridge signatures use the per-endpoint RSA public key and its `t` millisecond header plus raw body digest (10-minute replay window); Stripe signs `t` seconds plus the raw body with the endpoint's HMAC secret (5-minute window, multiple `v1` signatures). Stripe event `api_version` must match the configured `BRIDGE_STRIPE_API_VERSION`. Bridge and Stripe IDs share the `bridge` provider namespace; Stripe event IDs are prefixed `stripe:`. Both routes return 202 for deliberate rejection (disabled returns `accepted:false`), 400 for validly signed but stale deliveries (so the provider retries with a fresh signature), and 503 for transient failures. No customer/card/KYC body is stored. |
| Provider egress | `server/cards` client | HTTPS to pinned Immersve origin only, bounded timeout, manual redirects, secrets never logged. |

**Bounded-approval rule (replaces exact-approvals-only; Jesse, September 24, 2026).** Home's current Actions rule allows an approval only when it equals a spend in the same Action. That blocks any recurring spender. The replacement: every delegation of spend is bounded and purpose-bound. (1) A one-shot Action still uses an exact approval equal to its spend. (2) A standing ERC-20 allowance is allowed only for a spender registered to a product in server config (first: the card provider's program spender), for a finite customer-chosen amount below a product maximum, shown on review with spender and purpose, and revocable through the same Action kind. (3) The same rule covers a Base Account spend permission if a future funding strategy uses one: registered delegate, token, cap, period, expiry, and revocation shown on review. (4) Max uint, unregistered spenders, and unbounded permissions stay rejected. Slice 2 implements this in `server/money-actions/issue.ts` and updates [architecture](architecture.md) and [actions](actions.md) in the same PR.

## Provider seam

Home converges on two providers, **Immersve** and **Bridge** (Bridge + Stripe Issuing) (Jesse, September 25, 2026). Immersve was built first against its public sandbox; Bridge now has an offline event adapter, while live Bridge integration awaits sandbox access. Each customer routes by region to an available program: Immersve covers most non-US regions today, and Bridge is the likely US path. Both document approval-based funding on Base without prefunding ([Immersve funding protocols](https://docs.immersve.com/guides/funding-protocols/), [Bridge noncustodial cards](https://apidocs.bridge.xyz/platform/cards/overview/noncustodial)). Bridge pulls the purchase amount at authorization (subject to its overcapture allowance below); Immersve's pull timing remains open (Q6). Pomelo informs a future strategy where Home authorizes each purchase in real time; it is not planned. Lightspark Grid Cards is not a fit today: cards spend from a Grid account or a Grid embedded wallet holding USDB on Spark, not from a Base smart account ([Grid card funding sources](https://docs.lightspark.com/cards/card-management/funding-sources)). Immersve lists the United States as coming soon ([Immersve regions](https://docs.immersve.com/guides/regions/)), so US customers depend on Immersve's rollout or on Bridge.

- **`CardProvider` now implemented** (`server/cards/provider.ts`, adapters under `server/cards/immersve/` and `server/cards/bridge/`): declare `FundingStrategy` and verify/normalize a signed notification into `{provider, mode, eventId, kind, externalIds, occurredAt}`. A shared handler stores only that allowlist with provider/mode-scoped dedupe. Immersve declares `deposit` for its currently configured universal-EVM channel; Bridge declares `allowance-pull`. These declarations do not authorize funding, issue a card, or start egress.
- **Future adapter capabilities (not implemented):** enrollment and KYC state; issue, list, read, freeze, unfreeze, and cancel cards; browser-only detail reveal; fresh provider reads. Do not add lifecycle methods to the port before a caller exists. Immersve approval-based funding remains the target after Q6; `realtime-authorize` requires its own money and legal decision.
- **Shared, provider-neutral:** event dedupe keyed by `(provider, mode, eventId)` is implemented. The owner-to-cardholder link, eligibility and KYC state, `card-allowance` Action and bounded-approval rule, Activity rows joining payments and onchain draws, and fresh provider reads remain future slices.
- **Immersve-specific (do not generalize):** SIWE sign-in and deploy-first enrollment, cardholder token rotation, the `<listenerUrl>/<topic>` JWKS-signed envelope, `Holding`/`Cleared`/`Reversed` states, Funds Storage config, and PAN-token URLs. Bridge instead uses Bridge customers with a `cards` endorsement and Persona-hosted KYC, Stripe Issuing for card operations, Stripe Elements for card-detail reveal, and two event sources (Stripe webhooks for cards and transactions, Bridge webhooks for customers and KYC) with different signatures.
- **Available to spend** is computed by the funding strategy, not assumed: for `allowance-pull` it is bounded by wallet USDC and remaining allowance, then by provider limits the adapter reports. Bridge may [pull an additional amount at authorization](https://apidocs.bridge.xyz/platform/cards/overview/noncustodial) based on merchant category and the overcapture upper bound, refunding any difference after settlement. Home still shows one cash balance; a Bridge wallet can temporarily dip below the displayed balance minus hold, reducing available-to-spend until settlement and refund observation.
- **Bridge pull and Activity:** Bridge's [onchain pull is asynchronous](https://apidocs.bridge.xyz/platform/cards/overview/webhooks); a Stripe authorization event may arrive before the onchain transaction is confirmed. Activity must keep the authorization pending until the pull is observed, rather than treating Stripe approval as funded settlement. Bridge refunds are also asynchronous and may be batched; reconcile their observed onchain movement with provider reads instead of assuming one refund transfer per authorization.

The event seam now has Immersve JWKS, Bridge PKI, and Stripe HMAC adapters with shared offline conformance tests. Bridge mode pins `https://api.sandbox.bridge.xyz` or `https://api.bridge.xyz`, Base 8453 and Base USDC; `BRIDGE_ENABLED=1`, explicit mode, Bridge webhook public key, Stripe webhook signing secret, pinned `BRIDGE_STRIPE_API_VERSION` (date with optional release name), and checksummed nonzero/nonmax program spender are required. The configured spender remains a placeholder until Bridge assigns Home's specific issuer; no Bridge or Stripe API call, signing credential, or Action calldata is implemented. Stripe test-mode endpoint secrets differ from live-mode secrets and must not be reused. Bridge `kyc_link` events with a null `customer_id` cannot be associated with a customer through this port and are deliberately rejected; customer status/KYC changes with a customer ID are retained as invalidation signals.

**Local Base fork proof (2026-09-25, not CI):** `bun apps/web/scripts/bridge-allowance-fork.ts` forked Base at latest block 51792769 into local Anvil, deployed a Coinbase Smart Wallet v1.1 through factory `0xba5ed110eFDBa3D005bfC882d75358ACBbB85842`, locally seeded 20 USDC into its balance storage, and had the smart wallet execute `approve(30 USDC)` for the published Base Bridge address. An impersonated published contract address then called `USDC.transferFrom` directly: 10 USDC within cap succeeded (balance 10, allowance 20), 21 above remaining allowance reverted, 11 above balance reverted, and after the smart wallet's `approve(0)`, a 1 USDC pull reverted. **This fallback does not execute the Bridge contract's own pull logic or prove a Bridge program:** verified `IssuerFactory.transferToDestination` requires a program issuer ID and authorized debitor not assigned to Home. Home's actual program spender may differ. No transaction was sent outside the local fork; no Action approval code ships here.

**Fallback `card-fund` deposit gate (only if approval-based funding is unavailable; not implemented):** It is unavailable unless mode resolves to **production**, funding type is exactly `base-mainnet-usdc-universal-evm`, and token is the configured `BASE_USDC` on Base 8453. In addition it requires (a) a verified session with a smart account; (b) a Home record binding that owner to a completed Immersve login's `cardholderAccountId`; (c) a live `GET /api/funding-source/{id}` read proving a Funding Source whose depositor `fundingAddress` equals the session smart-account address case-insensitively and whose channel matches the configured ID/type; (d) a live funding-channel read and spending-prerequisites deposit target matching the configured channel, storage address, and mode — fail closed on missing access or mismatch; returned transaction params are compared, never executed; (e) Base `eth_getCode(storage) !== "0x"` at prepare; (f) config rejects both Funds Manager protocol addresses and the public Amoy storage and channel; (g) reuse the hashless-recent and in-flight guards from cash-out; (h) warn that Immersve spendable may be below balance because of limits, AML exclusions and pending withdrawals (formula unknown). Depositing before enrollment could strand funds until cardholder-session withdrawal, so enrollment is a hard prepare prerequisite.

Either funding path's first real transaction is **Base mainnet only**, small amount, after production program approval and Jesse's explicit authorization; neither sandbox validates a Home approval or deposit because Home signs only on Base 8453.

## Delivery slices

1. **Provider foundation (no UI or money action).** `server/cards` validated config and read-only JWKS/supported-regions client, verified public webhook ingress at listener URL `…/api/cards/webhooks/immersve` + `/<topic>`, mode-scoped event dedupe, `009_cards.sql`, synthetic SIWE probe.
2. **Card journey and enrollment.** Subject to Q2 and Q6: a deploy-if-needed step, owner-linked cardholder identity and encrypted token rotation, approval-based funding-source creation, the bounded-approval rule and `card-allowance` Action, Activity projection joining payment events with draws, card lifecycle routes and UI, feature-map/browser coverage. Deploy-if-needed: before Immersve sign-in, read Base `eth_getCode` for the session smart account; if empty, the customer approves a deployment in their wallet (Jesse, September 24, 2026) and enrollment continues once code is observed at the latest block.
3. **Identity.** Immersve-hosted KYC, contact and expected-spend prerequisites, activation; partner Sumsub once confirmed.
4. **Deposit fallback.** Only if Immersve cannot offer approval-based funding to Home's program: `card-fund`, withdrawal intent through Actions, and the card balance as a cash-total component.

Immersve endpoints for the planned journey: `POST /auth/login-init`, `POST /auth/login-complete`, `POST /auth/token`, `GET /api/accounts/{partner}/supported-regions`, `POST /api/funding-sources` (Login Wallet, Wallet Signature, or Simulator variant), `GET /api/accounts/{account}/funding-sources`, `GET /api/funding-source/{id}`, `GET /api/funding-channel/{id}`, `GET /api/funding-sources/{id}/interactions`, `POST /api/spending-prerequisites`, `POST /api/cards`, `GET /api/cards/{id}`, `POST /api/cards/{id}/freeze|unfreeze|cancel-async`, `POST /api/cards/{id}/pan-token`, `GET /api/accounts/{account}/transactions`, `GET /api/transactions/{id}`, `POST /api/funding-sources/{id}/withdraw`, `GET /.well-known/jwks.json`. The sandbox simulator is out of Slice 1. Funding-wallet ERC-1271 support documented by Immersve does **not** establish Wallet Signature Funding Source creation or SIWE login acceptance for a counterfactual smart account.

The `card_events` record holds only verified notification identity, kind, occurrence time and allowlisted cardholder/card/transaction/customer IDs, never the raw body. Migration `011_card_events_provider.sql` retains existing Immersve records (provider defaults to `immersve`), renames `topic` to `kind`, and changes the key to `(provider, mode, event_id)`. Messages from unknown owners are expected in a shared environment. All rows, including unknown owners, become eligible for bounded lazy deletion after 30 days on later deliveries; inactive environments have no background purge or strict deletion deadline. Because a valid Immersve signature does not expire, a verified delivery is accepted only when its signed `createdAt` is a valid ISO timestamp newer than 30 days ago and no more than 5 minutes in the future. That replay window matches the dedupe retention even after old rows are pruned. Do not use these events as transaction or balance state: at request time, read the provider transaction or Funding Source afresh, with stale/unavailable provenance. Bridge's delivery timestamp is capped at 10 minutes and Stripe's at 5 minutes; validly signed stale deliveries receive retryable 400 responses because retries generate fresh timestamps and signatures, while stored event IDs retain the 30-day pruning rule. Bad signatures, malformed headers or bodies, and mismatched Stripe API versions remain deliberate 202 rejections; stale deliveries never enter the store.

## Decisions before Slice 2

**Recommendations pending Jesse's decision; none is implemented by the event seam:**

1. Keep a durable `card_transactions` projection keyed by `(provider, mode, provider_transaction_id)`, written only from fresh provider reads, not webhook payloads. It survives the 30-day `card_events` prune and serves Activity, accounting, and dispute evidence.
2. Obtain each provider's program terms in writing from Bridge and Immersve before production to determine liability for an approved authorization whose wallet pull later fails; Stripe approval alone does not settle this liability.
3. When a program spender changes, require the customer to re-approve via the `card-allowance` Action; never automatically migrate an allowance. Remove a compromised or deregistered spender from server config to block new approvals and prompt customers to revoke existing approvals.
4. Route disputes and chargebacks to support per [#813](https://github.com/jessepollak/home/issues/813) until the provider dispute API is integrated.
5. On a region move or program end, freeze the card and re-enroll the customer with the available provider; eligibility, remaining holds, and transfer of dispute evidence remain open.

## Open questions

Bridge: program availability for Home and US customers; the program-specific Base issuer ID and spender (the published Base address `0x65bf8b55EEDef53C094E40003a03390De744DF33` is a verified `IssuerFactory`, not proof of Home's actual spender); whether a deployed ERC-1271 smart account can hold the approval and link as the card's wallet; which API or webhook confirms an asynchronous pull's completion, and what happens if the pull fails after Stripe approves; sandbox access and Stripe test-mode endpoint secret for a new developer. The local fork proof above does not answer these questions; and the exact webhook signature input. Bridge's prose and its Node, Python, and Java examples verify RSA-SHA256 over the SHA-256 digest of `timestamp.body` (what Home implements), while its Ruby example verifies over `timestamp.body` directly; confirm against the first real delivery.

Immersve:

1. Does SIWE accept deployed ERC-1271 smart accounts and ERC-6492 counterfactual accounts on `base-mainnet` (chain 8453)? Is Wallet Signature Funding Source creation compatible too? CDP embedded currently lacks smart-account `personal_sign` even if Base Account succeeds. Public-sandbox synthetic probe (2026-09-24, viem 2.56.3, Coinbase Smart Account v1.1 with throwaway local EOA owner, counterfactual on Base, ERC-6492-wrapped `signMessage`; `Origin: http://localhost:3000`, `network: base-mainnet`, `autoSignup: true`, no personal data): `supported-regions: HTTP 200 errorCode=none`; `counterfactual-smart-account login-init: HTTP 200 errorCode=none`; `counterfactual-smart-account login-complete: HTTP 403 errorCode=INVALID_SIGNATURE`; `plain-eoa-control login-init: HTTP 200 errorCode=none`; `plain-eoa-control login-complete: HTTP 200 errorCode=none`. This rejects that specific counterfactual signature, **not** every deployed ERC-1271 implementation. Smart-account enrollment remains blocked until Immersve resolves counterfactual and deployed acceptance; EOA success does not authorize use of an EOA in place of Home's verified account.
   Follow-up probe (2026-09-24, public sandbox, `network: base-sepolia`, synthetic throwaway owners, no personal data): a **deployed** Coinbase Smart Wallet v1.1 signing a plain ERC-1271 replay-safe message returned `login-init: HTTP 200`, `login-complete: HTTP 200`; an **undeployed** smart account whose ERC-6492 signature verified locally returned `login-complete: HTTP 403 INVALID_SIGNATURE`; the EOA control returned 200/200. So Immersve SIWE accepts deployed ERC-1271 smart accounts and rejects counterfactual ERC-6492 signatures. **Decision:** enrollment deploys the customer's smart account first when it has no code (Slice 2); Home does not depend on Immersve adding ERC-6492. Base-mainnet behavior is confirmed during enrollment validation.
2. May Home's server call cardholder endpoints with a customer's bearer token, and which registered Home-owned Origin permits server-side token refresh? Until confirmed and registered, no Immersve auth code ships.
3. Can one Home program serve many operators, or does each operator contract directly? Program country eligibility and US timing. Can Home credentials read `GET /api/funding-channel/{id}`? Published shared credentials returned HTTP 403.
4. Partner-conducted KYC with Sumsub: accepted, and with what statement and evidence payload?
5. Fees, numeric limits, spendable-balance rules, refund visibility, PCI-safe detail display options. For the deposit fallback only: deposit crediting/finality on Base, and whether an unexecuted withdrawal intent past `expiresAt` re-credits the Funding Source after its immediate debit.
6. Approval-based funding on Base: which funding type Home's channel uses, which contract the customer approves, whether the draw happens at authorization or at clearing (and how holds, partial clears, reversals and refunds move funds), and whether the approving wallet and Wallet Signature Funding Source creation accept a deployed ERC-1271 smart account.
