# Cards

Status: design of record for [#821](https://github.com/jessepollak/home/issues/821), September 24, 2026. Provider: **Immersve** (self-custodial Mastercard program). Decision: [product strategy](product-strategy.md#implementation-questions-still-open). This page authorizes synthetic public-sandbox probes only; it does not authorize a private sandbox, production program, mainnet deposit, or live card spend.

## Customer model

A verified, eligible customer gets a virtual card that spends USDC they moved from their Home smart account into their **card balance**.

- **One balance is the target.** Jesse decided (September 24, 2026) that the card balance and the cash balance should be one and the same. On Base, Immersve funding is deposit-based: the customer transfers USDC from their smart account to the program's partner Funds Storage contract, which credits their Immersve Funding Source, so wallet USDC drops by the deposit and the card balance rises. Until a single-balance mechanism exists (Q6), Home counts the card balance inside the cash total as a non-sendable component with its own provenance and age, never as a second copy of wallet USDC ([architecture](architecture.md), [product strategy](product-strategy.md)). A stale wallet snapshot plus a fresh Immersve credit can transiently double-count; action confirm/handle invalidation must heat the wallet snapshot. Immersve balance is not necessarily spendable.
- **Moving money back** uses Immersve's withdrawal intent: Home asks Immersve for the intent, the customer signs the returned execution transaction, and the Base receipt decides the outcome.
- **Purchases** are Immersve payment events (`Holding`, `Cleared`, `Reversed`) projected into Activity. They are provider observations, not onchain transfers and not Home Actions.

## Boundaries

| Concern | Owner | Rule |
| --- | --- | --- |
| Deposit calldata | Home server, Slice 2 | Server-authored exact-amount Base USDC `transfer` to the configured Funds Storage address; no approval, no max values; issued through Actions as kind `card-fund`. Never use provider-returned calldata. |
| Funds Storage address, funding channel, card program | Deployment env | `IMMERSVE_ENABLED`, `IMMERSVE_MODE`, `IMMERSVE_API_KEY`, `IMMERSVE_API_SECRET`, `IMMERSVE_PARTNER_ACCOUNT_ID`, `IMMERSVE_CLIENT_APPLICATION_ID`, `IMMERSVE_CARD_PROGRAM_ID`, `IMMERSVE_FUNDING_CHANNEL_ID`, `IMMERSVE_FUNDS_STORAGE_ADDRESS`, `IMMERSVE_FUNDING_TYPE`. Inert unless `IMMERSVE_ENABLED=1` and all fields are set. Unset mode means production; only `sandbox` may be set. Origin and funding type are pinned to mode. The config rejects the documented Funds Manager protocol addresses, the public Amoy storage address and channel ID; none is a Base storage target. Because channel IDs and storage addresses are opaque, config alone cannot prove their relationship. |
| Deposit outcome | Base receipt | Same Actions confirm/handle/receipt loop; Immersve's Funding Source balance is an observation, never proof a deposit settled. |
| Card data (PAN/CVV) | Immersve + customer browser | Home requests a single-use PAN token URL server-side and the browser fetches details directly. Home never receives, logs, or stores PAN/CVV. |
| Cardholder identity at Immersve | Immersve login (SIWE, `cardholder-partner` scope), Slice 2 | Target design: the customer signs Immersve's challenge with the same smart account Home verified. **No login/token storage implementation until** Immersve confirms server-side cardholder delegation and Home's origin is registered on a Home-owned application (Q2). Verify the SIWE message address against the verified session smart account before completion and storage. Store the access token plus expiry and refresh token together in an AES-256-GCM envelope ([secrets at rest](secrets-at-rest.md)), authenticated with purpose, account provider, owner subject, cardholder account ID, and mode. Refresh tokens rotate once; compare-and-swap the prior envelope on replacement; failed rotation means re-login, never retry. |
| KYC | Immersve-conducted first | Redirect to Immersve's hosted KYC; partner-conducted Sumsub sharing waits on Immersve's answer (#640, #857). |
| Events | Immersve webhooks | Register `…/api/cards/webhooks/immersve` as the listener URL; Immersve POSTs to that URL plus `/<topic>`. Reject unknown URL topics and require the signed envelope topic to match the segment. RSA-SHA256 over `{X-Delivery-ID}:{X-Key-ID}:{raw body}` against the configured-mode JWKS, verified before trusting parsing; issuer pinned to the mode's host. Test and Live JWKS published identical signing keys when checked on September 24, 2026, so the signed issuer check is essential. Dedupe on `(mode, messageId)` with insert-on-conflict; out-of-order events only invalidate provider observations and never apply deltas. JWKS fetches are allowed for signature verification; no transaction or Funding Source fetch occurs in the handler. 3DS/OTP material and KYC payload bodies are never persisted. Handled and deliberately rejected deliveries (including disabled/misconfigured ingress, malformed bodies or signatures) receive 202; JWKS failures or unknown signing keys, database failures, and the 14-second processing deadline return retryable 503 so Immersve can redeliver. `(mode, messageId)` dedupe makes retries safe. |
| Provider egress | `server/cards` client | HTTPS to pinned Immersve origin only, bounded timeout, manual redirects, secrets never logged. |

**Future `card-fund` prepare gate (Slice 2, not implemented):** It is unavailable unless mode resolves to **production**, funding type is exactly `base-mainnet-usdc-universal-evm`, and token is the configured `BASE_USDC` on Base 8453. In addition it requires (a) a verified session with a smart account; (b) a Home record binding that owner to a completed Immersve login's `cardholderAccountId`; (c) a live `GET /api/funding-source/{id}` read proving a Funding Source whose depositor `fundingAddress` equals the session smart-account address case-insensitively and whose channel matches the configured ID/type; (d) a live funding-channel read and spending-prerequisites deposit target matching the configured channel, storage address, and mode — fail closed on missing access or mismatch; returned transaction params are compared, never executed; (e) Base `eth_getCode(storage) !== "0x"` at prepare; (f) config rejects both Funds Manager protocol addresses and the public Amoy storage and channel; (g) reuse the hashless-recent and in-flight guards from cash-out; (h) warn that Immersve spendable may be below balance because of limits, AML exclusions and pending withdrawals (formula unknown). The first real `card-fund` is **Base mainnet only**, small amount, after production program approval and Jesse's explicit authorization; neither sandbox validates a Home deposit. Depositing before enrollment could strand funds until cardholder-session withdrawal, so enrollment is a hard prepare prerequisite.

## Delivery slices

1. **Provider foundation (no UI or money action).** `server/cards` validated config and read-only JWKS/supported-regions client, verified public webhook ingress at listener URL `…/api/cards/webhooks/immersve` + `/<topic>`, mode-scoped event dedupe, `009_cards.sql`, synthetic SIWE probe.
2. **Card journey and enrollment.** Subject to Q2: a deploy-if-needed step, owner-linked cardholder identity and encrypted token rotation, funding-source creation, `card-fund` Action with every prepare gate above, card balance inside the cash total and Activity projection, card lifecycle routes and UI, feature-map/browser coverage. Deploy-if-needed: before Immersve sign-in, read Base `eth_getCode` for the session smart account; if empty, the customer approves a deployment in their wallet (Jesse, September 24, 2026) and enrollment continues once code is observed at the latest block.
3. **Identity.** Immersve-hosted KYC, contact and expected-spend prerequisites, activation; partner Sumsub once confirmed.
4. **Withdraw.** Withdrawal intent through Actions.

Immersve endpoints for the planned journey: `POST /auth/login-init`, `POST /auth/login-complete`, `POST /auth/token`, `GET /api/accounts/{partner}/supported-regions`, `POST /api/funding-sources` (Login Wallet, Wallet Signature, or Simulator variant), `GET /api/accounts/{account}/funding-sources`, `GET /api/funding-source/{id}`, `GET /api/funding-channel/{id}`, `GET /api/funding-sources/{id}/interactions`, `POST /api/spending-prerequisites`, `POST /api/cards`, `GET /api/cards/{id}`, `POST /api/cards/{id}/freeze|unfreeze|cancel-async`, `POST /api/cards/{id}/pan-token`, `GET /api/accounts/{account}/transactions`, `GET /api/transactions/{id}`, `POST /api/funding-sources/{id}/withdraw`, `GET /.well-known/jwks.json`. The sandbox simulator is out of Slice 1. Funding-wallet ERC-1271 support documented by Immersve does **not** establish Wallet Signature Funding Source creation or SIWE login acceptance for a counterfactual smart account.

The `card_events` record holds only verified notification identity, topic, and allowlisted cardholder/card/payment IDs, never the raw body. Messages from unknown owners are expected in a shared environment. All rows, including unknown owners, become eligible for bounded lazy deletion after 30 days on later deliveries; inactive environments have no background purge or strict deletion deadline. Because a valid Immersve signature does not expire, a verified delivery is accepted only when its signed `createdAt` is a valid ISO timestamp newer than 30 days ago and no more than 5 minutes in the future. That replay window matches the dedupe retention even after old rows are pruned. Do not use these events as transaction or balance state: at request time, read the provider transaction or Funding Source afresh, with stale/unavailable provenance.

## Open questions for Immersve

1. Does SIWE accept deployed ERC-1271 smart accounts and ERC-6492 counterfactual accounts on `base-mainnet` (chain 8453)? Is Wallet Signature Funding Source creation compatible too? CDP embedded currently lacks smart-account `personal_sign` even if Base Account succeeds. Public-sandbox synthetic probe (2026-09-24, viem 2.56.3, Coinbase Smart Account v1.1 with throwaway local EOA owner, counterfactual on Base, ERC-6492-wrapped `signMessage`; `Origin: http://localhost:3000`, `network: base-mainnet`, `autoSignup: true`, no personal data): `supported-regions: HTTP 200 errorCode=none`; `counterfactual-smart-account login-init: HTTP 200 errorCode=none`; `counterfactual-smart-account login-complete: HTTP 403 errorCode=INVALID_SIGNATURE`; `plain-eoa-control login-init: HTTP 200 errorCode=none`; `plain-eoa-control login-complete: HTTP 200 errorCode=none`. This rejects that specific counterfactual signature, **not** every deployed ERC-1271 implementation. Smart-account enrollment remains blocked until Immersve resolves counterfactual and deployed acceptance; EOA success does not authorize use of an EOA in place of Home's verified account.
   Follow-up probe (2026-09-24, public sandbox, `network: base-sepolia`, synthetic throwaway owners, no personal data): a **deployed** Coinbase Smart Wallet v1.1 signing a plain ERC-1271 replay-safe message returned `login-init: HTTP 200`, `login-complete: HTTP 200`; an **undeployed** smart account whose ERC-6492 signature verified locally returned `login-complete: HTTP 403 INVALID_SIGNATURE`; the EOA control returned 200/200. So Immersve SIWE accepts deployed ERC-1271 smart accounts and rejects counterfactual ERC-6492 signatures. **Decision:** enrollment deploys the customer's smart account first when it has no code (Slice 2); Home does not depend on Immersve adding ERC-6492. Base-mainnet behavior is confirmed during enrollment validation.
2. May Home's server call cardholder endpoints with a customer's bearer token, and which registered Home-owned Origin permits server-side token refresh? Until confirmed and registered, no Immersve auth code ships.
3. Can one Home program serve many operators, or does each operator contract directly? Program country eligibility and US timing. Can Home credentials read `GET /api/funding-channel/{id}`? Published shared credentials returned HTTP 403.
4. Partner-conducted KYC with Sumsub: accepted, and with what statement and evidence payload?
5. Fees, numeric limits, deposit crediting/finality on Base, spendable-balance rules, refund visibility, PCI-safe detail display options. Does an unexecuted withdrawal intent past `expiresAt` re-credit the Funding Source after its immediate debit?
6. Can card authorizations draw directly from the customer's smart account at spend time (allowance or just-in-time funding, or automatic top-up from the wallet) so the customer has one balance? If not, what is the lowest-friction automatic top-up pattern?
