# Component workshop

Follow the [issue's design scope](../../.agents/skills/design-engineering/SKILL.md#follow-the-issue-scope); default to implementation within the current system. The production-component instructions below govern maintenance, journey validation and adoption. An explicitly scoped exploration may use local candidate presentation in a clearly labeled `Explorations/` story group, reusing financial fixtures and behavior where practical. Keep the proposal thin: compose owned `components/ui` variants and existing feature components, and drive candidate states with static fixtures and args rather than duplicate shells or flow logic. Story-only candidates stay in that group rather than joining the `UI/<Component>` owned inventory. It is not a second production UI system. Preserve production isolation, enforced repository rules and required checks; document the boundary and stop at the task's review checkpoint. Do not exhaustively harden every candidate before selection.

Storybook is a credential-free development and review workshop for Home's production components. From the repository root, install and run it without `apps/web/.env.local`, provider keys, a wallet, or a database:

```sh
bun install --frozen-lockfile
bun run --cwd apps/web storybook
```

The server listens on `127.0.0.1:6006`. Build the same workshop statically with:

```sh
bun run --cwd apps/web build-storybook
```

The generated `apps/web/storybook-static/` directory is ignored and must not be committed. A successful static build does not replace `bun check`; both remain required for a Storybook change.

## Review boards

**Default design loop:**

1. Frame the change in its issue; build options and states as stories using production components (isolated story-only candidates for explicit explorations).
2. Add or update a board manifest in `apps/web/stories/review/boards/`, or use **Changes in this PR** if it covers the proposal.
3. Declare the stories to review in the PR's `## Preview` ([Storybook links](../ui-pr-previews.md#storybook-links)); CI keeps the top **Review board** link and each row's frame link on the current Storybook deployment. Jesse can pin Vercel Comments on the preview for context, but only his own GitHub comments and reviews start a factory follow-up run, so feedback the factory should act on goes in a GitHub comment on the PR, with the board frame URL pasted or linked.
4. Record Jesse's selection and reviewed revision on the issue or PR; implement in the same components and verify in Home.

The board is the design surface for proposals, review, and selection, not approval by itself. The [issue scope](../../.agents/skills/design-engineering/SKILL.md#follow-the-issue-scope) and Jesse's approval authority still govern adoption.

A review board is a Storybook story arranging live story canvases; it is not part of the production application. The automatic **Changes in this PR** board shows indexed stories this build changed (changed story files or stories matching changed source files, using the PR number when known), plus any stories a `focus` link declares. Curated manifests in `apps/web/stories/review/boards/` hold story IDs, viewports, sections and review metadata; register their stories in `review-boards.stories.tsx`. Missing stories (and empty sections) are hidden, and a missing before story is omitted without hiding its after frame. Build Storybook to check the current index. Storybook injects `STORYBOOK_REVIEW_REPO`, `STORYBOOK_REVIEW_PR`, `STORYBOOK_REVIEW_CHANGED_FILES`, and `STORYBOOK_REVIEW_ADDED_FILES` alongside revision/deployment/branch; unavailable change data sends the manager's Review board link to Savings and displays an unavailable-data message on Changes.

The story-references gate checks curated board frames, literal `?id=` links, and story inventory IDs against exported stories.

The board URL keeps Storybook `id` and `viewMode` plus `frame` (selected frame), `side` (`after`, `before`, or `both`), `rev` (build revision), and `deployment` (build host). On the Changes board, `focus` (comma-separated story IDs) adds a leading **Review** section with those stories in order, even when the file heuristic did not match them, and the board opens on its first frame unless `frame` names another; the remaining changed stories follow. Without `focus`, stories whose own files changed come before those matched only through `components/ui/**`. Desktop opens on a fitted canvas with separate outline (`[`) and inspector (`]`) toggles. The outline lists frames with size and change pills; selecting a frame there also fits it. Scroll pans, Shift+scroll pans horizontally, ⌘/Ctrl+scroll or pinch zooms at the pointer, and Space+drag or middle-drag pans. Click selects and fits a frame; double-click, Enter, or Interact enters its live iframe; Esc exits interaction. `+`/`-` zoom, `0` resets, `1` fits the board, `2`/`F` fits the selected frame, and arrow keys pan. ⌘K (Ctrl+K elsewhere) opens the command palette, and `?` opens keyboard shortcuts. The header chip links to the PR when PR information is available and shows status when its status request succeeds. Mobile shows one live frame at a time with a grouped journey picker, Previous/Next actions, and a full-width interactive view. The runtime is design-lane code under `apps/web/stories/review/explorations/board/` and is imported only by review stories, never production bundles.

Open the board on the PR's commit-specific Storybook preview deployment, whose URL is unique to one build; the branch preview alias moves with later pushes. Review comments can use the Vercel Comments toolbar on previews or GitHub with a pasted board frame URL. On load the board writes the build's `rev` and `deployment` into its URL, so a comment's page URL records the revision it was made on, and each frame is covered by an element carrying `data-review-frame` and `data-review-story` for comments to anchor to. Opening that URL on a newer build shows a banner linking back to the reviewed deployment. To recover a comment's context, run `bun run --cwd apps/web review:context '<board iframe URL>'` (`--json` for machine output). It prints the board, frame, story, viewport, notes, story source (after `build-storybook`), story and board links on the reviewed deployment, and whether the story or manifest changed between the reviewed revision and `HEAD`. Record dispositions on the GitHub issue or PR.

On a desktop board opened on its own page (the toolbar's **Review board** link), comment pins and threads follow camera movement and are clipped to the canvas instead of covering the board controls and panels. Inside the Storybook manager the toolbar belongs to the outer page, so neither applies.

## Library

The **Library** toolbar link opens `review-library--library`, a desktop workspace for Home's owned `apps/web/components/ui` components. Its sidebar lists one row per `UI/<Component>` story group from the build's `index.json`, never a hand-maintained list; a blue dot marks components this build changed under the Changes board's file matching, and the header counts them only when change data is available and the build changed at least one. An **Overview** row above Foundations is the default view whenever the URL carries no known `component`: a responsive grid with one live, hand-written specimen per component from `explorations/library/overview/specimens.tsx` (not its stories; overlays show only their closed trigger), under the same Theme picker, with a Foundations strip; a card's name opens that component's sheet, and the Library's `OverviewGrid` story play (`stories/review/library.stories.tsx`) fails when a catalog component lacks a specimen or a specimen has no catalog component. Selecting a component renders its **variant sheet**: every story in that group except theme-pinned variants, in index order, as a labelled tile on an open canvas: a responsive grid of cells at least 360 pixels wide, each with the section's heading and a bordered stage whose full-width content box centres inline-sized stories and lets full-width stories fill the stage. Only declared desktop viewports at least 768 pixels wide span the full row; undeclared fullscreen layouts take one grid cell with a stage-fitted frame up to 390 pixels wide and 844 pixels tall, and portal frames also take one grid cell; the canvas is the sheet's scroll container. Sections render in the Library's own document as Storybook portable stories (`composeStory` with the project annotations from `apps/web/.storybook/preview.tsx`), loaded through a lazy `import.meta.glob` over `components/ui/*.stories.tsx`; the neighbouring components' modules are preloaded, and hovering or focusing a component row preloads it and the next row through the same module cache, so switching with a click or ↑/↓ reuses loaded modules instead of booting a preview. Frame selection is deterministic: a section uses its own isolated story frame, labelled with the reason, when the story or its meta declares loaders, `msw` parameters, a `beforeEach` hook or pinned non-theme globals, or when its args open an overlay (`open` or `defaultOpen`). It also conservatively frames stories whose own raw source or reachable `components/ui` modules contain `Portal` or `createPortal`, including strings and comments, rather than using runtime observation or a component list. A Storybook-only Vite plugin strips TypeScript and JSX at build time, then uses `es-module-lexer` to emit decoded import and export-from specifiers through `virtual:library-imports`; development edits, additions and deletions invalidate the module and reload the workspace. Comments, strings and erased type-only imports are not import edges; raw Portal detection remains intentionally conservative. Lexer/transform failures, missing virtual entries, non-literal dynamic imports, import queries and unresolved UI specifiers frame the story with “Couldn't read component source”. Plain `.css` (including `.module.css`), `.json`, `.svg`, `.png`, `.jpg`, `.jpeg`, `.webp`, `.gif` and `.avif` imports are non-code; unknown UI extensions fail closed. Source resolution tries the exact glob key, `.tsx`/`.ts` extension substitution (including `.js`/`.jsx` specifiers), then a one-level `/index.tsx`; unreadable component source frames the story without failing its module load. Detection follows the cycle-safe reachable import and export-from graph inside `components/ui` only. Packages and local modules outside `components/ui`, aliased or renamed portal primitives without recognizable raw portal text, and nested/index modules beyond the source glob's one-level index coverage are not inspected. Module-level detection may frame stories that never open a portal. Authors should use `parameters.library.render: "frame" | "document"` for these cases. Play functions alone do not require a frame: in-document sections render live without running play. Stories whose play establishes their named state, such as an open popover or focused field, declare `parameters.library.render: "frame"`. A per-story `parameters.library.render: "frame" | "document"` is the escape hatch: `"frame"` requests isolation and `"document"` overrides the source-based portal rule, but neither disables the existing lifecycle, non-theme globals, mocks, open-args or unreadable-source isolation rules. Framed sections have no device chrome: an undeclared frame is as wide as its stage, up to 390 pixels. Portal frames are 560 pixels tall; non-portal frames fit their content up to 844 pixels, with fullscreen layouts retaining the full 844-pixel height even when they render portals. Resolved declared viewports at least 768 pixels wide use an isolated frame with their exact width and height, scaled down to the measured full-row stage width; the outer box reserves the scaled height. The muted dimensions caption links to the standalone story in a new tab for full-size viewing. Global viewport selection takes precedence over the parameter default, and both legacy `viewports` and modern `options` declarations are supported, including rotation. Phone-sized or undeclared viewports use the undeclared frame width. Framed sections request one of three loading slots when their reserved-height placeholder enters a one-screen-ahead vertical preload margin around the sheet's scrolling viewport; admitted frames stay mounted and live when scrolled away. Without IntersectionObserver they request admission immediately. Waiting frames that are at least 50% visible, or intersect half the scrolling viewport height for tall frames, take priority at the next free slot; root resizing updates both visibility admission and the preload margin. Each frame has a 20-second load-and-render deadline starting at mount. A matching Storybook render reaching `playing` or a later success phase (`played`, `completing`, `completed`, `afterEach`, `finished`) counts as loaded: the deadline clears, the loading slot releases and the frame becomes usable without waiting for play to finish. Library play functions are best-effort demos, not tests; `test:stories` owns their assertions. A play still running stays live. Frames report iframe load errors, `storyThrewException` and `storyErrored`, `errored` or `aborted` phases before playing, preview-updated errors and the mount deadline. They ignore `playFunctionThrewException`, error-status `storyFinished` events, and `errored` or `aborted` phases reached after playing, regardless of user edits. Generation-fenced monitoring retains render failures until reload; reloading resets load-and-render monitoring. Untouched frames send no theme or args updates. Differing restoration waits until play finishes; user theme and props edits apply immediately, with generation fencing across reloads. The review board keeps its separate phase-finished completion rule. An initially URL-restored focused section scrolls into view once, without smooth scrolling, before the same preload admission rule applies; later selections do not trigger scrolling. One **Theme** picker in the shared top toolbar switches the document-wide appearance of the Library chrome, Foundations pages and all visible component sections; its `theme=light|dark` URL value restores the choice, and navigation between Foundations and components keeps it. Stories with story-level or meta-level `globals.theme` are omitted because the picker covers them; a small line at the end of the sheet reports the hidden count. Links to hidden stories fall back to no focus. There is no text-size picker: Home's type scale is `rem`-based, so scaling it would also scale the Library's own controls. Only activating a section's heading button, by pointer or keyboard, selects it and shows the props bar for that story, generated from its argTypes and args: selects where argTypes carry options, switches for booleans, and inputs for text, numbers, and option-less string props, whose placeholder shows the documented default. Story clicks, hover, keyboard input, drag, typing and overlay interactions never select a section or open the props bar, whether in-document or framed. Loaded frames remain interactive outside annotation mode, and the scroll guard permits trusted child-document pointer and keyboard input. Stories without editable args say so. Unconsumed Escape, including inside a frame, or the heading button again, clears focus and its overrides; with no focus the props bar is hidden. A failed in-document section retries when its composed story, theme or args change, without remounting healthy sections on prop edits. The URL keeps `component`, `story` (the focused section), `props` (JSON of changed args), `theme`, `rev`, and `deployment`, so a pasted link reopens the same state. Changing views between Overview, a component sheet and a Foundations page adds a history entry, so browser Back and Forward restore the view, theme, focused story and props from its URL. Story focus, props and theme edits within the current view replace that entry instead of adding another; an Overview URL omits `component`, `story` and `props`. Each section carries `data-review-frame` and `data-review-story`; **Annotate**, in the shared toolbar, freezes the sheet behind per-section anchors for Vercel Comments, and in `storybook dev` also mounts the Agentation toolbar over the workspace. Enter on a section, or pressing Annotate again, returns to the live sheet. The runtime lives in `apps/web/stories/review/explorations/library/`, reuses the board's live frame, build, and URL modules, and is imported only by review stories.

A **Compositions** row directly under Overview shows real Home screens through their production surfaces and providers, not hand-built UI copies. Each `apps/web/stories/review/compositions/<name>.stories.tsx` file titled `Compositions/<Name>` mounts the corresponding product component with shared fixtures and MSW handlers from the journey stories; requests never reach live services. The covering core has five screens and eight tiles, ordered like the bottom navigation: Home (Home and Home Loading), Card Onboarding (Card Onboarding and Card Active), Invest (hub and Asset Detail), Coverage (full registry), then Operator Shell. The phone compositions all mount the real `DashboardShell` through one story-side `CompositionShell` helper (`stories/journeys/explorations/composition-shell.tsx`) at their production pathname, with one `cardsEnabled` value, one deployment product offering and one asset-search `searchContent`, so header, bottom navigation and search match across tiles as they do in production. Operator Shell mounts the real `OperatorShell` with no section content because the support page reads operator cookies on the server. Each screen keeps its primary state and at most one visibly different state; broader loading, error, empty and success scenarios remain in the component and journey stories. If a surface cannot render without a product change, report the limitation rather than invent UI or change production code. The view discovers these stories from `index.json`, orders compositions by the loaded meta's numeric `parameters.library.order` (unordered compositions follow, with title as the fallback), keeps stories within each file in index order, and renders each as a labelled tile through the sheet's framed live-frame path (`parameters.library.render: "frame"`, so overlays and portals stay inside the tile) at its declared viewport: phone compositions declare 390 × 844 and desktop ones 1440 × 900, scaled to fit, with the dimensions caption linking to the standalone story. Inputs, toggles and overlays stay live. `component=compositions` restores the view and `story=<id>` its focused tile, with the same history and Annotate behaviour as the sheet.

Operator follows Coverage at a 1440 × 900 desktop viewport and mounts the real `app/admin/operator-shell.tsx` navigation shell. Its Storybook navigation mock supplies the current section and a fixture-only refresh; MSW supplies the support unread summary. It does not fabricate operator page content or exercise privileged access.

The Storybook-only imports plugin walks each composition's transitive real import graph across `apps/web`, following `@/` aliases and relative value imports, value re-exports and literal dynamic imports with `es-module-lexer` after TypeScript/JSX transformation. It resolves source extensions and index files, guards cycles, and does not follow packages, erased type-only imports, empty bindings or side-effect-only imports. A missing local source or transform failure fails coverage instead of producing a misleading unused list. The graph reports the reached `components/ui/<name>` set. Product usage is measured independently with the same walker, starting at every Next.js `page`, `layout`, `template`, `loading`, `error`, `global-error`, `not-found`, `default` and `route` entry under `app`; stories, tests and explorations are excluded from that graph. `virtual:composition-coverage` exports the product-graph-computed `notUsedInProduct` list; when nonempty, the Compositions view displays “Unused in product: …” above its tiles, linking each name to its component sheet. Source changes recompute the list in development. The `library-catalog` gate (`scripts/gates/library-catalog.mjs`, run by `bun run gates`; see [gates](../gates.md)) compares it to the reviewed `scripts/gates/library-catalog-not-used.json` list and separately requires every product-used catalog component to be reached by a composition. Product-used components without composition coverage fail with their names and catalog IDs; no silent exemption is permitted. Unknown listed names, missing product-unused names and listed components that become product-used also fail. The current unused catalog components are Button Group, Dialog, Kbd and Progress, matching the production dead-code dispositions. Review the expected list whenever real surfaces change; never force a component into a screen merely to make coverage green.

The product-usage walk runs only when `virtual:composition-coverage` is requested, not in the imports plugin's startup hooks or once per story. The Library requests that module only while Compositions is selected. The plugin shares a cached result across concurrent and repeated requests, clears it on watched source changes, and retries a failed computation on the next request.

In development, lazy-loading a composition's CSF module also requests its static value imports as Vite source URLs. Coverage imports the real `app/coverage/page.tsx`; Operator imports the real `app/admin/operator-shell.tsx`; Invest imports `tests/helpers/pin-clock.ts` and reaches `tests/browser/feature-map/search-fixtures.ts` through its market fixtures. The request guard permits only those exact same-origin source paths with GET or HEAD, not app routes, APIs or other test helpers. Built Storybook serves their bundled assets instead. Invest's stock and Bitcoin logos use the image URLs production's asset-icon resolver returns and load live: the guard also allows HTTPS GET or HEAD image requests to exactly `token-media.defined.fi` and `media.thegrid.id`, and story plays assert each named icon rather than a decoded image, so an unreachable host never fails a test.

The full Compositions interaction fixture retains all five compositions and eight tiles. Its `frameSource="blank"` placeholders settle immediately and release admission slots without waiting for a Storybook preview API; real story frames retain the existing rendering deadline and completion watchers. Frame-runtime unit suites use isolated inline child documents with local iframe network loading disabled, restored after each test.

A **Foundations** group above Components holds six reference sheets that render in the main surface, under the same Theme toolbar instead of a local toggle; Color's Light/Dark columns remain comparative data independent of the selected page appearance. **Color** registers authored colour candidates in `app/globals.css` (read through a Vite `?raw` import and grouped by name prefix) independently of measurement validity, with computed Light and Dark values, hex, and WCAG contrast against `--card` and the `--muted` page. Foregrounds retain their declared base pairing. Measurements are marked Pass, Fail or Unavailable against the [theme](theme.md) thresholds (4.5:1 text, 3:1 graphics and status; surfaces, brand marks and illustration colours are reference only), and unmeasured tokens are counted; **Type**, **Radius & spacing** and **Motion** report utilities Tailwind generates from component source, with the files they appear in. A Storybook-only Vite plugin runs Tailwind's pinned oxide scanner over non-story/non-test `components/**/*.tsx` at build time (and on source changes in dev), emitting one candidate entry per source occurrence through `virtual:library-candidates`; the browser does not tokenize source. Complete candidates are confirmed only against escaped class selectors inside the loaded CSSOM's `@layer utilities`, including nested rules and variant wrappers. Rules outside that layer, including foreign Storybook stylesheets, never confirm candidates. Counts are source occurrences: one token counts once, two separate occurrences count twice, and each file is listed once per utility. A complete utility token in a comparison or other literal counts too. Helper-return literals and `clsx` object keys follow the same rule; dynamic fragments without a generated class rule are excluded. If the virtual module or CSSOM access is unavailable, the sheet reports unavailable rather than zero counts. Motion adds individually measured utility values and motion custom properties from the loaded stylesheets with their resolved document-scope values. It does not reconstruct composed component or variant timings. Easing previews use a shared 350 ms comparison duration and respect reduced motion; measurements are mount-time snapshots, and unresolved values are shown as unavailable. **Elevation** and **States** are #2073 exploration sheets: Elevation lists scanned `shadow-*`, `ring-1` and `ring-foreground/*` utilities with measured values beside four proposed levels (raised, floating, overlay, toast) rendered on owned components with separate Light and Dark values; States groups state-variant utilities in Button, Item, Toggle, Input, Select and Combobox by hover/highlight, pressed, focus-visible, disabled and selected beside one proposed contract applied to owned components. Proposals stay in Storybook until Jesse selects them. `component=foundations/color` (or `type`, `radius-spacing`, `motion`, `elevation`, `states`) links a sheet.

## MCP workshop tools

`apps/web/.storybook/main.ts` registers `@storybook/addon-a11y`, `@storybook/addon-vitest`, and `@storybook/addon-mcp`, and sets `features.componentsManifest: true` — the Storybook 10.6 feature key, kept explicit rather than inferred from the addon's preset — alongside the `features.experimentalComponentsManifest: true` alias that issue #660 names. While the workshop runs, the MCP server answers at `http://127.0.0.1:$STORYBOOK_PORT/mcp` and exposes `docs-list`, `docs-show`, `docs-show-story`, `stories-find-by-component`, `stories-preview`, and `test-run`. The repository-root `.mcp.json` registers that endpoint as `storybook` with the literal `${STORYBOOK_PORT}` placeholder, so export the port in an interactive shell before starting the workshop (`export STORYBOOK_PORT=6006`; the factory sets it per slot) and start Storybook before relying on the tools.

Discover before composing: `docs-list` lists every component the manifest knows, which includes every owned `apps/web/components/ui` module (each has a minimal workshop story beside it) and the pilot and journey surfaces. `docs-show <id>` returns documented props and story usage, and `stories-find-by-component` maps any source file to the story IDs that render it. Do not restate component props from memory or invent a parallel component.

## Journey stories

Page-level flows live under `apps/web/stories/journeys/<flow>.stories.tsx`. A journey composes the real screen from production components, serves each existing external request with `msw-storybook-addon` handlers (`parameters.msw.handlers`), and walks the flow in a `play` function that asserts observable results, not implementation details. The reference journey is `journeys-savings-deposit--deposit`: it loads vault metadata over the production `/api/savings/vaults` fetch, selects a vault, prepares a deposit, and dispatches the exact prepared action.

## Story tests

`@storybook/addon-vitest` runs production component and journey stories in headless Chromium through the workshop's own Vite pipeline; exploration-tagged stories run separately as non-blocking CI review scenarios:

```sh
bun run --cwd apps/web test:stories
bun run --cwd apps/web test:stories:explorations
```

The same story tests are available through the MCP `test-run` tool and the workshop's test widget. Every story file under `**/explorations/**` declares `tags: ["exploration"]` on its default meta; a lint rule enforces this boundary. A failing `play` function fails its run, but exploration failures do not block merge. Exploration `play` functions use a controlled clock, not wall-clock timers, and do not replace component or journey regression tests when a candidate is adopted. The a11y addon audits every selected story. `a11y.test` is `"todo"` (report, do not fail) globally because owned components carry pre-existing violations that need a product decision — the `ItemMedia variant="avatar"` initials contrast (4.34:1) and the money-modal asset-picker controls' missing accessible names. Minimal workshop stories that pass the audit set `a11y: { test: "error" }` so a new violation in those components fails the run. The Storybook manager and the test runner share a Vite dependency cache, so stop a running `storybook dev` before a full story-test run.

Keep `*.stories.tsx` beside the production surface under `apps/web/components/**` or `apps/web/client/**`. A story imports the component Home uses rather than a separately styled copy, and composes the real card, list, shell, and provider constraints needed by that surface. Prefer the component's natural typed props and injected action functions; use provider fixtures or MSW only at an existing external-request boundary. The current MSW worker starts only through Storybook's global loader. Its file lives under `.storybook/static`, never `public`, and production modules may not import Storybook, stories, or MSW. Keep story-only fixtures inside a `*.stories.*` or `.storybook/**` path so the production-isolation gate can enforce that boundary.

Fixtures use fixed balances, clock values, and presentation regions. Each story resets the shared query client and owns cleanup for mutable or deferred state. Unexpected requests fail visibly; only known Storybook/Vite assets are bypassed. Never let a story fall through to a Home, provider, database, wallet, or other live service. Use the 390 CSS-pixel viewport as the representative mobile review composition; narrower widths such as 320px are safety checks for viewport containment, not the product's definition of mobile.

Every story meta has an explicit stable `id`; keep its meaningful export name stable once it is referenced. For story ID `<id>`, use these deployment-relative direct links:

- manager: `/?path=/story/<id>`
- canvas: `/iframe.html?id=<id>&viewMode=story`

The pilot and exploration inventories live in [story inventories](stories/). Add a file there for each new story group.

The adopted Borrow overview uses `borrowing-borrow-overview--multiple-loans`, `borrowing-borrow-overview--management-sheet-open`, and `journeys-borrow-overview--repay-review-cancel-back` (full inventory in [Borrow overview and management](../borrow-overview-design.md)).

Every owned `apps/web/components/ui` module also has a minimal workshop story (`UI/<Component>`) so the MCP manifest exposes the owned inventory rather than only the pilot surfaces, plus the journey inventory `journeys-savings-deposit--deposit`. The unwired, unapproved Card proposal lives in the `Explorations/Card` group (`explorations-card--*`, [#636](https://github.com/jessepollak/home/issues/636)) until selection. The unwired, unapproved USDC ↔ cbBTC trade proposal lives in `Explorations/Invest Trade` (`explorations-invest-trade--*`, [#935](https://github.com/jessepollak/home/issues/935)); [#616](https://github.com/jessepollak/home/issues/616) owns its production adoption. The built `index.json` and the MCP `docs-list` output are the durable discoverability sources when this inventory grows. An intentional ID or export rename must update direct links and review evidence in the same change.

Storybook can prove that a production component renders and supports fixture-backed component interactions under deterministic states and review viewports. Stories and play functions are review scenarios, not permanent browser tests or approval by themselves. Storybook cannot prove Home's Next routing/history, app-level scrolling or focus restoration, browser Back integration, wallet/provider behavior, physical keyboard behavior, or Safari behavior. Verify the integrated component in Home under the [browser-validation contract](../browser-validation.md), and record media and limitations under [UI PR previews](../ui-pr-previews.md).
