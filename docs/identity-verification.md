# Identity verification

Home verifies customers with one configured Sumsub level. Consent precedes applicant creation. Embedded Web SDK is primary; a short-lived hosted link is recovery. A GREEN decision counts as card-gating approval only when the reported level equals the configured level, the applicant is active, the row belongs to the running provider environment, and the customer has no unreleased identity restriction. An approval with an unknown level remains pending. The customer contract is `getIdentityApproval(customerId, "configured-level")`, returning `{ approved, level, approvedAt }`; changes in computed approval emit `identity.approval_changed` operator events with string-only properties. Linked sign-in credentials resolve to the same customer.
Each verification row stores the last approval it announced, and events are emitted against that value, so a configured-level change revokes an approval at the old level on the row's next readback (reconcile or status read) even when the provider reports nothing new.

## Persistence and configuration

Apply `011_operator_registry.sql` and `015_identity_verifications.sql` with `DATABASE_URL`; no database means identity is configuration unavailable, including local development. `identity_verifications` stores a customer-scoped active applicant per provider environment, consent version/level/locale, allowlisted review state and retry reason, attempt/review markers and approval/reconciliation timestamps, including the most recent failed reconcile attempt and the recorded level-move timestamp and attempt. Superseded rows preserve historical attempts. Append-only `identity_verification_events` hold Home facts, short allowlisted raw status/answer/type values, and review markers, not provider payloads. `customer_restrictions` retains final rejection after applicant removal or supersession. An authorized operator releases one restriction by its ID with `releaseRestriction(id, releasedBy, at, configuredLevel)`; the immutable release fields are the audit record. A final decision creates a restriction on transition into final, or when a newer final review (a higher attempt count, a later review time, or a different review ID) arrives while the row is already final; a replay of the same review cannot reinstate a released restriction. Approval changes and verification events reflect active restrictions, and release emits approval restored when the active row is approved at the configured level and no other restriction remains. Final rejection prevents another session; a duplicate-person decision instead directs the customer to sign in with the verified account and creates no restriction. Deactivation is reversible, blocks sessions and hosted links, and never counts as approval; activation restores the same row. Only a deleted-applicant webhook confirmed by a not-found readback marks removal and permits a fresh attempt with renewed consent. Verification rows cannot be deleted or truncated; restrictions cannot be deleted or truncated, nor can customers with identity rows be deleted.

Set server-only `SUMSUB_APP_TOKEN`, `SUMSUB_SECRET_KEY`, `SUMSUB_WEBHOOK_SECRET`, `SUMSUB_LEVEL_NAME`, and `HOME_SUPPORT_URL`. Only `sbx:` and `prd:` token prefixes are accepted. A sandbox token is refused on production Vercel. Sandbox rows and restrictions never approve or restrict production. A valid HTTPS or mailto support URL remains available on configuration errors. Optional `SUMSUB_WEBHOOK_SECRET_PREVIOUS` allows either digest during rotation; optional `SUMSUB_SECRET_KEY_PREVIOUS` retries an outbound 401 once with the previous signature. Present-but-invalid rotation keys fail configuration closed. Never expose these credentials to client code.

## Routes and operations

Authenticated `GET /api/identity/verification`, `POST /api/identity/verification/session`, and `POST /api/identity/verification/link` use the customer's canonical ID. Sessions take `{ consent?: true, locale?: string }`; consent is asked again on version or configured-level changes and after confirmed removal. Session and link creation share a Postgres-backed limit per customer of 10 requests per 10 minutes, including across server instances. All decisions come from provider readback, not browser SDK callbacks. Reviews are monotonic by attempt and review-created date, including when an attempt number is missing. Applicant adoption records the level returned by Sumsub before customer submission. A readback from an unknown or different stored level to the configured level always records a move boundary, even if Home restarts after the provider move. A completed review on that first readback belongs to the old level and cannot newly approve or restrict; if the provider has already reset the review, that pending review and later decisions count at the new level. The same boundary applies when Home has not yet recorded any level and the first readback it sees is already completed: only a later review counts. Level-change callbacks bind to their reported target level; a readback still at the configured level records a boundary even on a round trip, so carried decisions fail closed. A status read reconciles stale rows inline (24 hours only for an active approval at the configured level; five minutes for every other state, including an approval with a missing or different level and final rows after restriction release; scheduled batches use the same split), returning the stored status if Sumsub is unavailable. A reconcile that finds no provider change advances only the reconcile timestamp, with no version change or verification event. A not-found reconcile readback leaves the row unchanged, records an attempt timestamp and logs only its row ID; failed reads also record an attempt timestamp and back off for the same interval; scheduled reconciliation rotates failed rows behind untouched rows so a bad batch cannot starve the queue. Scheduled batches skip removed rows (including those with an active restriction), include unadopted active rows, dispatch at most five concurrent readbacks, and stop dispatching new rows 20 seconds after the batch starts; untouched rows remain eligible for the next run. After a hosted link opens, Account polls status every 10 seconds for 15 minutes; returning to the Home tab restarts that window while the 30-minute link could still have produced a submission awaiting its decision.
The renewed-consent request applies only where the customer can start or continue a session; a verified, pending, under-review, or final customer is not asked again, because no new provider processing follows. The one exception to a reconcile without a provider change is an announced approval that no longer matches the computed approval (for example, after a configured-level change): that reconcile writes a verification event and emits the approval change.

`POST /api/identity/webhooks/sumsub` accepts authenticated HMAC-SHA256 or SHA512 raw-byte digests. Configure applicant created, pending, on-hold, reviewed, level-changed, reset, deleted, deactivated, and activated webhook events. Released final rows also re-enter scheduled reconciliation. The endpoint verifies applicant ownership, ignores superseded or old-attempt events, and rejects a level-changed event without a valid target level. `POST /api/identity/reconcile` is a deployment-access exemption, authenticated by `Authorization: Bearer <IDENTITY_RECONCILE_SECRET>` with a 32+ printable-character secret. It reconciles at most 50 stale rows in the running environment and returns counts only. The operator must schedule it with an external scheduler; do not add `apps/web/vercel.json`.

Home does not store or log names, DOB, addresses, images, biometrics, comments, provider payloads, SDK tokens, links, applicant IDs or external IDs in observability logs. Webhook logs contain only the verification row ID. Synthetic tests are not a live Sumsub acceptance test; an operator-authorized sandbox trial remains necessary before rollout.

## Provider contract

Home signs each Sumsub request with `X-App-Token`, `X-App-Access-Ts` (Unix seconds) and `X-App-Access-Sig` (lowercase hex HMAC-SHA256 of timestamp, uppercase method, path with query, and the exact raw body) against `https://api.sumsub.com`, Sumsub's default processing region. The SDK access token (`POST /resources/accessTokens/sdk`) and the hosted link (`POST /resources/sdkIntegrations/levels/-/websdkLink`) both send the verification's random external ID as `userId`; Home never sends a customer ID. Home saves that ID before creating the applicant, so an unconfirmed create is adopted by looking the applicant up by external ID. Webhooks authenticate with `x-payload-digest` over the unmodified body; `x-payload-digest-alg` selects `HMAC_SHA256_HEX` (default) or `HMAC_SHA512_HEX`, and SHA-1 is rejected. Sumsub reports a deactivated applicant with `deleted: true` and sends `applicantDeactivated` / `applicantActivated`; a hard deletion reads back as not found.

A RED decision maps to duplicate-person only when every label is `DUPLICATE`; mixed labels follow the final or retry reject type. Other retry labels map to one allowlisted reason in priority order: photo quality (`UNSATISFACTORY_PHOTOS`, `SCREENSHOTS`, `BLACK_AND_WHITE`, `DOCUMENT_DAMAGED`); incomplete document (`DOCUMENT_PAGE_MISSING`, `INCOMPLETE_DOCUMENT`, `FRONT_SIDE_MISSING`, `BACK_SIDE_MISSING`, `SAME_SIDES`, `UNFILLED_ID`, `DOCUMENT_MISSING`); expired document (`EXPIRATION_DATE`); unsupported document (`ID_INVALID`, `WRONG_DOCUMENT_TYPE`); selfie (`BAD_SELFIE`, `BAD_VIDEO_SELFIE`); proof of address (`BAD_PROOF_OF_ADDRESS`, `WRONG_ADDRESS`); proof of identity (`BAD_PROOF_OF_IDENTITY`). Unknown, risk, fraud, sanctions and final-rejection labels never reach clients, storage or logs.

The browser passes the SDK language. Sumsub lists `pt` and `pt-br` but not Maltese (`mt`) or European Portuguese; Home uses English for Maltese and `pt` for Portugal.
