# Balances: one snapshot, every row, cached on the device

Status: **G1 CDP-first server, G2 deletion, G3 server observation, G3b production completeness, G3c latency/price observations, and G4 dust default shipped** (2026-09-13); **history data foundation shipped without a route or UI** (#1163, §10). Subsystem design under [architecture.md](architecture.md) (principles 2 and 5; the balances snapshot is an *observation*) and the current home for the locked inventory direction. Home enumerates the wallet through CDP, resolves against registry ∪ Codex 512 ∪ wallet metadata, reads the registry at one pinned block, prices resolved rows, and stores the last observation in Neon. Home's own actions and CDP webhooks invalidate that snapshot; the 120-second refresh is a backstop. Add another enumerator only after measured CDP limits justify it. Jesse accepted historical balances as the shipped requirement for a Home-owned change log (#1041, September 27, 2026). Provider webhooks mark it dirty, and it is ingested on requests only: by the operator check in this slice, and on history reads once slice 2's route ships. It adds no indexer process, cron, or queue. Do not add any other self-hosted indexer without a shipped requirement. Provider failure stays `unavailable`, a successful zero stays `0`, and no cache authorizes an action.

## What Jesse asked for

1. Balances are cached on the client so they feel instant: reload, tab switch, return-from-background paint from the device, then revalidate.
2. All 512 recognized tokens are first-class everywhere balances appear (Home teaser, Cash/Savings, Investments), not "nested-Balances-only".
3. Rows look good and identical regardless of which source produced the holding.
4. One backend read with one shape; every feature selects from it.

## Pending cash-out

Cash remains the pinned wallet-only USDC balance. Home adds the still-escrowed, unfilled portion of an unsettled Peer cash-out to the net total as a separate Pending cash-out breakdown item; Cash shows that same priced amount below its wallet-only hero balance. The amount uses the snapshot's Base USDC unit price in its quote currency (USD or GBP), including when wallet USDC is zero. A missing unit price leaves the line out and makes the total partial.

The action's attributable successful deposit receipt supplies its observed block number, and only once that receipt's outcome is finalized: while the receipt is still unfinalized, the observation is deliberately retained, so projecting the block early would let a reorged-out deposit count escrow beside wallet USDC restored on the replacement fork. Before finality the estimate is indeterminate instead. Home includes escrow only after the balances snapshot is pinned at or beyond that block; an earlier snapshot still includes wallet USDC and must not count escrow again.

Pending cash-out shares the memory-only `[owner, "actions"]` query and parser with Activity, action toasts, and money results. Each query read records a client-side monotonic sequence at its start. When the hook first observes an owner/fetch-time/block snapshot key, it records the current sequence; only a completed read with a later sequence can establish escrow or its absence. Any observer's qualifying read counts. Joining a read that started before the snapshot does not count: once it completes, the hook requests a post-snapshot read without cancelling another observer's fetch. A confirming refetch that joins an older read can retry once. Until a qualifying read completes, even cached positive escrow stays loading rather than contributing to the new snapshot. A failed confirming read makes the estimate unreadable; a later qualifying shared read recovers it. The verified shell always mounts action toasts when Portfolio Home enables the pending hook, using the identical server-verification condition and owner key. Action toasts owns the visible-tab 15-second cash-out poll; the pending hook adds no interval. Home pull refresh still refreshes the shared actions scope.

A capped actions read cannot establish the escrow set, and a same-owner cash-out or cash-out-withdrawal row the parser rejects (a missing required field, a malformed amount entry, an unrecognized kind carrying cash-out progress, or a withdrawal whose deposit link is blank) is reported as incomplete rather than silently absent, so either makes the estimate unreadable rather than a definite amount. The amount is counted only when the same actions response wrote a confirmed progress row for the order (a provider order read or a verified withdrawal receipt); a record served from storage without a successful write in that request (provider failure, timeout, or an order outside the per-request refresh budget) is unconfirmed and makes the estimate indeterminate rather than adding a possibly obsolete amount. An in-progress cash-out whose escrow amount cannot be established (including absent progress, deposit link or receipt, or a linked return in progress) is indeterminate: Home leaves the wallet-only total partial and Cash shows Pending cash-out without a number. A known positive escrow remains visible and included in the total even if another in-progress order is indeterminate; the total is then partial. An unusable actions read is unreadable: Home is partial and Cash has no pending line. While a restored snapshot is painted before the owner session is verified, or no post-snapshot actions read has completed, the estimate is a distinct loading disposition: Home marks the wallet-only total partial and Cash shows no pending line until the owner-scoped read establishes whether an order exists, so an understated total is never presented as complete. Ended orders omit escrow. A return performed outside Home can remain counted until provider progress refresh observes it.

Absent progress is not proof of a terminal order: a cash-out row whose progress projection is missing entirely stays indeterminate even when its own receipt-derived status reads terminal, because that status alone cannot establish the provider order's end state. Only a projected terminal state removes the line.

## Boundary: display snapshot vs action-time reads

`GET /api/balances` is the **display and client-availability** source: what rows to paint, what a user *can* start (Send max, Save deposit and withdrawal max). It is not action authority. Registry vault shares carry optional `withdrawableBalance`, bounded by their underlying position value and the owner's onchain `maxWithdraw` at the snapshot block. Withdraw uses that limit for Max and its available label; older snapshots or unreadable limits fall back to the position value with a saved label instead. Where calldata depends on chain state, the action's server `prepare` reads it at a pinned block and validates the amount (`server/borrowing/prepare.ts` via the market-parameterized `BorrowRpcReader.readSnapshot`, exposed for detail display at `/api/borrow/markets/:marketId`; `server/savings/prepare.ts` via `savings/rpc.ts`); a plain Send is checked by the chain at execution. Those reads stay exactly as they are. This is two responsibilities, not two sources of truth.

## Design

### 1. One enumeration + one registry

The server has two bounded inputs with different freshness and authority:

1. **Enumerate per owner.** CDP Token Balances scans up to 32 pages at the documented maximum of 100 rows per page (3,200 rows). It returns lowercase ERC-20 contract addresses, decimal-integer-string amounts, and optional trimmed `name`, `symbol`, and `decimals`. The native `0xeeee…` sentinel is excluded because ETH is read from the registry path. One in-flight scan is shared per owner and detached from route caller aborts. It starts pages inside a 2.5 s soft budget, lets a healthy in-flight page finish, and enforces a 4 s hard ceiling per page including retries. Stopping after one or more pages preserves those rows, marks the scan incomplete, and stores the next page cursor so a stale signal or 120 s backstop resumes instead of restarting. A bounded scan that began at page one also preserves stored holdings from pages it did not reach; only a complete scan replaces stored non-registry holdings.
2. **Read the registry.** `server/balances/universe.ts` contains only configured direct assets and vault shares from `config/portfolio-assets.ts`. Registry ordering stays cash → native → other direct assets → vaults. It never expands to the Codex catalog and never performs a 512-contract `decimals()` verification.

CDP supplies display-grade quantities only for positive non-registry rows. Registry quantities, including ETH and vault shares, always come from the pinned Base read. This deliberately gives action-relevant assets a coherent block while allowing Home to show tokens discovered by the wallet index.

### 2. One chain read

`server/balances/read.ts` reads the registry and vault conversions in one pinned pass through the configured Base RPC:

1. `eth_getBlockByNumber("latest")` selects `{number, hash, timestamp}`. `eth_chainId` remains asserted once per resolved URL.
2. In parallel at that block: `eth_getBalance(owner)` and one Multicall3 `aggregate3(allowFailure: true)` containing every configured ERC-20 and vault-share `balanceOf(owner)` call.
3. One batch converts positive vault shares with `convertToAssets(shares)`, reads `maxWithdraw(owner)` for those same vaults at that block, and re-reads the pinned block. `withdrawableBalance` is the smaller of the converted assets and withdrawal limit; a failed conversion, share balance or limit makes it unavailable, and zero shares yield a ready zero without either vault call. A changed hash re-pins and retries the whole read once; a second mismatch fails.
4. A failed registry call is retried once. A successful zero is `"0"`; a failed read is `unavailable`, never zero. The whole read retains its 4 s deadline.

The hosted public-default guard is unchanged: preview/production never uses an implicit public RPC for registry quantities, marks those rows unavailable, and emits one `portfolio-balance-source` event per read. There is no catalog chunk and no sequential-public-catalog branch. The snapshot row's hot window drives post-action registry refreshes; instances keep only in-flight dedupe.

### Resolve

After enumeration and the pinned registry read finish concurrently, `server/balances/resolve.ts` joins `registry ∪ Codex 512 catalog ∪ wallet`:

- Registry contracts found in CDP are ignored; their quantity remains the pinned registry quantity.
- A positive enumerated contract in the cached Codex 512 catalog becomes a `catalog` holding. Catalog `name`, `symbol`, `decimals`, image, and liquidity win; the CDP amount supplies the display quantity. If CDP supplies decimals and they disagree with Codex, the row is skipped and coverage becomes incomplete.
- A positive contract outside registry and catalog is looked up on Codex by contract address in batches of 100 (global 60 s, 2,048-address LRU). Codex name, symbol, image, and liquidity win; a CDP/Codex decimals disagreement skips the row and makes coverage incomplete. Unknown or failed lookups remain quantity-only `wallet` rows with valid CDP metadata.
- Registry non-cash ERC-20s receive `imageUrl` from the one-hour configured-asset icon resolver; icon failure is ignored. Cash, ETH, and vault shares never receive an image.
- Zero rows are skipped and contracts are deduped by lowercase address.

The Codex catalog reader remains the three-page, 512-entry, 60 s shared cache. It resolves membership and presentation metadata; it is not part of the chain quantity read.

### 3. One pricing pass

`server/balances/price.ts` prices positive holdings as follows:

- The full non-stock registry ERC-20/vault-underlying input set remains one stable Codex batch on every pricing pass.
- Registry stock holdings use the Chainlink tokenized-equity feed read on Base through `BASE_RPC_URL`, never Codex. Feed reads are a pure function of (feed, block) for historical reuse. Open and closed sessions use the feed price (closed = last close); paused, stale, unavailable, and removed listings stay unpriced. A feed answer already includes the oracle registry multiplier: valuation is token balance × feed price × FX, never a second multiplier. Zero balances retain the existing zero valuation. The session calendar is vendored through 2028-12-31; a date beyond it is never counted as open, so the state falls to the frozen "Last close" rather than a live price, and staleness then relies on the wall-clock bound (heartbeat + 1 hour + 7 days); `invest-catalog:refresh` reports the remaining calendar coverage and fails the drift check once it is expired or within 120 days of expiring.
- The stock reference read never blocks a cached response. A bootstrap pass awaits one read for all listed stock feeds and keeps each stock's last good reference in memory; a `cached` pass serves those references and schedules the next read (`STOCK_REFERENCE_REFRESH_MS`, 30 s) through the shared scheduler, so a cold instance reports the stock unpriced and revalidating instead of waiting on Base RPC. A region with no quote currency, a removed listing, a zero balance, or no stock holding issues no stock read at all. References age per stock: a rejected refresh, or a stock that comes back unavailable or missing while others succeed, keeps that stock's previous reference only while it is within `STOCK_REFERENCE_MAX_AGE_MS` (5 min) of its own last good read; past that the stock is unpriced and `revalidating` marks the degraded value. A routine refresh of a still-usable reference does not mark the snapshot stale.
- Positive `catalog` rows are priced in batches of 25 and retain the ≥ $25k exact-contract liquidity market gate for the total; 24 h volume is not an admission dependency (#470).
- Bootstrap token pricing uses `BALANCES_PRICE_BUDGET_MS`, derived from the 4 s `BALANCES_READ_DEADLINE_MS`, with at most four concurrent 25-token batches. Completed batches keep their quotes; skipped or unfinished batches become `price-unavailable` without writing valuation attempts or observations. Budget expiry schedules only the unfinished inputs for request-independent background refresh and marks the snapshot stale. Caller abort stops waiting and starting batches, schedules no additional refresh, and prevents a subsequent FX read from starting; FX already in progress and stock-reference reads retain their own timeouts. Shared Codex requests track waiters: one caller abort leaves other waiters alive, and only the last waiter abort cancels the provider fetch.
- Background token refreshes checkpoint each completed 25-token batch's fresh observations and all completed valuation attempts before that worker starts its next batch, retaining four-worker concurrency and input result order. Checkpoints serialize only when their asset keys overlap so successful-write fences cannot race; disjoint batches and bootstrap writes progress independently, and failed writes do not advance those fences. Caller abort releases a bootstrap waiting behind conflicting persistence and skips its writes if they have not started, without cancelling shared background writes. A cancelled mixed-key bootstrap immediately frees unrelated keys, including their already-queued waiters; each key retains its own active predecessor barrier so conflicting descendants cannot overlap writes or fences. Tokens do not wait for later batches or FX to persist. An interrupted route leaves checkpointed keys durable for the next instance, which refreshes only keys still due under the existing positive and negative retry windows; unfinished and budget-expired late results never receive negative attempts. FX outcomes still persist once after their read. This is request-driven progress, not a queue or a guarantee that every refresh finishes within the route lifetime.
- A Codex price is usable for display valuation when its `asOf` is within `BALANCES_PRICE_MAX_AGE_MS` (24 h); older → `price-stale`. Fresh quotes are stored once per asset in `price_observations`, and a cold instance or failed Codex batch may reuse the newest stored quote inside that bound. Trade/borrow authorization keep the 5-minute market-prices rule (decision 7).
- Codex-enriched `wallet` rows share the catalog 25-token price batches and market gate; unknown quantity-only rows return `value: { status: "unpriced", reason: "below-market-gate" }` and never enter the total.
- ETH and FX continue to use Coinbase exchange rates. Cash rows still get `cashValue` in their own denomination.
- `total.status` is `complete` only when registry and inventory coverage are complete and every known positive registry, catalog, or wallet holding is priced. Any missing inventory coverage or positive unpriced holding makes a nonzero known total `partial`; when no positive priced contribution exists the total is `unavailable`, not a misleading zero. Every priced holding contributes exactly once.

All amount and valuation math remains bigint / exact-decimal based; no amount crosses through JavaScript `Number`.

### 4. One snapshot (contract v4) and coverage

`GET /api/balances?region=XX` returns the response shape owned by the `zod/mini` schemas in `shared/balances/contract.ts`; `shared/balances/types.ts` re-exports the schema-derived response types. Registry, catalog, and wallet rows all use `holdings[]`; the parser continues to require positive non-registry ERC-20 rows with canonical lowercase source-specific ids and keys. Wire addresses may be lowercase or valid EIP-55 checksums, and hashes may use either case; the parser returns them lowercase. v4 adds `borrow` and `totals` (#794); `holdings[]` and the gross `total` are unchanged.

- **`borrow.positions[]`** has one entry per configured Borrow market where the owner has collateral or debt. `collateral` is a `Holding` with `source: "borrow"`, `collateral: { marketId }`, and the market's collateral asset key. It is priced by the balances pricer with the same quote and FX that price that asset in the wallet. `debt` is a signed Borrow line (`sign: -1`, market id, loan asset, raw accrued debt, and region-currency `value` converted with the same loan-asset quote and FX). `borrowAprWad` is the market's variable borrow APR (per-second rate × seconds per year), the value the Borrow surface already labels APR.
- **`borrow.coverage`** is `complete` only when every configured market was read. A failed, timed-out, or never-observed market read is `partial`. So is a stored nonzero position in a market that is no longer configured, so its debt is never silently dropped from a complete net. It is never a zero position. Each market is read at the registry read's block (number and hash), so a collateral supply or withdraw is counted in exactly one of the wallet and Morpho. If the pinned block cannot be read or is no longer canonical, that market is `unavailable`; the reader never falls back to `latest`. The Morpho reader verifies `eth_chainId` once per reader instance, so a pinned read fits the 4 s deadline.
- **`totals`** has `cash` (cash-currency holdings plus savings vaults), `investments` (every other holding plus Borrow collateral), `borrow` (a positive magnitude of all debt), and `net = cash + investments − borrow`, with `net.negative` carrying the sign. Each component follows the gross-total rules: `complete` only when every contribution is known and priced, `partial` when a known nonzero sum is missing something, and `unavailable` otherwise. Partial Borrow coverage makes Investments and Borrow incomplete, so `net` can never be `complete` without a full Borrow read, and a gross total is never reported as a complete net. Regions without a quote currency report every total as `no-quote-currency`. Home renders `totals` since #789 (`presentHomeBalances` in `shared/balances/present.ts`): the net total, the signed allocation bar and legend, and the Cash, Investments, and Borrow Cash rows, with Borrow's rate as `N% APR` from each owing market's `borrowAprWad` weighted by its debt `value` (or by debt normalized to token decimals when any debt is unpriced). A partial net renders dimmed but raises no header status: a large wallet's long-tail inventory or unpriced holdings keep coverage partial indefinitely, so partial coverage alone is not an interruption (#700, #826). Home's own header status (`homeBalancesStatus` in `client/home/home-status.tsx`) appears only when the balances read fails (`Balances are unavailable`, with a Retry icon button) and clears after a successful read; with no quote currency (`needsCountry`) the popover shows the `Choose a country in Account…` prompt and opens Account instead. The offline and interruption statuses below take precedence over it. An unavailable net renders `—`; a failed summary row shows a muted `—` without a chevron, and a known but partial row (for example Borrow with partial coverage) renders its value muted. The gross `total` stays in the contract but has no Home consumer.
  In exit-only mode, Home omits a product row only when its summary is known empty, and a Borrow discovery row additionally needs an enabled offered market, so a Borrow product left on with every market reducing-only hides both the empty-account row and its rate read. Borrow's no-debt summary also reports whether any position retains positive collateral; a collateral-only holder keeps a `Collateral` / `Manage in Borrow` row to `/borrow` with no advertised borrow rate, so they can withdraw their collateral. Unknown Borrow balances keep their exit route.
- **Boundary parse.** `server/balances/handler.ts` parses the assembled snapshot with the `shared/balances/contract.ts` parser against the verified session (owner address and chain) and the single requested region before serializing it, so a snapshot for another owner, chain, or region is never served as a 200; a snapshot the parser rejects returns the same `BALANCES_UNAVAILABLE` 502 as a failed read and emits a `balances-contract` event with code `BALANCES_CONTRACT` and reason `invalid-snapshot`, without attributing the failure to an inventory source (#1559).

When verified dashboard balance reads fail because of a network error or server 5xx, Home confirms after 5 foreground seconds before showing the interruption status across tabs; a confirmed interruption rechecks every 30 foreground seconds up to ten times, then offers manual Retry. Offline status appears after 2 continuous foreground seconds and changes to the interruption status on reconnect; a successful read clears either status after 3 foreground seconds. Cached values remain display-only.

Coverage now means:

| field | status | meaning |
|---|---|---|
| `coverage.registry` | `complete` | Every configured registry quantity was read successfully. |
| `coverage.registry` | `partial` | At least one registry quantity is unavailable. |
| `coverage.catalog` | `complete` | A page-one CDP scan completed, the Codex catalog cache is complete, and no enumerated positive non-registry row was skipped for unusable metadata or a CDP/Codex decimals disagreement. Enumerated registry contracts and duplicate rows are intentionally ignored and do not reduce coverage. |
| `coverage.catalog` | `incomplete` | The scan hit its page or soft page-start bound, Codex returned a partial catalog, or a positive non-registry row was skipped for unusable metadata or a CDP/Codex decimals disagreement. Completing a stored-cursor resume preserves an earlier `incomplete` result until a later complete page-one scan verifies the whole inventory. |
| `coverage.catalog` | `unavailable` | CDP enumeration was unavailable; only registry inventory is known. This incomplete inventory cannot produce a `complete` total; it yields `partial` when a positive priced contribution is known and `unavailable` otherwise. |

CDP unavailability never turns `/api/balances` into a 502. A registry read failure retains the existing fail-closed registry row semantics and can still cause the route-level read failure behavior when the pinned pass itself cannot complete.

Server composition is: `enumerate(owner)` concurrently with `read(registry, owner)` followed by `readBorrow(owner, registryBlock)` (one Morpho position read per configured Borrow market at the registry block, bounded at 4 s) → `resolve` → `price` → `snapshot`. Caller abort signals do not cancel shared owner observation work; they apply to the request's bootstrap token pricing.

### 5. One client query, persisted whole

`client/balances/use-balances.ts`:

- Key `ownerQueryKey(owner, "balances", region)`, `meta: ownerQueryMeta(owner, "owner")` — **persisted including every catalog and wallet row**. The full validated owner query envelope now lives in IndexedDB (`home-query-cache` / `owner-clients`, one active-owner slot), using `idb-keyval`. The lossless `home-gzip-v1:` codec remains bounded to 8 MiB of encoded characters and 32 MiB of decoded bytes; small and legacy JSON remain readable. The buster stays `home-query-v4`; it drops raw responses cached before the typed-factory migration replaced them with parsed rows for actions, activity orders, funding providers, provider customers and funding orders. Parsed actions and activity orders stay memory-only; balances and the other validated scopes, including the funding reads, persist for the seven-day owner-session retention period. Storage rejection remains best effort and cannot turn a partial portfolio into a complete one.
- Home separately retains at most 8 KiB of the existing formatted total, allocation and three money-row presentation in localStorage. This display-only projection is scoped by owner and region, carries the query observation timestamp and seven-day retention, and paints in a layout effect. It never populates the balances query, holdings, send availability, vault positions or action authority. Invalidated summaries are removed from disk; the mounted view retains its previous complete projection while pending cash-out reconciliation settles, then swaps to the confirmed presentation. Cached age is available to assistive technology and `data-home-cached-summary`; no visible updated-time label is added.
- The same bounded summary record optionally includes Cash APY and Borrow offer APR labels, each with its own five-minute restore lifetime and unchanged observation timestamp. Rate writes merge each label against the stored observation timestamp. This best-effort display cache does not lock simultaneous cross-tab writes; failed refreshes never renew a retained rate’s observation age. Pending dependencies retain known labels; only settled holdings can select a portfolio APY or an empty-portfolio teaser. Settled unavailable results clear the corresponding label. These labels never populate savings positions, borrow snapshots or action authority. A known Home display reserves Activity space without a shimmer while verified sources restore; first-visit loading still has placeholders. Device-country restoration completes before paint, retaining account-preference and owner holds. Home money-row values update without rolling digits.
- A separate `home.display-summary.v1` cookie mirrors only the bounded display summary and recent rate labels for `/home` document requests (encoded maximum 3,500 characters, seven-day retention, Secure on HTTPS, SameSite=Lax). The shell reads it only beside a valid signed render-session seed and only for the same owner and resolved country; duplicate, invalid, future, expired or mismatched values are misses. This untrusted display projection renders through the same components in the initial HTML and never populates a query or enables Send, transport or confirmation. Sign-out clears the cookie even from another route; balance invalidation removes it; a matching owner-preservation boundary retains it. Local summary restore may replace an older server projection before paint. Large summaries keep the local cache but omit the request cookie. Rate expiry remains five minutes. The pre-hydration browser regression blocks React bundles while allowing streaming HTML to settle, checks the money values/subtitles and disabled Send, then removes the live signed-session hint and proves the same cookie cannot render money by itself.
- Full IndexedDB restore begins after two animation frames, allowing the small summary to paint first. Restoration still passes the same scope, owner, region and timestamp guards and cannot replace newer query data. Legacy localStorage envelopes migrate after a successful IndexedDB commit and are deleted only if unchanged. If IndexedDB cannot open, the previous localStorage persister remains the best-effort fallback.
- Atomic IndexedDB updates compare the captured owner epoch, owner and timestamp. Owner clearing queues a new epoch and synchronously cancels local pending work; a revoked lease cannot resurrect data after sign-out or A→B→A. Matching seed-owner preservation keeps its lease and summary. A local memory clear fences pending restoration and cancels writes without deleting durable data. Persistence is throttled before snapshot construction; blocking diagnostics measure serialization, excluding gzip and IndexedDB waits.
- Region defaults to `usePresentationRegionId()`; the Cash panel uses the same `PresentationRegionProvider` as Invest (`feature-panels.tsx`), so Cash/Savings and Home share one key. USDC base units are region-independent anyway.
- `staleTime` 15 s, `refetchOnWindowFocus: true`, `placeholderData: keepPreviousData` for the same owner, `retry: false`.
- Full small JSON restores asynchronously after the summary paint. Large gzip restores asynchronously, then passes the same scope/owner/region contract guards and timestamp-aware TanStack hydration. A boundary revision and effect-lifetime check discard late restores after owner changes or memory clears; persister revisions discard late compression after cancellation, removal or a newer queued write. No cached snapshot authorizes execution, and late cache hydration cannot replace newer query data.
- Reload: the shell layout (or the landing page) derives an optional provisional owner seed only from an HMAC-valid Home session or complete CDP render-hint pair. SSR and the initial hydration still render the loading shell; summary restore runs before paint while full owner restore is deferred (neither runs during render), but it can now select that signed owner's snapshot before SDK/native session restoration finishes → cash, registry, and catalog rows paint without a network wait. Provisional status never enables the balance query, transport, actions, validation, or CDP activation, so the first network balance read still requires server verification. The seed is one-shot: a matching provider-native owner retains the cache, while mismatch, signed-out settlement, sign-in/out, or verification loss clears it and unchanged layout props cannot restore it. `balances:painted` fires on `ready` only; `balances:summary-painted` records the separate summary paint; the Home hero keeps refreshed financial values still. Measure `presentBalances` on a 512-row fixture against the `balances:painted` budget.
- After an action: `invalidateAfterAction` invalidates every registered `afterActionScopes` entry — card-spending, balances, activity, borrow, borrow-market, actions, trade availability, activity orders and transfer recent recipients (`client/query/after-action.ts`). `borrow` owns the overview and `borrow-market` owns each market detail; both participate in indexed convergence. `startBalanceFreshness` reads `holdings[].balance.baseUnits` by `id` or CAIP `key` from the snapshot; the multi-region merge from #373 stays. The post-action `fetchQuery` retains owner persistence while forcing a fresh read.
- Transport gains `fetchBalances` additively; `fetchPortfolioValuation` / `fetchSavingsPositions` are removed in the deletion step.

```ts
type BalanceRowModel = {

  group: "cash" | "asset";
  name: string;                 // "US dollar" | "Aerodrome"
  mark: { kind: "flag"; currency } | { kind: "image"; url; fallbackSymbol } | { kind: "eth" } | { kind: "symbol"; symbol };

```

Anatomy, identical for every source: `[40 px mark] name / secondary … primary`. Cash: `[flag] US dollar … $1,234.56` (from `cashValue`). Priced asset: `[image] Aerodrome / 12.5 AERO … $18.20`. Unpriced asset: `[image] Foo … 12.5 FOO` (muted). Unpriced cash keeps its available native quantity in the default tone. Unreadable cash or asset: `Unavailable` in destructive tone, never `$0.00`. Unsupported local currency, where Home has no verified cash asset and reads no balance: `[flag] Mexican peso … Verification pending` or `[flag] Canadian dollar … Additional verification` (muted), never a zero amount, and excluded from subtotals and totals. The label is the region candidate's configured `verificationStatus` ([currency defaults](currency-defaults.md)), so a candidate with an unresolved material fact never reads as further along than its configuration. Loading: skeleton rows from a real `loading` state, not the `"Updating…"` sentinel.

Membership rules: cash rows (canonical USD + selected local) always render, including at zero and when `unavailable`; other cash and non-cash rows render with a positive balance or, since #1396, with an `unavailable` balance when Home can name the holding (non-empty name or symbol) — the row shows `Unavailable`; a known zero stays hidden, and tokens seen in the wallet but never read have no holding and no row (they surface only through coverage and the total status label); vault shares are never rows (they count in `total` and appear in Savings detail via `selectVaultPositions`). Grouping and ordering: **Cash** (selected local, canonical USD, other cash — authored order, never re-sorted by value), **Investments** (positive non-vault priced holdings by value desc, then unpriced and unreadable registry/catalog holdings by name; priced dust last when shown), then **Unpriced** (positive unpriced wallet-source holdings by name, omitted when empty). Cash and Investments show a quote-currency subtotal of their priced holdings (omitted, never 0, when nothing is priced); Unpriced has no subtotal. This grouped-list model remains available through `presentBalances` for tests and stories; production pages use focused presenters. The Cash page renders only its cash rows, while the Investments page renders the flat owned-holdings list from `selectOwnedInvestments` (unpriced holdings and priced dust included) with activatable rows that open a holding; `/balances`, `/balances/cash`, and `/balances/investments` redirect there. Since #789 the Home "Your money" card instead shows three summary rows from `totals` — Cash, Investments (`Across N assets`, counting visible readable non-dust holdings and Borrow collateral once per asset key), and Borrow Cash — and the hero shows the signed Borrow · Cash · Investments breakdown. Formatting stays in `shared/formatting`. Dust behavior is described in §9.

The Home Borrow Cash row is a discovery row when offered, but an exit-only Borrow holder with collateral and no debt sees `Collateral` / `Manage in Borrow` instead. It stays linked to `/borrow` while a fully empty, known Borrow summary hides the row; partial or unavailable balances do not hide exits.

Home’s funded Investments row opens the owned holdings list at `/investments`, with `/investments/native` and `/investments/<0x-address>` as direct holding paths. The list holds non-cash assets with a read, positive balance, named assets whose balance can't be read (shown as `Unavailable`, also in their detail), plus confirmed collateral. An unread balance is not counted as ownership for Home's summary: emptiness comes from readable owned rows, not Home's small-balance display count, so a sub-cent holding still opens `/investments`; an empty, complete Investments summary opens Invest discovery at `/invest`.

No 24 h change, no contract addresses, no source labels on rows (ui-direction). An Investments holding row opens that holding; cash rows are not tappable.

### 8. Server observation: `balance_snapshots` (G3, shipped 2026-09-13)

Jesse accepted one server-side balance cache as an *observation* (architecture.md principle 2): derivable, stamped with its source position, droppable, never authority for an action. It replaces the per-instance TTL caches as the server's cache; per-instance in-flight dedupe stays.

```sql
create table balance_snapshots (
  chain_id     integer not null,
  address      text not null,            -- lowercase smart account; what the chain and the webhook know
  block_number    bigint not null,
  block_hash      text not null,
  block_timestamp bigint not null,    -- unix seconds from the pinned block
  observed_at     timestamptz not null,     -- when the last full observation pinned its block
  stale_at     timestamptz,              -- one-shot: activity seen (webhook, funding receipt)
  hot_until    timestamptz,              -- post-action window: registry re-read on every request
  enumeration_cursor text,               -- next CDP page when a bounded scan is incomplete
  holdings     jsonb not null,           -- pre-pricing holdings with provenance (registry pinned, catalog/wallet from CDP)
  coverage     jsonb not null,
  borrow       jsonb,                    -- per-market Morpho collateral, accrued debt, and APR; null for rows observed before #794
  primary key (chain_id, address)
);
```

Rules:

- **Scope.** The row is keyed by address because that is what the chain and the webhook know; the verified session decides which address a request may read (unchanged verified-scope rule). Two providers on one address share one observation.
- **Writers touch only their columns.** An observation write is a conditional upsert ordered by `block_number`, then `observed_at` for the same block (a newer observation never loses to an older response), and writes the observation columns only. Signal writers (`/confirm`, `/handle`, the webhook, a funding receipt) touch only `stale_at` or `hot_until`. A signal before the first observation intentionally no-ops: the first read is fresh by definition, and placeholder rows are forbidden.
- **When a read re-observes.** An existing stale, expired, or degraded row is served immediately while a per-owner deduped full observation runs through the route's `after()` scheduler. A fresh row with an enumeration cursor is also served immediately while enumeration resumes, without being marked stale. `hot_until > now()` remains synchronous registry-only because a person is waiting for a post-action balance to move; when hot and stale overlap, that registry refresh is returned and a full observation is also scheduled. A missing row still requires a synchronous full observation. `hot_until` is set by `POST /api/actions/:id/confirm` and `/handle` to `now() + 60 s`; `stale_at` by the CDP webhook and by a funding order reaching `received`; the backstop is 120 s.
- **Serving as observed.** `observed_at` is the last full observation's pin time; registry-only refreshes update registry rows and coverage without moving it. `fetchedAt` on the wire is `observed_at`, never the response time. `stale: true` means a required re-observe is pending or failed and is not included in this response. Cash/Savings currently keeps a retained snapshot visible without an explicit age label; consumers must not treat the stale marker as fresh or substitute zero.
- **Stale maxima.** Send and savings deposit/withdraw use snapshot amounts even when stale; the server's pinned read at `prepare` remains the authority (§Boundary). Cash/Savings currently has no explicit age label for a retained snapshot.
- **Prices never per owner.** Stored token and FX observations are read concurrently and applied at response time. Existing balance rows never await Codex or Coinbase: a missing or expired valuation is returned honestly as unpriced and refreshed through the route's retained `after()` work. Only creation of a previously absent balance row may bootstrap providers synchronously. `price_observations` remains last-good global exact data; Coinbase uses `fx:USD:<currency>` and `fx:USD:ETH` keys, while USD is arithmetic identity and needs no provider or store row. `valuation_attempts` records every provider outcome without erasing last-good values. Unavailable attempts retry after 60 seconds; missing, invalid, and stale attempts retry after 15 minutes. Safe values remain displayable for 24 hours and routine refreshes are silent. The route is `private, no-store`.
- **Borrow rides the observation.** Full and hot registry-only observations both re-read Borrow positions at the registry block, so `/confirm` and `/handle` hot windows and activity webhooks refresh collateral and debt with the wallet. A row with a missing or partially unavailable Borrow read is degraded, but only once `BALANCES_BORROW_RETRY_MS` (30 s) has passed since its `observedAt`: then it is served stale and re-observed in the background, like partial registry coverage. Inside that interval the row is served without `stale` and schedules no background full, so a Morpho or RPC outage cannot drive a full observation (including CDP) on every client poll; `borrow.coverage` stays `partial` and the totals stay non-complete throughout. A hot registry-only read decides this from its fresh Borrow read, not the stored row.
- **A transient Borrow failure keeps the last verified market read.** When a configured market's fresh pinned read is unavailable but the stored row holds a `ready` read of that market no more than `BORROW_CARRY_FORWARD_BLOCKS` (60 blocks, about two minutes on Base) older than the new registry block, the observation keeps that prior read (with its original `blockNumber`) instead of replacing it (#1069). Home then keeps showing the known Borrow position right after another money action instead of `—` with Retry. A carried read counts toward `borrow.coverage` but is not current, so it is degraded under the retry interval above exactly like an unavailable Borrow read: inside the interval the snapshot is not marked `stale` for the carry alone, so freshly read registry balances stay usable (for example, as Trade inputs); past it the row is served `stale` and re-observed until a pinned read at the current block succeeds. Client polling follows the [architecture](architecture.md#client) contract unchanged. Beyond the bound, or with no prior verified read, the market is `unavailable` exactly as described above. Only markets the fresh read covers are carried, so a market removed from configuration is dropped rather than carried; the bound is by block distance only and does not re-check the carried block's hash.
- **Dropping the row never affects correctness**; it costs one re-observe and any open hot window.

Enumeration cost moves from "every 60 s per active user" to "once per activity event", which is what makes the all-tokens phase affordable for dusty wallets.

Webhook subscription lifecycle is automatic in production. At the first authenticated balance read for an address, and at the first confirm of an action for it (so the action can settle while nobody is present; [actions.md](actions.md#follow-through)), Home lists subscriptions (60 s per-instance cache, one shared instance per server), selects an enabled `wallet_activity` subscription on `base-mainnet` whose target origin matches this deployment and has fewer than 100 addresses, re-lists immediately before a full-subscription `PUT`, and confirms the address by reading CDP back. If none has room, Home creates one targeting `/api/webhooks/cdp` and persists the returned one-time signing secret only as an authenticated envelope in `webhook_subscriptions` before returning ([secrets at rest](secrets-at-rest.md)). Production derives its origin from `VERCEL_PROJECT_PRODUCTION_URL`; `HOME_WEBHOOK_ORIGIN` is an optional override. Registration is disabled without PostgreSQL because an ephemeral instance cannot retain the secret. `POST /api/webhooks/cdp` opens stored secrets into a 60 s per-instance verifier cache, verifies legacy `v0` or current `v1` HMAC-SHA256 signatures within the five-minute replay window, accepts the documented wallet activity family, sets `stale_at` on every extracted address, schedules follow-through for the matched wallet addresses in the delivery, and returns 200. Registration failures are non-fatal: confirm and balance reads never wait on them, and the 120 s backstop remains.

Unverified until preview: the production `wallet.activity.multi` delivery envelope and exact documented address fields; whether production deliveries use `wallet.activity`, `wallet.activity.detected`, or `wallet.activity.multi`; list pagination beyond the first response; and address packing/update behavior at the 100-address boundary. The implementation tolerates snake_case list fixtures and emits a bounded failure event without addresses.

### 10. History data foundation (#1163)

Slice 1 of [#1041](https://github.com/jessepollak/home/issues/1041) stores what is needed to reconstruct past Cash, Investments, Borrow, and net values. It has no route, contract, or chart yet; those arrive in slice 2. Every history table is an **observation**: it is rebuildable from CDP SQL, Base archive reads, and price and FX providers, may be dropped, and never authorizes an action or supplies a displayed current quantity. The current-balance read (§2–§8) does not call history.

- **Enrollment.** A history row exists only for a `customer_wallets` row and is deleted with it (`ON DELETE CASCADE`). A first read without a wallet row enrolls nothing and reports building history. The window starts at the 00:00Z day at or before one year before the finalized head at enrollment, including time before sign-up. Its time is the future "History starts {date}" label.
- **Change log.** `balance_changes` stores one signed quantity change per `(address, asset, block, log index)`, hash-partitioned by address into 32 partitions. Changes come from CDP SQL `base.transfers`, grouped by the full transfer identity (block, log index, token, sender, recipient, value) with the re-org-aware net action above zero. Two surviving transfers at one position with different content fail the window closed. Each query covers one ≤31-day window for one wallet, padded by one hour on each side for time pruning. Rows outside the window's block range are then dropped, because a block predicate defeats the provider's time pruning. A window that returns 50,000 rows (the provider page cap), hits the provider scan cap, or times out is halved, down to one day. A single 365-day query and wallet-scoped `base.events` windows older than about 60 days both exceeded the provider's 93 GiB scan cap on September 27, 2026. `base.transfers` has no transaction hash, so `tx_hash` is null for these rows. Inserts are `ON CONFLICT DO NOTHING`.
- **Cursors.** Backfill runs backward from the enrollment block to the window start in 31-day chunks, and forward ingest runs from the enrollment block to a watermark that stays a fixed lag (about 30 minutes of blocks) behind the finalized head. Enrollment pins its block at that watermark. Ingest commits only behind the lag watermark and re-reads a bounded replay window of about 30 minutes of blocks across each cursor boundary: the committed forward range and the newest backfill chunk. A transfer that the provider indexes into that window lands on the next run; replay inserts never move a cursor. New replay rows atomically clear only their assets' later reconciliation log comparisons, retaining pinned chain quantities. A cleared comparison is pending and fails closed to archive reads from the window start until the next run recomputes it under the address lock. A history read takes the address row's shared lock before reading checkpoints and cumulative changes, so it cannot mix pre-replay comparisons with post-replay changes. If the provider indexes both legs of an offsetting pair after that window, the endpoints still net to the same quantity, so no mismatch appears and the interval between them stays unverified: the provider is assumed to index finalized transfers completely. Backfill and forward cursor commits cover disjoint ranges, though replay queries overlap committed ranges. Each chunk commits under a transaction-scoped `FOR UPDATE` row lock with a compare-and-set on its cursor; no session advisory lock is used because Neon's pooled endpoint cannot hold one. Only blocks behind that watermark are ingested, so rows never need re-org repair. A run is bounded by its deadline, and every provider call inside it is aborted at that deadline without moving a cursor. A log-derived quantity at a bucket after the forward cursor is pending, never complete. `ready` means caught up to the watermark of that run, with a computed comparison or pinned position sample for every anchored asset not on the static archive-read list and no unresolved pending reconcile comparison. A mismatch is still a computed comparison: it demotes that asset to archive reads instead of matching. The CDP webhook sets `dirty_at` on enrolled rows only, and a dirty mark that arrives during ingest survives it. In this slice only the operator check below runs ingest. Slice 2's owner-scoped history route will run it in `after()` on each read, with the address taken from the verified session, never from the request.
- **Checkpoints.** Each asset gets a pinned chain read at the window-start block: native ETH, every contract seen in the window, configured registry assets and vaults, and both sides of every configured Borrow market. A contract with no code at that block is zero only after `eth_getCode` returns `0x`; a revert or RPC failure stays unknown. Reconciliation checkpoints record the chain quantity next to the log quantity at the first complete import, then per asset at least every 30 days: one asset's recent checkpoint never defers another's, and an asset whose read failed keeps its own due date. A reconcile checkpoint with a null log quantity retains its pinned chain quantity but has no verified comparison; the next run repairs pending comparisons before log tracking can resume.
- **Asset identity.** `history_assets` is keyed by chain and asset key. An ingest refreshes its kind, contract, decimals and cash denomination from configuration and from the snapshot holding that vouches for them, and it never downgrades a stored `vault-share` to a plain token, so a vault removed from `portfolioVaults` keeps its vault basis and stays unpriced (`unpriced-basis`, partial) rather than being valued by its share-token close. Verified decimals and a cash denomination are stored once and never overwritten. A contract whose historical kind cannot be established, for example one first enrolled after its vault was removed, is treated as an ordinary token by the admission rule, which is the same floor the current-balance path has. Existing changes and checkpoints keep their identity.
- **Tracking per (address, asset)** is derived from checkpoints, not stored:
  - WETH (which changes balance without `Transfer`) and B20 stock tokens (whose #624 multiplier is not a transfer) always use `archive-read`. Promotion never overrides this list.
  - Configured registry ERC-20s use `transfer-log` and configured vault shares use `shares-rate` only after a comparison has been computed at the window start or later; before any comparison is computed they stay on `archive-read` from the window start, so an unverified log never supplies a complete point. A computed mismatch demotes the asset to `archive-read` from its last matching checkpoint instead of promoting it.
  - Every other ERC-20 starts on `archive-read`. It moves to `transfer-log` only after two matching checkpoints with at least one balance-changing transfer (non-zero delta) between them.
  - Native ETH uses `archive-read` at buckets for the whole window once the stored snapshot or any checkpoint shows a positive balance. While every checkpoint and the snapshot show zero, ETH is trusted as zero (the approved fallback). So ETH credited and spent entirely between two zero checkpoints while the snapshot shows zero is not seen, and CDP balance history for ETH would close that gap.
  - Borrow collateral and borrow shares use `position-index`: Morpho Blue `position()` read at bucket blocks, with debt from the shared accrued index.
  - A mismatching checkpoint, or a running log balance below zero, moves the asset to `archive-read` from its last matching checkpoint. A pending reconcile comparison instead requires `archive-read` from the window start and cannot promote or supply a trusted log segment. Points requiring archive reads stay pending until read; they are never shown from the log as complete.
- **Buckets.** `chain_buckets` maps each hourly bucket to the last block at or before it, only up to the finalized head. The block is estimated from Base's 2-second cadence and verified against both neighbouring headers. Daily points use the 00:00Z row.
- **Shared series.** `valuation_points` holds series shared by every account, filled on read and keyed by series, basis version (`history-basis-v1`), granularity, and bucket:
  - vault `convertToAssets(10^36)` at the bucket block;
  - each Borrow market's borrow assets per share, accrued to the bucket block through the IRM;
  - the latest completed 15-minute Codex close at or before the bucket, for each exact contract (ETH and WETH use WETH closes);
  - Coinbase daily FX for the UTC day before the bucket, used only to convert into the display currency.

  Only settled values are stored, and a settled miss is stored as null so it is not refetched. Hourly rows older than 8 days are deleted in batches. `price_observations` keeps its spot meaning and is unchanged.
- **Valuation.** `shared/balances/history-valuation.ts` turns log quantities and series into Home holdings and Borrow positions, then runs `computeBalancesTotals`, so history uses the header's accounting and coverage. Admission applies today's admitted set to every point under `history-classification-v1`: registry assets, vaults, and Codex catalog members are admitted, and any other positive token is `below-market-gate`. The held set comes from the stored `balance_snapshots` row: its positive holdings are anchored even without a transfer in the window. A point can be complete only when that row exists and its registry and catalog coverage are complete. A tracked position in a market no longer in the configuration, or shares of a vault no longer in `portfolioVaults`, is never valued on another basis: it is reported `unsupported` or `unpriced-basis` and keeps the point partial, or unavailable when it leaves no defensible value. B20 stocks stay partial (`unpriced-basis`) until #624 supplies their feed valuation. A missing close, including a stablecoin close, marks its component partial and is never valued at 1.00. Unknown quantities are never zero. The reconciliation tolerance against an archive reference, or against the header on the history basis, is 0.5% of ETH-weighted value.
- **Operator check.** `bun run --cwd apps/web history:reconcile -- --address <address>` enrolls an existing wallet row in the configured database and ingests it to ready. It then compares history quantities and valuations with independent archive reads at recent daily and hourly buckets at or behind the committed forward cursor, reports the omitted tail count, and prints a sanitized summary.

Known limits: a wallet with more than 50,000 transfers in one day cannot finish backfill and stays building. A token whose historical `balanceOf` reverts stays unknown, so its points stay partial or unavailable. Deriving current quantities from the log and the held-set current-balance multicall are separate follow-ups.

## Constants

### Provenance and valuation

`observedAt` is the timestamp of the registry read's pinned block, not the time the observation was stored. A holding value's `asOf` is the price source time; display valuation accepts the documented maximum age while trade and borrow enforce their own stricter limits. Snapshot totals include every priced registry, catalog, and wallet holding exactly once and are `complete` only with complete registry and inventory coverage; missing coverage leaves a nonzero known sum `partial`, never a silently smaller complete total.

### Runtime bounds

| Constant | Value | Why |
|---|---|---|
| Client `staleTime` | 15 s | refetch on focus/mount past this; bounded 3 s retries for stale snapshots, and 30 s rechecks only during a confirmed interruption |
| Device cache TTL | 24 h | persisted owner snapshot; cleared on owner change |
| Read dedupe (per instance) | in-flight only | concurrent regions/tabs share one owner observation; no completed-value TTL |
| CDP enumeration dedupe | in-flight only | completed enumeration lives only in `balance_snapshots` |
| Read deadline | 4 s | shorter than the 6 s per-call RPC timeout; a timeout fails the read and the client keeps previous data |
| Enumeration budgets | 2.5 s soft page-start; 4 s hard in-flight page | returns collected rows with `incomplete`; stale signals and the 120 s backstop continue from the stored page token |
| Price batch concurrency | 4 | bounds concurrent Codex batches while avoiding sequential latency |
| Hot window | 60 s | set by `/confirm` and `/handle`; registry re-read on every request |
| Backstop | 120 s | full re-observe when no signal arrived |
| Price maximum age | 24 h | newest per-asset observation inside this bound may value balances |
| Price observation refresh | 60 s | older safe stored observations are served and refreshed silently in the background |
| Negative valuation retry | unavailable 60 s; missing/invalid/stale 15 min | suppresses repeated provider misses without deleting last-good values |
| Codex prices / Coinbase FX | 45 s / 60 s | global, shared across users |
| Market gate | ≥ $25k exact-contract liquidity, fresh price; no volume requirement | priced catalog/wallet rows enter the total (#337; #470 removed the ≥ $10k 24 h volume gate and set liquidity to $25k) |

## Decisions taken (Jesse can veto on the issue)

1. **CDP-first:** CDP Token Balances enumerates and supplies display-grade quantities for non-registry rows; one pinned registry+vault multicall backs actions and the total; Codex prices — Jesse, Go, 2026-09-13.

6. **Icons ride on the holding, not on Invest.** Production showed registry Invest rows (cbBTC, DEGEN, stocks) as pending discs because the balance rows borrowed `assetMarkResolution` from the Invest discover query (public, unpersisted, gated on Codex trending). The server attaches `imageUrl` to registry ERC-20 holdings from the asset icon resolver (1 h cache; configured memes added to its set); catalog and wallet rows keep their Codex image; the presenter uses `holding.imageUrl` for every source and the balance presenters no longer depend on Invest — Jesse, 2026-09-13.

Enriched wallet rows are priced and gated exactly like catalog rows; contracts Codex does not know stay quantity-only with CDP metadata — Jesse, 2026-09-13.
