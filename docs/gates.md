# Repository gates

`bun run gates` first checks that this worktree has a ready dependency tree (printing `bun run worktree:bootstrap` when it is missing, incomplete or stale), then runs the repository gate unit tests, and `bun check` runs that plus the rest of the checks. The check compares installed versions against `bun.lock`—each declared dependency with an attributable lockfile key must match its workspace-selected resolution, so a nested copy at another version of the same name is not ready; names recorded only at unattributable keys may match any recorded version. An installed lockfile-recorded package whose `package.json` is unreadable or has no string `version` is not ready either. Root-declared dependencies must resolve from the root `node_modules`; only `apps/web` declarations may resolve from the hoisted root tree. It cannot see damage inside a file of a version-correct package; a clean reinstall repairs that. All of it runs without provider or funded-wallet secrets. These checks guard twenty invariants across `bun run gates` and `bun check`:

- Migrations run before build, so a build cannot ship a schema it never applied.
- Every table a migration in `server/db/migrations/` or `server/funding/migrations/` creates has a row in the [data model](architecture.md#data-model) with a `record` or `observation` kind and a reason; partitions are covered by their parent, and any exemption carries a reason and fails once stale. The gate reads `CREATE TABLE` in migration SQL and in the quoted bodies PostgreSQL executes (`DO`, including a `LANGUAGE` option, function bodies, and a literal `EXECUTE` argument); unqualified tables created inside `CREATE SCHEMA` take that schema; quoted text stored as data is not SQL; dynamic SQL inside a body, changes to `search_path`/schema or `standard_conforming_strings`, and Unicode-escape or newline-concatenated literals fail the gate.
- No unresolved CSS custom properties, so every referenced token resolves in the theme.
- `globals.css` has only the imports, `@source` directives, variants, custom-property names, selectors, and rule declarations in `scripts/gates/globals-css-allowlist.json`. This exact structural allowlist includes the shell-owned deferrals (#1075/#1137) and is the allowlist consumed by #1140's styling guards; adding or retiring global surface requires updating it. It pins token names, not token values: retuning a colour or radius needs no allowlist change.
- Every custom property declared in the `@theme inline`, `:root`, `.dark`, `@supports`, and `@media` sections of `globals.css` has a `var(--name)` or parenthesized shorthand reference or, for Tailwind theme mappings, a statically recognizable utility or variant use. Consuming spellings are measured from the installed Tailwind build: candidate namespaces come from its default theme plus every namespace introduced by the repository's declared `@theme inline` tokens, and variant templates cover named-container modifiers and negated variants. A contract test pins the default-theme-only namespace set and proves each modeled namespace keeps a token live. Declarations named exactly like bare default-value keys (`--spacing`, `--radius`) and tokens consumed only through utility modifiers such as `text-lg/7` still need a `var()` reference. This includes references in design explorations and stories; tests and Oxlint tooling are not consumers. The unused-token guard has no committed exceptions after removal of the unused `--radius-3xl` mapping.
- New product CSS modules are prohibited outside explorations and stories. The five retained modules and their specific reasons are pinned in `scripts/gates/module-css-allowlist.json`; deleted modules make their entries stale.
- Source CSS in `app/`, `client/`, and `components/` (including explorations and story files in those layers) has no root-anchored `:has()`; product CSS outside explorations and story files has no `!important` outside an exact-match allowlist. The top-level `stories/` workshop tree is outside this source guard.
- Built CSS has no root-anchored `:has()` and no descendant/non-child `:has()` except classes emitted from the reviewed form-control source files. Direct-child forms are allowed. This invariant runs in `bun check` after build, not in `bun run gates`, scans production output under `.next` (skipping the development-server `dev/` and `cache/` directories), and fails if the build emits no CSS.
- API routes stay dynamic. The build half runs in `bun check` after `bun run build` via `bun run api-routes:dynamic`. It reads `apps/web/.next/prerender-manifest.json` and fails when any `/api` or `/api/` route is prerendered, because a prerendered GET handler serves one shared static response. The build manifest is the authority for whether a route was actually prerendered. The same command scans every reachable `apps/web/app/api/**/route.ts` (a handler inside a private `_`-prefixed folder is not a route and is skipped) and fails when a file that exports a `GET` or `HEAD` handler has no request-time read (a request argument, `headers()`, `cookies()`, `connection()`, `draftMode()`, `noStore()`, or `unstable_noStore()`), is not bound to a handler factory call or named handler (`export const GET = createXHandler(...)`, `export const { GET } = createXHandlers()`, `export const GET = handle`), and has no dynamic route segment (`export const dynamic = "force-dynamic"` or `export const revalidate = 0`); the app runs with Cache Components, which rejects route segment `dynamic` exports, so a factory-bound handler is trusted to read its request and the build manifest verifies it; a file with no recognizable method export fails too, so an unmodeled form fails closed. Only `GET` is statically prerendered, so a handler file that exports only methods other than `GET` and `HEAD` needs no signal. The source half also runs in `bun run gates`, whose gate test scans the repository's real handlers and requires none to be static. It is a static-text heuristic: comments and string literals are not parsed, a handler that only declares an unused request argument still counts as a signal, and a handler that reaches a request-time read only through an imported helper is reported although Next treats it as dynamic — call `await connection()` in the handler to satisfy the gate. It names the offending route and points at the [Next.js Cache Components route-handler guidance](https://nextjs.org/docs/app/getting-started/route-handlers#with-cache-components).
- No comments in CSS or Python under the five product layers beyond a third-party notice header and Python functional lines (shebang, encoding declaration, `# type:`/`# noqa`), so the [comment policy](architecture.md#comment-policy) covers the source formats Oxlint cannot parse.
- Every `process.env` read is declared in `.env.example`, so a clone knows which variables it needs.
- No personal-email literal in the live-login/Gmail helpers, fixture-session helper, `docs`, or `.agents`, so the bot mailbox stays runtime configuration (`HOME_VERIFY_ACCOUNT_EMAIL`) instead of a committed address.
- Storybook review-board frames, literal `?id=` links in stories, manifests, and story inventories, and inline inventory IDs resolve to exported story IDs; board frame IDs must be unique and board stories registered. The gate derives the same story IDs Storybook indexes — the same story-file globs, literal and regex `includeStories`/`excludeStories` filters, exported declaration forms and story-level id overrides — and fails on an input form it cannot model instead of guessing.
- Custom lint rules are non-vacuous, proven against temporary-mirror fixtures rather than a clean source tree.
- Production TypeScript in `apps/web` (the app, client, components, config, lib, server, shared, and types layers plus root instrumentation, proxy, and Next config; excluding tests, stories, testing, explorations, test harnesses, and smoke fixtures) has per-file type-assertion, non-null assertion (including definite-assignment `!`), suppression-directive, and explicit generic parse/JSON-call counts compared against the merge base of `BASE_REF` and `HEAD`. The count is syntactic: a generic call counts when its callee name, or the module path of a default import, or a same-file named import, destructuring, or `const` alias of it, contains `parse` or `json`, so a shadowing name can over-count; helpers that return `any` under another name are left to the unsafe type-aware rules. Only paths the change touches are compared, so no change can fail on debt it did not introduce and a new path starts from zero; the budget for each changed path is its count at the merge base (nothing is hand-maintained), a changed path may not raise any of the four counts over that budget, and only debt the change adds fails. A path git reports as renamed at any similarity carries its source's content, recounted as the destination's script type, and a path absent at the base revision whose content matches a deleted path in the same scope byte for byte takes that source's counts once; a move git reports as a separate delete and add otherwise begins at zero and needs narrowed casts or a reviewed exception. A reviewed exception with a reason in `scripts/gates/type-assertions-exceptions.json` covers debt a change adds, where inherited exceptions grant nothing, duplicate entries for one path and kind sum, and an exception granting more than the change adds to a touched path is a non-failing note. Test and story TypeScript (`*.test.*`, `tests/`, `testing/`, test harnesses, smoke fixtures, and `*.stories.*`) has the same per-file counts compared against the same merge base, with its own reviewed exception surface in `scripts/gates/type-assertions-test-exceptions.json`; this scope never includes production TypeScript, and `.mts`/`.cts` harnesses or fixtures join it only outside production, preserving existing production membership. A test- or story-named path is in that budget wherever it lives, including `apps/web/scripts/` and `*.stories.*` files under an `explorations/` tree; a path that matches neither scope — tooling config files, `.storybook/` entry points, top-level `stories/` workshop helpers, and exploration files that are not test- or story-named — stays outside both. Run `bun run assertions:report` for both current per-file inventories. `BASE_REF` names a branch (`<name>`, default `main`, resolved as `origin/<name>`) or a commit SHA; an unresolvable base ref, commit, or merge base fails loudly, with `git fetch origin main` or an explicit `BASE_REF` as the fix. A base without an exceptions file grants nothing (the introducing pull request); an unreadable or malformed base file fails loudly.
- Every `oxlint-disable`/`eslint-disable` directive in Oxlint's linted `apps/web` tree is counted by rule and file in `scripts/gates/lint-disables-baseline.json`, and every counted directive must carry a `-- <reason>`. The checked-in counts may only shrink: the gate compares them against the remote-tracking base branch tip (`origin/<BASE_REF>`, default `origin/main`) or, for push CI, the commit SHA supplied as `BASE_REF`; a raised count fails, so a branch must merge a base that lowered a count. Admitting a disable — or moving one to a new path — requires a reviewed exception entry (`path`, `rule`, `count`, `issue`, `reason`) that links a lint issue. Deleting a disable leaves its count stale until `bun run disables:shrink` lowers it; nothing raises a count automatically. Only a resolved base that does not carry this baseline file yet (the pull request that introduces it) reports a note instead of failing. The gate does not fetch or fall back to a local branch; fetch the remote base before rerunning if `origin/<BASE_REF>` is unavailable. An unresolvable ref or a malformed base baseline fails.
- Production modules never import or re-export `explorations/` code. `home/no-exploration-imports` covers static, re-export, dynamic, template, `require()`, and type-query (`typeof import("./x")`) forms in the production layers; story, test, and exploration files are exempt. The rule also consults TypeScript's JSDoc parse in JavaScript and TypeScript files and reports exploration references TypeScript resolves, including braced or brace-less type queries, `@import` tags, and escaped specifiers. Comment text TypeScript does not read as a reference, such as non-JSDoc comments, description prose, and a template-literal specifier inside an `import(...)` type expression, stays clean; an `@import` tag's module specifier is always reported, even when written with backticks. Statically known path fragments are followed across concatenation, template, assertion, conditional, and logical forms; identical operand alternatives collapse before expansion, and analysis is bounded by 4096 distinct merged alternatives, 16384 operand-pair evaluations, and a 16384-segment work budget per specifier. Exceeding any bound stops merging and rejects the specifier for this rule, so an exploration join cannot hide past the bound; the shared fragment check covers only fragments accumulated within the bound. The override fences the eight app, client, components, config, lib, server, shared, and types layer directories and every root-level JS-family file through `./*.{js,jsx,mjs,cjs,ts,tsx,mts,cts}`. `scripts/gates/exploration-boundary-exemptions.json` is the reviewed exemption surface carrying a reason for every non-production top-level directory and root-level file, and the override's `excludeFiles` must name exactly those root files; each exemption names a literal path, so a path containing a glob metacharacter is invalid rather than interpreted as a pattern; root-level test, story, and test-harness modules are already non-production under the canonical exclusions and need no separate entry. The gate fails when a top-level directory or root-level JS-family file with lintable source carries no fence, canonical exclusion, or reasoned exemption, when an exemption is stale, duplicated, or lacks a reason, or when the override's `files` or `excludeFiles` differ from that canonical set. The override also owns `home/no-test-support-imports` and `home/no-full-portfolio-presentation`, and the gate fails when one of the three boundary rules drops out of that owner, moves to a second override, or is set to a non-enforcing severity (`off`, `allow`, or `0`, including array form). The gate also pins the linted ignore surface (`ignorePatterns`) so a production path cannot silently leave the linter. It also proves Oxlint selects every git-visible production source file for linting (discovery), so no ignore mechanism (config ignores, ignore files, or an ancestor `.gitignore`) can drop a production path silently, with `.storybook/static/mockServiceWorker.js` as the one reasoned exception.
- Production modules never import or re-export test-support code. `home/no-test-support-imports` covers static, re-export, dynamic, template, `require()`, and type-query (`typeof import("./x")`) forms only in the production layers, stripping the `@/` alias prefix and normalizing specifiers (backslashes and `.`/`..` segments) rather than resolving against the checkout path before rejecting `tests/` and `testing/` directory segments, `*.test.*` modules, and test harnesses; a fully static specifier is normalized completely, while a fragment adjacent to an unknown expression keeps a trailing `..` because that segment may continue. Story, test (including `*.test.*` declaration variants), `tests/`, `testing/`, exploration, and story-fixture importers are exempt, and `**/*test-harness.*` modules are exempt as importers but rejected as production import targets. A barrel inside a test-support tree can no longer re-export exploration code into production. Statically known path fragments are followed across concatenation, template, assertion, conditional, and logical forms; identical operand alternatives collapse before expansion, and analysis is bounded by 4096 distinct merged alternatives, 16384 operand-pair evaluations, and a 16384-segment work budget per specifier. Exceeding any bound stops merging and rejects the specifier for this rule, so a test-support join cannot hide past the bound; the shared fragment check covers only fragments accumulated within the bound.
- Every config rule exemption in `apps/web/.oxlintrc.jsonc` has a reviewed entry (`glob`, `rule`, non-empty `reason`) in `scripts/gates/lint-exemptions-baseline.json`, sorted by rule then glob and unique on that pair. `scripts/gates/lint-exemptions.mjs` inventories `off`, `allow`, and numeric `0`, including array-form severities, for top-level rules (glob `**`) and every override `files` glob. Warnings still fail under `--deny-warnings` and are not exemptions. New exemptions require an explicit reviewed baseline entry or restoring the rule; deleted exemptions fail as stale until `bun run lint-exemptions:shrink` drops them while preserving surviving reasons and never adding entries. Malformed config or baseline input and any additional Git-listed Oxlint config fail closed. Categories, plugins, and override `excludeFiles` are outside this inventory; directive counts remain separate and unchanged.
- No new Knip production exemption hides exploration-only code. `scripts/gates/knip-exemptions.mjs` resolves every `entry` pattern ending in `!` and every `ignore` pattern in `apps/web/knip.json` against the import graph. Non-production classification covers only `*.stories.*` files, `**/explorations/**`, the top-level `stories/` workshop tree, `.storybook/`, and test paths; a production path is never design-lane because of its file-name suffix. A production-path module is exploration-only when stories or explorations reach it, directly or through a chain of production modules that nothing else consumes; a pattern matching one fails. A production module with no importers is treated as an entry-like production root, so a module it imports is not exploration-only; the gate cannot tell a dead production helper from a route or config entry. `scripts/gates/knip-exemptions-baseline.json` is the reviewed exception surface, like the other allowlist gates: an exemption passes only when the same change adds a baseline entry with a reason, so every one is explicit and reviewed rather than silent. A baseline entry that no longer applies fails as stale. Each baseline entry also records its `kind`: an `"exploration-only"` entry makes the exempt module a design-lane root, so the gate walks its production import closure and fails any module in it that is itself exploration-only and has no exemption of its own, naming the chain from the exemption. `"test-support"`, `"cli-entry"`, and `"structural-contract"` entries record a different reason and never make their module a design-lane root, so no walk starts from them and nothing they import becomes design-lane; a module that is itself exploration-only still fails when an `"exploration-only"` entry reaches it through them. An `"exploration-only"` entry is stale once a product consumer appears; the other kinds are stale once their pattern leaves `knip.json` or matches no source file, which the gate decides by evaluating that pattern against every source path rather than only the exploration-only candidates. A missing or unknown kind fails closed. Test-only importers do not count as exploration use, and a type-only reference — `typeof import("./x")`, `import("./x").Type`, or a JSDoc `@type {import("./x")}` — counts as reaching the module, so a story that only names a type still registers. A JavaScript module's JSDoc `@import { X } from "./x"` registers the same importer edge as a static import of the module it names, while a template-literal specifier TypeScript parses but cannot resolve registers nothing. An unknown top-level Knip key or a second Knip config fails closed. A `!`-negated `ignore` pattern excludes its own re-included match only, never an `entry` exemption, and an `ignore` list of only negated patterns fails closed. Shared component `cva` variants and exports used only by stories are reported by `scripts/gates/story-only-usage.mjs` as diagnostics in `bun run gates` output and never fail it; a type-only import or JSDoc `@import` binding still counts as a use of a component's exports, but never as a runtime JSX tag or variant call.

  Picomatch with `{ dot: true }` decides every match verdict, so the gate never reimplements its dialect. Compilation and matching run in child processes under a five-second default evaluation budget per run with SIGKILL: a pattern that exhausts it — a reviewed config edit with a star-heavy single segment, for example — is reported as invalid rather than stalling the gate, already completed results are retained, later unevaluated patterns are identified, and child/protocol failures remain diagnostics rather than successful empty results.

  Degradation reporting is separate from matching: debug regex compilation failures, extglob text tokens whose emitted output is exactly the escaped literal spelling of that token (not safe semantic rewrites such as `+(*(a))` or `+(*(a)|*(b))`), and brace ranges with non-single-character endpoints or a step are reported as invalid unless an exact candidate path equals the pattern. Range validation also recognizes closing brace tokens with quoted suffixes. Only `file === pattern` is honored for a degraded pattern; non-exact Picomatch matches are not accepted. Cleanly compiled literal syntax remains supported.

## Production warm navigation

The **Production warm navigation** workflow (`production-navigation.yml`) runs `bun run --cwd apps/web test:browser-production-navigation` with the pinned Node/Bun/Chromium setup used by performance CI. Its `chromium-production-navigation` project builds with the local pinned Next binary, then uses `next start` and credential-free smoke fixtures; only the warm Home/Cash/Invest request assertion runs, without skips or retries. It waits for visible destination content, measures warmed Cash as well as Invest and Home, and fails on any document/navigation or RSC request. Build/startup/assertion failures fail this workflow, with total build/start/test wall time in the step summary and counts plus failure traces/video in the `production-navigation-results` artifact.

This workflow triggers only on push to `main` and `workflow_dispatch`. It adds no PR build cost and no dependency to required checks; **Chromium smoke** keeps its development-mode coverage and server command. See [production warm navigation](browser-validation.md#production-warm-navigation) for the local command, fixture restrictions and `Playwright-rung: dispatch` rationale.

## SQL query behavior

The required **SQL query behavior** job executes the generated Base ERC-20 transfer query against embedded ClickHouse (`chdb==4.4.0`) with synthetic `base.events` rows. It covers named, numeric-string, Int8 and Enum8 actions, cancellation and re-addition, numeric ordering, keyset pagination after aggregation, wallet/token/time/event filters, and rejection of unknown actions. These tests live in `scripts/sql/`, outside the apps/web unit shards; the required `bun check` CI aggregate waits for this job and fails if it fails. They do not contact CDP or require provider credentials, and do not establish provider-specific query acceptance or index performance.

To run separately from the ordinary local unit suite, create a Python 3.12 virtual environment, install `chdb==4.4.0` with `pip install --only-binary=:all: chdb==4.4.0`, activate it, and run `bun test --preload ./tests/server-only-preload.ts ../../scripts/sql/base-erc20-transfers.test.ts` from `apps/web`. The application has no Python runtime dependency.

## Unit-test runtime

CI runs the apps/web unit suite in parallel `unit tests (server)` and `unit tests (client)` jobs. Tracked Bun test files under `app/`, `client/`, `components/`, and `tests/` belong to client; all other test files belong to server, including root files and future top-level directories. Each shard hands its top-level directories and root files to the bounded-batch runner below, so CI keeps that batching, its DOM preload and its RSS guard; a shard is filtered before batching, so a batch holds only that shard's files and the commands below reproduce one shard exactly. The required `bun check` job waits for both shards, `static checks`, and `SQL query behavior`; it verifies that the two JUnit reports cover every tracked unit file exactly once and fails if either shard, static checks, or SQL query behavior fails. A test file that yields no testcases is a coverage failure. Local `bun check` runs the entire suite in batches, then the static checks. Files share one Bun process per batch, so a test that passes alone but fails in a batch usually depends on a module another file loaded first; make the file load what it needs rather than relying on order. After the client shard's batches, the same job runs the whole client shard again as explicit, alphabetically sorted paths (`node scripts/gates/unit-test-file-order.mjs client`), the batch runner's opposite: Bun is handed the paths rather than a directory to discover, the static import scan separates DOM tests from non-DOM tests, and the DOM partition preloads the same harness as a DOM batch so happy-dom's registration and blocked fetch cannot reach the non-DOM files. Within each partition the paths run in contiguous groups of at most 10 files by default, one sequential `bun test --max-concurrency 1` process per group, so a runaway group is bounded; `HOME_UNIT_TEST_FILE_ORDER_GROUP_SIZE` overrides the group size. The trade-off is that each group boundary starts a fresh process, so cross-group state interactions are no longer exercised and a file that depends on state from an earlier group fails; within a group the sorted explicit paths still share one process, and each group's first file must self-setup. A file that only passes when another file ran first, or that leaves global state a later file needs, fails there; a failing group names its files, and a group over its 240 s budget fails with that named cause instead of an unattributed Bun watchdog. The check reports plain pass or fail and does not feed the runtime budgets, which stay calibrated to the batched shards. The same check accepts `server`; that variant covers the server shard the same way and is available locally, but the required CI job runs only the client shard.

The `apps/web` `test` script discovers Bun test files and runs them sequentially in sorted batches of 25 files (`HOME_UNIT_TEST_BATCH_SIZE` overrides this). A static import scan separates DOM tests from non-DOM tests; DOM batches preload the happy-dom test harness before module loading. The preloaded DOM hook sets Base UI's `BASE_UI_ANIMATIONS_DISABLED` before every test in every file, because Base UI's close-animation wait under happy-dom cost gigabytes per test; a test that asserts animation timing sets it to `false` itself, and a file that deletes it cannot take the default away from a later file. Each batch records its partition, peak RSS and status in `unit-test-results/memory.json`, retains JUnit under `unit-test-results/batches/`, and contributes to the merged `unit-test-results/junit.xml` even if another batch fails. A failed test is reported separately from a Bun runtime failure (signal, non-test exit, missing or invalid JUnit, or an exit-1 report that records no failing testcase, such as a module that throws while it is imported), with the affected files named. The run fails above 3 GiB peak RSS per batch (`HOME_UNIT_TEST_MAX_RSS_MB` overrides the limit); DOM batches peaked near 0.7 GiB when it was set. Both overrides require positive integers. The previous results directory is removed before argument checks. Positional arguments to `bun run --cwd apps/web test` filter file paths: an argument that starts with `./` names a file or directory scope, and other arguments match anywhere in the path. Flags such as `-t name` pass through to every batch, while `--watch`, `--hot`, `--bail`, `--coverage` and the other coverage flags are rejected because they cannot span batches. Blank override values count as unset.

A deferred chunk that a test opens for the first time is evaluated at the top of its test file instead, which keeps that module load out of every test window and leaves the sheet's shared loader unresolved. Per-test time ceilings stay in `scripts/gates/test-runtime-allowlist.json`, not in a test's own watchdog, so the batch reports the same measurement the runtime gate reads. The one exception is a file whose per-case cost is a spawned subprocess: the Oxlint rule tests and the fixture-server tests carry a file-level watchdog budget (20 s) because a loaded shared process can stretch a single spawn past Bun's 5 s default, and the runtime gate still enforces the calibrated ceiling from the measured JUnit.

The **Unit-test runtime** CI step merges JUnit reports from both shards. A test over 5 seconds or a file over 30 seconds fails unless `scripts/gates/test-runtime-allowlist.json` declares a higher ceiling; exceeding that ceiling still fails. The `tests` and `files` entries match exact identities. A `testFiles` entry sets a per-test ceiling for every test in one file, used by the Oxlint rule-check harness whose per-case cost is a spawned linter process. Unless a `files` entry overrides it, that file's ceiling is its declared per-test ceiling multiplied by the number of testcase elements measured for it, repeated identities included, because the file time sums every occurrence. The test identity is its nested describe names and test name joined with ` > ` (or just the test name without a describe), which is why an entry can be copied from the slow test's console line. Bun emits describes as nested `testsuite` elements; its `classname` attribute joins the same describes in the opposite order and is not used. File time is the sum of testcase times, including repeated testcases; hooks and module load are not included. Repeated test identities in one file use their maximum time for the per-test check.

Ceilings are calibrated as `ceil(max observed × 1.25)` from ten CI-runner samples at the main baseline. Entries must be sorted and unique, with ceilings above the defaults and a non-empty evidence `reason` alongside each ceiling. Raising a ceiling is visible next to its reason in the reviewed diff; there is no PR-body declaration or separate authorization step. An entry absent from JUnit fails as stale and should be removed; a `tests` or `files` entry currently within the default limit produces a non-failing removable note. The `testFiles` ceilings express declared harness budgets and are not reported as removable outliers. Removing or lowering ceilings is always allowed. The base comparison is informational: the job summary lists added, raised (old and new ceilings), and removed entries. The base is resolved from `origin/<BASE_REF>` or a local `<BASE_REF>` (with a fallback note); an unavailable or invalid base allowlist is a note, not a failure, and HEAD is never substituted. Missing, malformed, or empty JUnit reports fail, as does a root `tests` count that is missing or differs from the number of testcase elements (including skipped and repeated cases).

Run the full suite locally with `bun run test` followed by `node scripts/gates/test-runtime.mjs` from the repository root. To reproduce CI, run `node scripts/gates/unit-test-shards.mjs run server`, save `apps/web/unit-test-results/junit.xml`, then run `node scripts/gates/unit-test-shards.mjs run client` and save its JUnit separately (each run recreates the results directory, then batches that shard). Pass both to `node scripts/gates/unit-test-shards.mjs verify --junit server=<server.xml> --junit client=<client.xml>` and `node scripts/gates/test-runtime.mjs --junit <server.xml> --junit <client.xml>`. Local machines differ from the CI runner; investigate local findings against CI timings rather than treating local measurements as calibration. CI runs the runtime step whenever shard JUnit exists, even after failed coverage; the required check remains failed. ## Performance budgets

The **performance budgets** job runs in `.github/workflows/performance.yml` on every push to `main`, nightly at 03:17 UTC, and by manual `workflow_dispatch`. Pull requests run it only while carrying the `perf` label: opening, reopening, and synchronizing a labeled PR run it, as does adding `perf` after opening. Adding any other label skips the job without canceling a running one. Removing `perf` no longer cancels an in-progress run; later PR updates skip the job until `perf` is added again. It uses an isolated production fixture build, not a dev server or a provider-backed session. It pins Ubuntu 24.04, the repository's Playwright Chromium, a mobile viewport, and CDP CPU 4× throttle. It samples 20-row calibration and 100-, 300-, and 2,000-row Activity feeds with three 6,000 px flings each, ten warm round trips from Home to each of Invest, Cash, Borrow, and Investments (one fresh browser context per destination, after one unmeasured warm-up visit), and ten Activity-detail and Send modal cycles. Activity has no Home control, so it is covered by cold route loads only; the retired `/balances` route redirects to Cash or Investments and is no longer a measured cold route.

Structural gates block from day one:

- **Mounted rows:** at most 25 Recent-group rows in the settled window after each fling, at every feed size. Focus is cleared before each fling, because the list deliberately keeps a focused row mounted. The peak during the gesture is reported but not gated: it is about 30 mid-list, because the list overscans eight rows on each side.
- **DOM nodes:** connected elements and text nodes on each cold-loaded route stay at or below the baseline plus 10%.
- **Warm requests:** zero network requests of any kind start during warm client-side navigation. No request is allowlisted. The fixture build sets `NEXT_PUBLIC_HOME_INTERACTION_SAMPLE_RATE=0`, so sampled navigation telemetry cannot add random beacons. Query freshness is held fixed after warm-up, so a request reflects navigation behaviour rather than expiring data. Each destination's loop finishes well inside the 60-second savings poll.
- **Initial JS:** the gzip size of the distinct scripts in each route's document HTML stays at or below the baseline plus 5%. A script URL that appears twice counts once, because the browser fetches it once; the streamed shell can repeat a chunk tag that the static shell already carries.
- **Resource growth:** CDP DOM nodes, event listeners, and JS heap after forced garbage collection are compared between cycle 2 and cycle 10 of each navigation loop and each modal loop. Nodes and listeners tolerate +65 and +12, and heap tolerates +2.5 MB.
- **History writes:** at most five `pushState`/`replaceState` calls per fling.
- **Balances painted (`balances-painted`):** `/home` and `/cash` each measure a cold load and a persisted restore in the same session. The restore waits for a settled owner query snapshot, marks its queries stale, and reloads with session and balances reads held until `balances:painted` is collected. Each kind must stay within 1.5× its baseline mark-to-shell ratio, scaled by the new document's own `shell:paint`. The baseline selects the median-ratio sample per kind from three cold-load/restore pairs per route. The seed records 2× the larger baseline-kind ratio times that document's shell paint, waiting for the shell mark when necessary. Missing, non-finite, or non-positive marks are harness errors.

The `perf:seeds` self-check injects one synthetic regression per structural gate through the harness, never through product code. Each seed runs only its own gate's scenarios on a reduced sample: one fling repetition on the 20- and 300-row feeds, the cold route loads, or the 20-row feed with one navigation path and one modal. A seed that escapes fails the job.

The `perf:cpu-check` self-check opens separate 4× and 1× sessions, fills each 300-row feed at 1×, then measures twenty alternating Home→Cash→Home and Home→Invest→Home round trips per session. It checks that the applied rate matches the requested rate on every sample, 1× script time is at most 60% of 4× script time, and 1× has fewer long animation frames (≥50 ms) than 4×. A 4× run with no long frames is reported as an inconclusive failure (`signal`). The budget harness records requested and applied CPU throttle for every fling, warm navigation, and modal-open sample in `results.json` (cold route loads measure DOM nodes and bytes, plus startup paint marks on `/home` and `/cash`); a mismatch is named in `results.json` and `summary.md`, then the run exits as a harness error.

Timing is report-only until 2026-10-11. It covers fling p95 rAF interval, the share of intervals over 33.4 ms, trace-counted dropped frames, long-animation-frame blocking, detail-open, warm navigation p50/p95, and modal-open latency. Each metric except dropped frames has an absolute ceiling and a relative ceiling against this job's own 20-row calibration run. Dropped frames are recorded without ceilings until their headless variance is known. Share and blocking metrics use an additive margin (for example, the 33.4 ms share must be at most 5% and no more than 2 points above calibration); latencies use a 1.5× ratio. Breaches do not block. The first three failing or breaching scenarios in a run (structural failures first) are re-run once with a Playwright trace and a CPU profile. After 2026-10-11, a pull request will propose blocking thresholds from the observed variance; the job never switches over on its own.

Run `bun run --cwd apps/web perf:budget --base-url http://localhost:3199 --out-dir performance-results` against the isolated production fixture using the [local server recipe](activity-performance.md#activity-scroll-profile). Intentional baseline changes use `perf:budget --update-baseline` and include the updated `apps/web/scripts/performance/baseline.json` in the same PR, reviewed like code. The `performance-results` artifact keeps regression traces, JSON, Markdown summaries, seed results, and the server log for 90 days. The workflow summary includes a trend over the last 20 completed `main` runs of the performance workflow, with the median job runtime and the share of completed jobs that failed or needed a rerun (the flake indicator). The trend fills in from new runs after the workflow moves out of CI.

The job is not a required pull-request check. A structural failure marks the `main`, nightly, manual, or labeled-PR workflow run as failed; it does not fail the separate CI workflow or its required `bun check` job.

Synthetic Chromium and CDP CPU throttle are not real device frame-rate measurements. The job does not validate production network or device performance.

## Styling guards

`home/no-descendant-has` and `home/no-important-utilities` are added to the existing styles rule module (`apps/web/oxlint/rules/styles.mjs`, alongside `home/no-literal-utility-styles`) and compile each class token with the Tailwind design system already loaded for `home/no-unknown-tailwind-classes`, so every spelling and alias is judged by the CSS it emits. Their policies live in `apps/web/oxlint/policy/has-selectors.mjs` (child-form rules and the form-control allowlist: combobox, field, input group, OTP) and `apps/web/oxlint/policy/important-utilities.mjs` (exact file and token pairs with a reason). No existing rule covered `:has()` or `!important`; the source CSS test in `bun run gates` and the post-build `bun run css:built` check reuse the same selector policy rather than a parallel parser. The source CSS test also reads `@apply` token lists for Tailwind's important modifier, terminating the body at the next `;`, `{` or `}`, so `@apply p-4!` fails exactly like a written `!important`; comments and quoted strings are masked first, so a commented-out or string-literal `@apply` and a value such as `content-['!important']` are not miscounted. The built gate accepts only a descendant `:has()` whose first CSS-unescaped class in the subject compound (the compound that owns `:has()`) is an exact `has-*` variant utility or `group/…`/`peer/…` marker written in an allowlisted form-control file; a class inside `:not(…)` or a multi-alternative or combinator `:is()`/`:where()` argument does not own the subject, while a single same-subject `:is()`/`:where()` wrapper does. Root subjects include `:root`, `html`, `body` (with or without a namespace prefix), top-level `:scope` (not `:scope` inside `@scope`), `@scope` start and end prelude selectors, and any nesting of `:is()`/`:where()` whose alternative's subject compound is one of them; CSS escapes that spell letters are decoded before selectors and `!important` are compared; Tailwind excludes the non-UI `apps/web/oxlint/` tooling tree from its source scan. Story files are outside both lint rules because a class they generate matches only elements carrying that class, and any product use is linted; CSS inside TSX `<style>` blocks is outside these guards. A new form-control allowlist entry needs a measured story.

The unused-token test reads `globals.css` declarations through `scripts/gates/globals-css-allowlist.mjs` and scans `apps/web` source with `scripts/gates/source-files.mjs` and the string extraction in `scripts/gates/css-custom-properties.mjs`. It counts `var(--name)` uses (including theme mappings referencing root values), static Tailwind utility and variant classes (including the parenthesized custom-property shorthand such as `bg-(--color-probe)`), and CSS `@apply` bodies (read to the next `;`, `{` or `}`). Class classification reads `classBody`, a slice with comments blanked, quoted interiors with their non-whitespace characters replaced by `x` while the quotes and any whitespace stay, so quoted whitespace still separates tokens, and bracketed groups preserved, so arbitrary modifiers such as `@probe/['a']:block` remain recognizable without quoted CSS text becoming a utility consumer. Body boundaries, shorthand and important checks use `maskedBody`, which still blanks quoted strings and bracketed groups, so a brace inside `content-['}']` cannot end the body early. JS/TS literals keep their existing class-scanning path. `scripts/gates/tailwind-theme-spellings.mjs` derives consuming spellings from the installed Tailwind build, memoized per distinct declared-token set: candidate namespaces are dash-prefixes of Tailwind's default theme keys plus every namespace introduced by the repository's declared `@theme inline` tokens. It probes these prefixes with unique values, compiles all functional utility roots, negated variants and variant-modifier probes in one batch, and reads base variant templates from Tailwind's metadata. Only candidates with a consuming spelling are kept. Named-container modifier forms (`@probe/sidebar:block`, `@min-probe/sidebar:block`) are measured per variant template, including negated forms, rather than assumed: only a compiled `/sidebar` probe adds a `/{modifier}` template. A modifier template matches exactly one unescaped slash outside brackets, parentheses and quoted runs, followed by a bare container name (`[A-Za-z0-9_.-]+`) or exactly one non-empty arbitrary group (`[...]`). A dedicated modifier validator, independent of class-separator depths, tracks nested brackets and parentheses: backslashes escape the next character, single/double quoted runs keep delimiters literal, opening parentheses increase their depth, and extra closing parentheses clamp their depth at zero. A closing bracket decreases bracket depth only when parenthesis depth is zero; the group must reach bracket depth zero exactly at the final character, with parenthesis depth zero and no open quoted run. Backticks remain literal. `@probe/[a]:block`, `@probe/[a/b]:block`, `@probe/[(])]:block` and `@probe/[())]:block` match, while `@probe/[]:block`, `@probe/[a]b:block`, `@probe/[a(b]:block`, `@probe/(a/b):block`, `@probe/a\/b:block`, `@probe//sidebar:block` and `@probe/:block` do not. Templates without that marker require an exact segment match, so unsupported breakpoint forms such as `probe/sidebar:block` and `not-probe/sidebar:block` cannot keep a token live. Whitespace always separates class tokens, including immediately after a backslash or escaped character and inside brackets, parentheses or quoted runs; each separator resets delimiter depths and quoted state. Single, double and backtick quotes outside brackets and parentheses also separate tokens. Inside brackets and parentheses, only single and double quotes open quoted runs that keep brackets, parentheses, colons and other quotes literal until the matching unescaped quote or the end of the literal; backticks are literal characters. Parentheses inside brackets do not change the depth outside those brackets. Escaped non-whitespace characters remain literal and cannot change delimiter or quoted state; unmatched closing brackets and parentheses clamp their depth at zero. Class segments split only at unescaped colons outside brackets, parentheses and quoted runs, so quoted arbitrary-value delimiters cannot keep an unrelated variant token live or hide a consuming utility. Thus `blur-probe`, `tracking-probe`, `rounded-tl-probe`, `leading-probe` and a breakpoint's `probe:block` variant keep their theme token live without a hand-maintained spelling list. Every matching namespace is considered, including overlapping `--font` and `--font-weight` prefixes. Two residuals still need a `var()` reference: a declaration named exactly like a bare default-value key (`--spacing`, `--radius`), which is a default-value lookup rather than a namespace value, and a token consumed only through a utility modifier such as `text-lg/7`. A third conservative limit: the guard measures the spellings the installed compiler accepts, not which candidates the Tailwind source scanner extracts, so a spelling that compiles only through a CSS `@apply` body (for example `not-@probe:block`) is counted as a use in class strings too. The contract test pins the default-theme-only namespace set and verifies a matching spelling keeps each modeled namespace's probe token live while a wrong spelling reports it unused; a Tailwind upgrade that adds a default-theme namespace requires confirming this behavior and updating the test's namespace list. Additional canaries cover namespaces introduced only by declared tokens. The resolution test reads the same shorthand in class strings and `@apply` bodies: a `var()` or shorthand without a fallback must resolve, while a fallback makes the reference optional. Stories and `**/explorations/**` count as source; tests, the top-level `oxlint/` tooling tree, and generated/build directories do not. There is no unused-token allowlist file: remove a dead declaration rather than silently exempting it. The CSS-module gate checks Git-listed existing `*.module.css` files under `apps/web`, including new untracked files; `**/explorations/**` and the `apps/web/stories/` tree are exempt, as is a module named `*.stories.module.css`. Other modules must have an exact path and non-empty reason in `scripts/gates/module-css-allowlist.json`.

Unrecognized variant segments in a chain are conservatively treated as uses, matching the guard's existing behavior for any unknown variant prefix: `@probe/a:b:block` keeps `--container-probe` live just as `notavariant:bg-probe` keeps `--color-probe` live.

The arbitrary-modifier validator is deliberately conservative (fail-open) for exotic nested-delimiter combinations, where the validator may disagree with Tailwind in either direction: it treats `[([)]]` as a use although Tailwind rejects that modifier, and it reports `[([])]` unused although Tailwind compiles it. The guard never reports a compiling modifier spelling unused in the measured matrix; this does not establish exact acceptance parity for every possible delimiter combination.

## Fix-commit provenance

The repository gate checks commits after the pull request branch's merge-base with `main`; outside a pull request it checks `HEAD`. Every scoped `fix(...)` subject must name exactly one detector in its commit body with one of these trailers: `Caught-by: lint`, `Caught-by: bot`, `Caught-by: review`, `Caught-by: browser`, or `Caught-by: production`. Identical trailers count once, because a squash merge that records message bodies concatenates every inner commit's body and a multi-commit fix PR repeats the same detector once per commit; two different detectors in one body still fail, as does none. Earlier commits on `main` are grandfathered.
On `main`, a pushed pull request squash (a subject ending in `(#N)`) is exempt from the trailer check because some merge tools write only the title; the required **Caught-by PR body** check enforces its detector on the PR body before merge. Direct pushes to `main` still need the trailer.
A GitHub squash merge uses the pull request title as the commit subject; it writes the pull request body as the commit message only when the merge tool records one, so a title-only squash keeps no body. Therefore every scoped `fix(...)` PR must put its `Caught-by: <lint|bot|review|browser|production>` line in the visible PR body, even when the branch commits already have trailers; a branch-only trailer does not reach the squash commit on `main`. Identical lines count once, but multiple distinct detectors fail the PR-body gate. The **Caught-by PR body** check runs in the separate **PR metadata** workflow, which also runs when the title or body is edited, so the verdict always matches the current pull request title and body.

## Caught-by report

`bun run caught-by-report` (or `node scripts/gates/caught-by-report.mjs`) aggregates the `Caught-by` trailers from scoped `fix(...)` commits into a detector report. It defaults to `--since 30.days` on the current branch, accepts `--range <a..b>`, and prints JSON with `--json`. It is a report, not a gate: it always exits 0, so a broken or empty corpus never fails a build.

The report has three parts. **Detectors** counts every scoped fix commit by its `Caught-by` value and shows each detector's share. Identical trailers dedupe to one value (`browser`, `browser` counts as `browser`); a squash-merged body with two or more distinct values counts as `mixed`, which is what multi-commit fix PRs look like on `main`. For a post-policy title-only squash whose subject ends in `(#N)` and whose commit body has no valid trailer, the report looks up that pull request body and reads its visible lines using the same rule as the PR-body check (ignoring HTML comments and code fences). One detector is recovered, multiple distinct detectors count as `mixed`, and none count as `unknown`; an unavailable lookup also counts as `unknown` and is reported separately. Lookups share a bounded time budget; lookups past it count as unavailable. Fixes that do not descend from the trailer policy start (`226d2f26`, #709, 2026-09-21) are marked pre-policy and excluded from the detector and scope statistics, with the count stated in the report header. **By scope** breaks the same counts down by the `fix(<scope>)` token. **Rule candidates** lists every `review`, `bot`, and `production` fix (including recovered ones) with its sha, subject, and files touched; each row is a rule candidate for the gardener to triage under the [rule-first policy](operating-manual.md#delivery-loop), because a `home/*` lint rule could have caught it. The report caps the candidate list at 50 rows with 10 files each and truncates its body at 60,000 characters.

The **caught-by report** CI job writes the pull-request-range report to the run summary, and the **Caught-by weekly** workflow posts the trailing 7-day report as a comment on the open `Caught-by weekly report` issue, creating one when no open issue exists and pinning it when possible. The weekly report step supplies a pull-request read token for body lookup. Both are informational; neither fails a build.

In tests, a pin with `setSystemTime(x)` or `useFakeTimers({ now: x })` exempts Date reads in its own scope (test, program body, describe body, or post-hook), and a pinning `beforeEach`/`beforeAll`/`before` also governs tests/hooks; a `beforeEach` pin does not cover `beforeAll`/`before` reads in the same or any descendant suite. A pin in one test or describe does not exempt a sibling. The last pin in the read's own scope decides, even when invalid. Otherwise, the innermost container with an applicable `beforeEach` pin decides for tests and later hooks; only if none exists does the innermost applicable `beforeAll`/`before` pin decide. A `beforeAll`/`before` read is governed only by earlier-phase pins. Within each phase and container, the last registered pinning hook decides. Pins in sibling scopes keep governing their own scopes. Framework callbacks are recognized by call name or imported name rather than binding identity, so a local lookalike is treated as a framework callback. A singly registered named suite body provides container ancestry. - `home/no-silent-catch` rejects a catch when some path has no observable disposition: empty or comment-only bodies, bare returns, discard-only bodies, outer assignments of only `undefined`, and conditional handling with an unhandled fallthrough path. The same policy covers inline `.catch(handler)` and `.then(onFulfilled, onRejected)` rejection callbacks, including bracket-spelled static keys such as `run()["catch"](handler)`; dynamic keys are not analysed. Concise arrow bodies count as returned values, while `.cancel()` and `.return()` cleanup on a stream or iterator receiver (`reader`, `stream`, `iterator`, or a `*.body` stream) is exempt. Explicit return values, non-`undefined` assignments to outer bindings read after the try, throws, approved reporting and recovery calls, collection cleanup such as `pending.delete(key)`, `void reportClientError(...)` reporting calls, promise settlement, and aborts are dispositions. A call to a same-file helper that itself throws, reports, or sets outer state disposes, and a nested `try`/`catch` disposes when every arm returns, throws, or assigns outer state. A `try` whose `finally` block always throws disposes unless a `try` or `catch` arm diverges. A `finally` that reports on every path through an approved reporting helper, or a returned or awaited telemetry write inside an `observeSafely` callback, likewise disposes the whole `try` statement unless a `try` or `catch` arm returns, because the finalizer's own exit discards a pending arm return. A `while (true)`, `do … while (true)`, or `for (;;)`/`for (; true;)` loop with no `break` or `continue` in its body cannot complete, making a later report unreachable and preventing a containing `try` or `catch` arm from reaching a reporting or throwing finalizer or preserving a retained fallback; it counts as reporting only if its body reports on the first iteration, while other loop tests and loops nested in unmodelled statements are not proved divergent. A finalizer that can diverge counts as a path without disposition even when its arms report, return, or throw. The proof is syntactic and conservative: a statement kind the analysis does not model, a `break` or `continue`, or an evaluated `yield` or class body before the report counts as a path that may not report, and an exception from an expression evaluated before the report — a call, property read, `await` or a throwing operation such as BigInt arithmetic — or a disposal in a nested resource scope can still skip it, so a `finally` that only cleans up, disposes only conditionally, or reports only on some paths does not. A catch with no disposition of its own also preserves a disposition when its try assigns an outer `let` or `var` with a non-`undefined` initializer and that retained fallback is read after the try; inline promise handlers likewise preserve a fallback assigned by their inline success callback, but outer recovery assignments and retained fallbacks require a read after the chain is directly awaited in the same function, within a chained inline `.then` success or `.finally` callback, or inside a function expression or arrow created after the chain's statement (such as an effect cleanup), which cannot run before the handler is scheduled; a function declaration hoisted into the calling function, or any closure inside one, does not count. A syntactically later read alone, or returning the chain without a sequenced read, does not prove settlement; promise aliases and named continuations are not traced. Fallback-value correctness belongs to `home/no-amount-fallback` and code review; this rule never asks code to be reshaped between `return x` and an outer assignment. Coverage includes `app`, `client`, `components`, `config`, `server`, `shared`, and root `instrumentation*.ts` files. The rule targets the state-and-cache failures represented by `a3efbae2`, `01042089`, and `14465e42`. An approved reporting helper counts only when its call resolves to an approved helper export imported from a configured `reportingModules` entry (`@/server/observability/log` or `@/client/observability/client-reporter`); an alias of an approved export counts, but a local function, parameter, or object method of the same name does not. `observeSafely(...)` additionally requires an inline callback that calls either `emitServerEvent`/`writeObservabilityEvent` imported from `@/server/observability/log`, `reportClientError` imported from `@/client/observability/client-reporter`, or an injected sink parameter declared by a delegation wrapper whose body is exactly that `observeSafely(...)` call (a single expression statement or a concise arrow body), with an argument on every path; a parameter used as a sink inside a larger function body does not count; a parameter the wrapper reassigns, including through a default value, does not count either; the telemetry call must itself be the callback's returned value without an enclosing `finally` between the return and callback boundary that can override or delay it (`return`, `await`, `for await`, `break`, `continue`, `throw`, or a `using`/`await using` declaration in the finalizer's own execution context or in a block the returned value exits), or an awaited operand that disposes immediately even with such a finalizer. The scan is syntactic and conservative: it recognizes only those constructs in an enclosing explicit finalizer or in a block the returned value exits,also scans the body of a synchronous, non-generator immediately invoked function expression plus the parameter initializers of any immediately invoked plain function or generator in the finalizer's execution context (including constructs before a return in the finalizer itself; a generator's parameters run synchronously even though its body does not, while an async function's parameter failure becomes a rejected promise rather than a synchronous throw), and treats a bare returned telemetry write inside a `for...of` body as unsurfaced because closing the iterator can discard it,  so an exception from a call or property read, or a disposal in a scope it does not model, can still discard the returned promise — a call left in a statement, conditional, binding, or any other expression is not a disposition, because `observeSafely` can only consume a thrown error or a rejection from the callback's returned promise. Import aliases of those exact exports count, but arbitrary imports (including report builders), variable aliases, and parameters declared inside the callback do not. Returning, console logging, or throwing the caught error inside its swallowed callback does not count.

## HTTP, query-scope and address-primitive lint contracts

Five rules enforce the adopted HTTP, query-scope, and address primitives. They are syntax rules: they detect a written shape and cannot prove that a call is bounded at runtime, that a query actually invalidates, or that an address reached a branded type.

- `home/no-inline-request-json` rejects a zero-argument instance `.json()` call in `app`, `server`, and `shared` modules, excluding `server/http/**`, `shared/http/**`, tests, stories, testing helpers, and explorations. Static construction such as `Response.json(body, init)` is a different call shape and stays clean. Application boundaries parse through `readJson` in `apps/web/shared/http/read-json.ts`.
- `home/no-manual-abort-timeout` rejects a `setTimeout` whose callback reaches an `.abort(...)` call, including a callback named through an immutable same-file `const` binding, in `server` modules outside `server/http/**` and tests. `AbortSignal.timeout` and stream-cleanup callbacks that cancel a reader or resolve a promise stay clean. Pre-existing sites whose migration is tracked by #1187, #1188, #1189, and #1190 are listed in `apps/web/oxlint/policy/http-primitives.mjs`; delete an entry when its file adopts the shared upstream deadline. Each entry also pins the exact number of findings its file produces and each registry pins its total size, so a new violating site -- even one added inside an already-listed file -- fails that rule's own test until the entry is explicitly lowered in the same reviewed change.
- `home/no-fetch-in-client-components` rejects a statically-GET `fetch` in `client` and `components` modules, excluding tests, stories, testing helpers, and explorations. A call whose second argument cannot be shown to be a GET (a pass-through `init`, for example) stays clean, as do `POST`, `PUT`, `PATCH`, and `DELETE` mutations. Its policy registry is empty.
- `home/query-key-factory` rejects a `queryKey` property whose value is an array literal, a string literal, or an immutable same-file alias of either, in `client` and `components` modules outside tests, stories, testing helpers, and explorations. Keys come from the registered scope factories in `apps/web/client/query/query-options.ts` over the `queryScopes` registry. Its policy registry is empty. `apps/web/client/query/query-scopes.test.ts` separately proves that every scope with `mutatedByActions: true` is invalidated after a confirmed action or refreshed on pull.
- `home/no-address-literal-regex` rejects an anchored hex-40 address validator written as a regex literal or a `RegExp` constructor call with a static pattern, anywhere outside tests, stories, testing helpers, explorations, and the lint tooling tree. Sentinel checks such as `^0x0{40}$`, extraction embedded in a larger pattern, hash patterns, and range or unanchored forms stay clean. Pre-existing validators are listed in `apps/web/oxlint/policy/address-literals.mjs` and must be deleted as their files adopt `parseAddress` or `requireAddress` from `apps/web/shared/chain/hex.ts`; the rule's own test fails on a stale entry. `parseAddress` and `requireAddress` validate through viem's strict checksum path, which accepts an all-lowercase address and any address whose letter casing matches its EIP-55 checksum, and rejects an address that is neither all-lowercase nor checksum-correct, while several registered sites currently accept any-case hex-40; the migration must therefore review each site's acceptance change instead of treating the swap as behaviour-neutral.

These registries are pinned baselines, not blanket disables: each entry names one file and a finding count, the matching rule test fails when an entry stops violating or a listed file gains a new violation, and neither registry size may rise. `apps/web/shared/chain/hex.ts` is the canonical helper and is never listed. The timer rule analyzes a callback body and the helpers it calls; a parameter default is not analyzed, so a default that aborts its controller is a documented miss. The negative and control fixtures in `apps/web/oxlint/tests/` and the delivery-mirror contracts in `scripts/gates/tests/oxlint-contracts.test.mjs` prove shape coverage only.

## Portfolio presentation boundary

`home/no-full-portfolio-presentation` keeps `presentBalances` out of production consumers. Home uses `presentHomeBalances`, Cash uses `presentCashTotal` and `presentCashSelection`, and Investments uses `presentInvestmentTotal` and `presentHoldingMark`; the retired full-list presenters no longer exist. The rule is an error in the normal lint and CI gate. It checks named imports and re-exports, aliases, relative and `@/` paths, extension variants, and statically composed dynamic imports and `require` calls. Runtime namespace/default imports and wildcard exports of the presenter module are rejected because they obscure which API is used; type-only imports/exports and named focused presenters are allowed. Tests, stories, testing helpers and explorations retain the existing non-production exclusions.

This boundary prevents known full-portfolio entry points from leaking into a page that shows a summary or a single slice; it does not prove runtime complexity or 60 fps. Arbitrary computed module paths and values passed through function arguments are outside its analysis, so work-count or component tests still prove that a retained hidden page does not construct rows. Review any new presenter or boundary exception for unnecessary sorting/formatting. Performance acceptance also requires large-wallet browser/device evidence; lint is not a timing benchmark.

## SQL performance evidence

The **SQL performance evidence** CI step runs `node scripts/gates/sql-performance.mjs` for pull requests. It compares the merge base of `origin/<BASE_REF>` and HEAD and finds changed production server modules containing SQL-looking string/template literals, plus server SQL files (including migrations). Any edit to such a module requires exactly one visible `SQL-performance: <verified|not-verified|not-applicable> — <specific evidence, blocker, or reason>` line. Missing, malformed, duplicate, comment-hidden or fenced lines fail. Tests, fixtures and docs are excluded.

This is an evidence-presence guard, not a SQL planner or a proof of index use. It does not cover indirect changes in other helper modules or runtime SQL assembled without recognizable literals. Reviewers apply [SQL performance](sql-performance.md) to every changed query regardless of detection. A blocked disposition keeps validation honest; it does not establish acceptance. Gate contract tests run in `bun run gates`.
