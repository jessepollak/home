# Repository gates

`bun run gates` first checks that this worktree has a ready dependency tree (printing `bun run worktree:bootstrap` when it is missing, incomplete or stale), then runs the repository gate unit tests, and `bun check` runs that plus the rest of the checks. The check compares installed versions against `bun.lock`—each declared dependency with an attributable lockfile key must match its workspace-selected resolution, so a nested copy at another version of the same name is not ready; names recorded only at unattributable keys may match any recorded version. An installed lockfile-recorded package whose `package.json` is unreadable or has no string `version` is not ready either. Root-declared dependencies must resolve from the root `node_modules`; only `apps/web` declarations may resolve from the hoisted root tree. It cannot see damage inside a file of a version-correct package; a clean reinstall repairs that. All of it runs without provider or funded-wallet secrets. These checks guard seventeen invariants across `bun run gates` and `bun check`:

- Migrations run before build, so a build cannot ship a schema it never applied.
- Every table a migration in `server/db/migrations/` or `server/funding/migrations/` creates has a row in the [data model](architecture.md#data-model) with a `record` or `observation` kind and a reason; partitions are covered by their parent, and any exemption carries a reason and fails once stale. The gate reads `CREATE TABLE` in migration SQL and in the quoted bodies PostgreSQL executes (`DO`, function bodies, and a literal `EXECUTE` argument); quoted text stored as data is not SQL, and dynamic SQL inside a body fails the gate rather than hiding a table.
- No unresolved CSS custom properties, so every referenced token resolves in the theme.
- `globals.css` has only the imports, `@source` directives, variants, custom-property names, selectors, and rule declarations in `scripts/gates/globals-css-allowlist.json`. This exact structural allowlist includes the shell-owned deferrals (#1075/#1137) and is the allowlist consumed by #1140's styling guards; adding or retiring global surface requires updating it. It pins token names, not token values: retuning a colour or radius needs no allowlist change.
- Every custom property declared in the `@theme inline`, `:root`, `.dark`, `@supports`, and `@media` sections of `globals.css` has a `var(--name)` reference or, for Tailwind theme mappings, a statically recognizable utility use. This includes references in design explorations and stories; tests and Oxlint tooling are not consumers. The unused-token guard has no committed exceptions after removal of the unused `--radius-3xl` mapping.
- New product CSS modules are prohibited outside explorations and stories. The five retained modules and their specific reasons are pinned in `scripts/gates/module-css-allowlist.json`; deleted modules make their entries stale.
- Source CSS in `app/`, `client/`, and `components/` (including explorations and story files in those layers) has no root-anchored `:has()`; product CSS outside explorations and story files has no `!important` outside an exact-match allowlist. The top-level `stories/` workshop tree is outside this source guard.
- Built CSS has no root-anchored `:has()` and no descendant/non-child `:has()` except classes emitted from the reviewed form-control source files. Direct-child forms are allowed. This invariant runs in `bun check` after build, not in `bun run gates`, scans production output under `.next` (skipping the development-server `dev/` and `cache/` directories), and fails if the build emits no CSS.
- No comments in CSS or Python under the five product layers beyond a third-party notice header and Python functional lines (shebang, encoding declaration, `# type:`/`# noqa`), so the [comment policy](architecture.md#comment-policy) covers the source formats Oxlint cannot parse.
- Every `process.env` read is declared in `.env.example`, so a clone knows which variables it needs.
- No personal-email literal in the live-login/Gmail helpers, fixture-session helper, `docs`, or `.agents`, so the bot mailbox stays runtime configuration (`HOME_VERIFY_ACCOUNT_EMAIL`) instead of a committed address.
- Storybook review-board frames, literal `?id=` links in stories, manifests, and story inventories, and inline inventory IDs resolve to exported story IDs; board frame IDs must be unique and board stories registered. The gate derives the same story IDs Storybook indexes — the same story-file globs, literal and regex `includeStories`/`excludeStories` filters, exported declaration forms and story-level id overrides — and fails on an input form it cannot model instead of guessing.
- Custom lint rules are non-vacuous, proven against temporary-mirror fixtures rather than a clean source tree.
- Production TypeScript in `apps/web` (the app, client, components, config, lib, server, shared, and types layers plus root instrumentation, proxy, and Next config; excluding tests, stories, testing, explorations, test harnesses, and smoke fixtures) has per-file type-assertion, non-null assertion (including definite-assignment `!`), suppression-directive, and explicit generic parse/JSON-call counts compared against the merge base of `BASE_REF` and `HEAD`. The count is syntactic: a generic call counts when its callee name, or the module path of a default import, or a same-file named import, destructuring, or `const` alias of it, contains `parse` or `json`, so a shadowing name can over-count; helpers that return `any` under another name are left to the unsafe type-aware rules. Only paths the change touches are compared, so no change can fail on debt it did not introduce and a new path starts from zero; a changed path may not raise any of the four counts over the same path at the merge base, and only debt the change adds fails. A path git reports as renamed at any similarity carries its source's content, recounted as the destination's script type, and a path absent at the base revision whose content matches a deleted production path byte for byte takes that source's counts once; a move git reports as a separate delete and add otherwise begins at zero and needs narrowed casts or a reviewed exception. A reviewed exception with a reason in `scripts/gates/type-assertions-exceptions.json` covers debt a change adds, where inherited exceptions grant nothing, duplicate entries for one path and kind sum, and an exception granting more than the change adds to a touched path is a non-failing note. Run `bun run assertions:report` for the current per-file inventory. `BASE_REF` names a branch (`<name>`, default `main`, resolved as `origin/<name>`) or a commit SHA; an unresolvable base ref, commit, or merge base fails loudly, with `git fetch origin main` or an explicit `BASE_REF` as the fix.
- Every `oxlint-disable`/`eslint-disable` directive in Oxlint's linted `apps/web` tree is counted by rule and file in `scripts/gates/lint-disables-baseline.json`, and every counted directive must carry a `-- <reason>`. The checked-in counts may only shrink: the gate compares them against the remote-tracking base branch tip (`origin/<BASE_REF>`, default `origin/main`) or, for push CI, the commit SHA supplied as `BASE_REF`; a raised count fails, so a branch must merge a base that lowered a count. Admitting a disable — or moving one to a new path — requires a reviewed exception entry (`path`, `rule`, `count`, `issue`, `reason`) that links a lint issue. Deleting a disable leaves its count stale until `bun run disables:shrink` lowers it; nothing raises a count automatically. Only a resolved base that does not carry this baseline file yet (the pull request that introduces it) reports a note instead of failing. The gate does not fetch or fall back to a local branch; fetch the remote base before rerunning if `origin/<BASE_REF>` is unavailable. An unresolvable ref or a malformed base baseline fails.
- Production modules never import or re-export `explorations/` code. `home/no-exploration-imports` covers static, re-export, dynamic, template, `require()`, and type-query (`typeof import("./x")`) forms in the production layers; story, test, and exploration files are exempt. Statically known path fragments are followed across concatenation, template, assertion, conditional, and logical forms, bounded at 4096 branch alternatives.
- No new Knip production exemption hides exploration-only code. `scripts/gates/knip-exemptions.mjs` resolves every `entry` pattern ending in `!` and every `ignore` pattern in `apps/web/knip.json` against the import graph. Non-production classification covers only `*.stories.*` files, `**/explorations/**`, the top-level `stories/` workshop tree, `.storybook/`, and test paths; a production path is never design-lane because of its file-name suffix. A production-path module is exploration-only when stories or explorations reach it, directly or through a chain of production modules that nothing else consumes; a pattern matching one fails. A production module with no importers is treated as an entry-like production root, so a module it imports is not exploration-only; the gate cannot tell a dead production helper from a route or config entry. `scripts/gates/knip-exemptions-baseline.json` is the reviewed exception surface, like the other allowlist gates: an exemption passes only when the same change adds a baseline entry with a reason, so every one is explicit and reviewed rather than silent. A baseline entry that no longer applies fails as stale. Test-only importers do not count as exploration use, and a type-only reference — `typeof import("./x")`, `import("./x").Type`, or a JSDoc `@type {import("./x")}` — counts as reaching the module, so a story that only names a type still registers. An unknown top-level Knip key or a second Knip config fails closed. Entry and ignore patterns are matched with the same Picomatch matcher and `dot: true` semantics Knip uses, so an exemption cannot silently match nothing by speaking a different glob dialect. A `!`-negated `ignore` pattern excludes its own re-included match only, never an `entry` exemption, and an `ignore` list of only negated patterns fails closed. Shared component `cva` variants and exports used only by stories are reported by `scripts/gates/story-only-usage.mjs` as diagnostics in `bun run gates` output and never fail it.

The full check suite also covers:

- `bun check` (including Oxlint-only lint with warnings denied, unused suppressions reported, and the Knip production dead-code gate)
- Chromium product smoke
- story tests (`bun run --cwd apps/web test:stories`)
- `bun run gates` (the repository gate unit tests above, including commit provenance; also run inside `bun check`)
- disposable PostgreSQL contracts discovered from tracked `apps/web/**/*postgres*.test.ts` files (including country preferences), run against CI's PostgreSQL 14 service
- unit-test runtime budgets (per-test and summed per-file JUnit timings, with a checked-in outlier allowlist)
- performance budgets (separate, non-required workflow: production fixture, structural gates, and report-only timings)
- the API route contract inventory (`bun test` running `apps/web/app/api/route-contracts.contract.test.ts`), which requires every API route to declare a shared versioned parser contract or a reasoned machine/webhook/redirect/status exemption, checks handler and client linkage, and fails on new or stale baselined gaps

CI cancels in-progress runs only for pull requests. Each push to `main` runs in its own concurrency group keyed by commit, so no push cancels or replaces another and each gets its own verdict.

## Unit-test runtime

CI runs the apps/web unit suite in parallel `unit tests (server)` and `unit tests (client)` jobs. Tracked Bun test files under `app/`, `client/`, `components/`, and `tests/` belong to client; all other test files belong to server, including root files and future top-level directories. Each shard hands its top-level directories and root files to the bounded-batch runner below, so CI keeps that batching, its DOM preload and its RSS guard; a shard is filtered before batching, so a batch holds only that shard's files and the commands below reproduce one shard exactly. The required `bun check` job waits for both shards and `static checks`; it verifies that the two JUnit reports cover every tracked unit file exactly once and fails if either shard or static checks fail. A test file that yields no testcases is a coverage failure. Local `bun check` runs the entire suite in batches, then the static checks. Files share one Bun process per batch, so a test that passes alone but fails in a batch usually depends on a module another file loaded first; make the file load what it needs rather than relying on order.

The `apps/web` `test` script discovers Bun test files and runs them sequentially in sorted batches of 25 files (`HOME_UNIT_TEST_BATCH_SIZE` overrides this). A static import scan separates DOM tests from non-DOM tests; DOM batches preload the happy-dom test harness before module loading. The harness sets Base UI's `BASE_UI_ANIMATIONS_DISABLED` before each test, because Base UI's close-animation wait under happy-dom cost gigabytes per test; a test that asserts animation timing sets it to `false` itself. Each batch records its partition, peak RSS and status in `unit-test-results/memory.json`, retains JUnit under `unit-test-results/batches/`, and contributes to the merged `unit-test-results/junit.xml` even if another batch fails. A failed test is reported separately from a Bun runtime failure (signal, non-test exit, missing or invalid JUnit, or an exit-1 report that records no failing testcase, such as a module that throws while it is imported), with the affected files named. The run fails above 3 GiB peak RSS per batch (`HOME_UNIT_TEST_MAX_RSS_MB` overrides the limit); DOM batches peaked near 0.7 GiB when it was set. Both overrides require positive integers. The previous results directory is removed before argument checks. Positional arguments to `bun run --cwd apps/web test` filter file paths: an argument that starts with `./` names a file or directory scope, and other arguments match anywhere in the path. Flags such as `-t name` pass through to every batch, while `--watch`, `--hot`, `--bail`, `--coverage` and the other coverage flags are rejected because they cannot span batches. Blank override values count as unset.

The **Unit-test runtime** CI step merges JUnit reports from both shards. A test over 5 seconds or a file over 30 seconds fails unless its exact identity is listed in `scripts/gates/test-runtime-allowlist.json` with a higher ceiling; exceeding that ceiling still fails. The test identity is its nested describe names and test name joined with ` > ` (or just the test name without a describe), which is why an entry can be copied from the slow test's console line. Bun emits describes as nested `testsuite` elements; its `classname` attribute joins the same describes in the opposite order and is not used. File time is the sum of testcase times, including repeated testcases; hooks and module load are not included. Repeated test identities in one file use their maximum time for the per-test check.

The checked-in outlier ceilings were calibrated as `ceil(max observed × 1.25)` from ten CI-runner samples at the main baseline. Entries must be sorted and unique, with ceilings above the defaults and a non-empty evidence `reason` alongside each ceiling. Raising a ceiling is visible next to its reason in the reviewed diff; there is no PR-body declaration or separate authorization step. An entry absent from JUnit fails as stale and should be removed; an entry currently within the default limit produces a non-failing removable note. Removing or lowering ceilings is always allowed. The base comparison is informational: the job summary lists added, raised (old and new ceilings), and removed entries. The base is resolved from `origin/<BASE_REF>` or a local `<BASE_REF>` (with a fallback note); an unavailable or invalid base allowlist is a note, not a failure, and HEAD is never substituted. Missing, malformed, or empty JUnit reports fail, as does a root `tests` count that is missing or differs from the number of testcase elements (including skipped and repeated cases).

Run the full suite locally with `bun run test` followed by `node scripts/gates/test-runtime.mjs` from the repository root. To reproduce CI, run `node scripts/gates/unit-test-shards.mjs run server`, save `apps/web/unit-test-results/junit.xml`, then run `node scripts/gates/unit-test-shards.mjs run client` and save its JUnit separately (each run recreates the results directory, then batches that shard). Pass both to `node scripts/gates/unit-test-shards.mjs verify --junit server=<server.xml> --junit client=<client.xml>` and `node scripts/gates/test-runtime.mjs --junit <server.xml> --junit <client.xml>`. Local machines differ from the CI runner; investigate local findings against CI timings rather than treating local measurements as calibration. CI runs the runtime step whenever shard JUnit exists, even after failed coverage; the required check remains failed. CI uploads `unit-test-timings` (both merged JUnit reports, every batch report, `memory.json`, and full timing/findings JSON) for 30 days and prints coverage, findings, notes, and the ten slowest tests and files in the job summary.

## Performance budgets

The **performance budgets** job runs in `.github/workflows/performance.yml` on every push to `main`, nightly at 03:17 UTC, and by manual `workflow_dispatch`. Pull requests run it only while carrying the `perf` label: opening, reopening, and synchronizing a labeled PR run it, as does adding `perf` after opening. Adding any other label skips the job without canceling a running one. Removing `perf` no longer cancels an in-progress run; later PR updates skip the job until `perf` is added again. It uses an isolated production fixture build, not a dev server or a provider-backed session. It pins Ubuntu 24.04, the repository's Playwright Chromium, a mobile viewport, and CDP CPU 4× throttle. It samples 20-row calibration and 100-, 300-, and 2,000-row Activity feeds with three 6,000 px flings each, ten warm round trips from Home to each of Invest, Cash, Borrow, and Investments (one fresh browser context per destination, after one unmeasured warm-up visit), and ten Activity-detail and Send modal cycles. Activity and Balances have no Home control, so they are covered by cold route loads only.

Structural gates block from day one:

- **Mounted rows:** at most 25 Recent-group rows in the settled window after each fling, at every feed size. Focus is cleared before each fling, because the list deliberately keeps a focused row mounted. The peak during the gesture is reported but not gated: it is about 30 mid-list, because the list overscans eight rows on each side.
- **DOM nodes:** connected elements and text nodes on each cold-loaded route stay at or below the baseline plus 10%.
- **Warm requests:** zero network requests of any kind start during warm client-side navigation. No request is allowlisted. The fixture build sets `NEXT_PUBLIC_HOME_INTERACTION_SAMPLE_RATE=0`, so sampled navigation telemetry cannot add random beacons. Query freshness is held fixed after warm-up, so a request reflects navigation behaviour rather than expiring data. Each destination's loop finishes well inside the 60-second savings poll.
- **Initial JS:** the gzip size of the scripts in each route's document HTML stays at or below the baseline plus 5%.
- **Resource growth:** CDP DOM nodes, event listeners, and JS heap after forced garbage collection are compared between cycle 2 and cycle 10 of each navigation loop and each modal loop. Nodes and listeners tolerate +65 and +12, and heap tolerates +2.5 MB.
- **History writes:** at most five `pushState`/`replaceState` calls per fling.

The `perf:seeds` self-check injects one synthetic regression per structural gate through the harness, never through product code. Each seed runs only its own gate's scenarios on a reduced sample: one fling repetition on the 20- and 300-row feeds, the cold route loads, or the 20-row feed with one navigation path and one modal. A seed that escapes fails the job.

The `perf:cpu-check` self-check opens separate 4× and 1× sessions, fills each 300-row feed at 1×, then measures twenty alternating Home→Cash→Home and Home→Invest→Home round trips per session. It checks that the applied rate matches the requested rate on every sample, 1× script time is at most 60% of 4× script time, and 1× has fewer long animation frames (≥50 ms) than 4×. A 4× run with no long frames is reported as an inconclusive failure (`signal`). The budget harness records requested and applied CPU throttle for every fling, warm navigation, and modal-open sample in `results.json` (cold route loads measure DOM nodes and bytes, not time); a mismatch is named in `results.json` and `summary.md`, then the run exits as a harness error.

Timing is report-only until 2026-10-11. It covers fling p95 rAF interval, the share of intervals over 33.4 ms, trace-counted dropped frames, long-animation-frame blocking, detail-open, warm navigation p50/p95, and modal-open latency. Each metric except dropped frames has an absolute ceiling and a relative ceiling against this job's own 20-row calibration run. Dropped frames are recorded without ceilings until their headless variance is known. Share and blocking metrics use an additive margin (for example, the 33.4 ms share must be at most 5% and no more than 2 points above calibration); latencies use a 1.5× ratio. Breaches do not block. The first three failing or breaching scenarios in a run (structural failures first) are re-run once with a Playwright trace and a CPU profile. After 2026-10-11, a pull request will propose blocking thresholds from the observed variance; the job never switches over on its own.

Run `bun run --cwd apps/web perf:budget --base-url http://localhost:3199 --out-dir performance-results` against the isolated production fixture using the [local server recipe](activity-performance.md#activity-scroll-profile). Intentional baseline changes use `perf:budget --update-baseline` and include the updated `apps/web/scripts/performance/baseline.json` in the same PR, reviewed like code. The `performance-results` artifact keeps regression traces, JSON, Markdown summaries, seed results, and the server log for 90 days. The workflow summary includes a trend over the last 20 completed `main` runs of the performance workflow, with the median job runtime and the share of completed jobs that failed or needed a rerun (the flake indicator). The trend fills in from new runs after the workflow moves out of CI.

The job is not a required pull-request check. A structural failure marks the `main`, nightly, manual, or labeled-PR workflow run as failed; it does not fail the separate CI workflow or its required `bun check` job.

Synthetic Chromium and CDP CPU throttle are not real device frame-rate measurements. The job does not validate production network or device performance.

## Styling guards

`home/no-descendant-has` and `home/no-important-utilities` are added to the existing styles rule module (`apps/web/oxlint/rules/styles.mjs`, alongside `home/no-literal-utility-styles`) and compile each class token with the Tailwind design system already loaded for `home/no-unknown-tailwind-classes`, so every spelling and alias is judged by the CSS it emits. Their policies live in `apps/web/oxlint/policy/has-selectors.mjs` (child-form rules and the form-control allowlist: combobox, field, input group, OTP) and `apps/web/oxlint/policy/important-utilities.mjs` (exact file and token pairs with a reason). No existing rule covered `:has()` or `!important`; the source CSS test in `bun run gates` and the post-build `bun run css:built` check reuse the same selector policy rather than a parallel parser. The source CSS test also reads `@apply` token lists for Tailwind's important modifier, terminating the body at the next `;`, `{` or `}`, so `@apply p-4!` fails exactly like a written `!important`; comments and quoted strings are masked first, so a commented-out or string-literal `@apply` and a value such as `content-['!important']` are not miscounted. The built gate accepts only a descendant `:has()` whose first CSS-unescaped class in the subject compound (the compound that owns `:has()`) is an exact `has-*` variant utility or `group/…`/`peer/…` marker written in an allowlisted form-control file; a class inside `:not(…)` or a multi-alternative or combinator `:is()`/`:where()` argument does not own the subject, while a single same-subject `:is()`/`:where()` wrapper does. Root subjects include `:root`, `html`, `body` (with or without a namespace prefix), top-level `:scope` (not `:scope` inside `@scope`), `@scope` start and end prelude selectors, and any nesting of `:is()`/`:where()` whose alternative's subject compound is one of them; CSS escapes that spell letters are decoded before selectors and `!important` are compared; Tailwind excludes the non-UI `apps/web/oxlint/` tooling tree from its source scan. Story files are outside both lint rules because a class they generate matches only elements carrying that class, and any product use is linted; CSS inside TSX `<style>` blocks is outside these guards. A new form-control allowlist entry needs a measured story.

The unused-token test reads `globals.css` declarations through `scripts/gates/globals-css-allowlist.mjs` and scans `apps/web` source with `scripts/gates/source-files.mjs` and the string extraction in `scripts/gates/css-custom-properties.mjs`. It counts `var(--name)` uses (including theme mappings referencing root values), static Tailwind utility classes (including the parenthesized custom-property shorthand such as `bg-(--color-probe)`), and CSS `@apply` bodies (read to the next `;`, `{` or `}`). The theme-utility list enumerates the spellings the evaluator models, so `drop-shadow-probe`, `rounded-tl-probe`, `leading-probe` and `mask-linear-from-probe` all keep their token live; a token consumed only through a namespace the evaluator does not model is reported unused, and is kept live by extending that list or by an allowlist entry with a reason. The resolution test reads the same shorthand in class strings and `@apply` bodies: a `var()` or shorthand without a fallback must resolve, while a fallback makes the reference optional. Stories and `**/explorations/**` count as source; tests, the top-level `oxlint/` tooling tree, and generated/build directories do not. There is no unused-token allowlist file: remove a dead declaration rather than silently exempting it. The CSS-module gate checks Git-listed existing `*.module.css` files under `apps/web`, including new untracked files; `**/explorations/**` and the `apps/web/stories/` tree are exempt, as is a module named `*.stories.module.css`. Other modules must have an exact path and non-empty reason in `scripts/gates/module-css-allowlist.json`.

## Dead-code boundary

The **Dead code (knip)** CI step runs `bun run --cwd apps/web knip`, and `bun check` runs the same production-mode gate. A replacement change deletes the component, hook, or module it replaces in the same PR. New deliberately public exports carry a one-line `/** @public <reason> */` JSDoc. Design-lane non-production code stays inside a `*.stories.*` file or under `**/explorations/**`; temporary deferrals for #686 and #687 are listed explicitly in `apps/web/knip.json`. Exploration-only Knip exemptions are limited to the reasoned baseline above.

## Catalog drift (informational)

The weekly and manually triggered **Invest catalog drift** workflow runs `bun run --cwd apps/web invest-catalog:refresh --onchain` against the official Base stock roster/integration doc, Chainlink Base feed directory, and Coinbase wrapped issuer page. It compares them to dated, committed snapshots without updating product config; status 0 means in sync, 1 means drift (an addition, removal, identity change, a Coinbase tokenized-equity feed for an instrument absent from the Base roster, or a vendored session calendar expiring within 120 days or already expired), and 2 means a source, parser, or chain read failed. Feeds already recorded as feed-only (COIN, CRCL, INTC) are reported separately as `knownFeedWithoutRosterAsset` and are never admitted. The `--onchain` check reads Base token names, symbols and decimals, feed descriptions and decimals, and the oracle registry at one latest block through `BASE_RPC_URL` (the public Base endpoint when unset); a registry entry that no longer returns a positive multiplier for a listed stock is an identity change, because every runtime valuation for that asset would be unavailable. RPC unavailability is reported separately. This workflow is not a required PR check and adds no network access to `bun check`.

## Surface verification boundary

Use the repository-pinned `agent-browser` directly for [fixture and live browser validation](browser-validation.md). The [feature-map surfaces](../.agents/skills/browser-iteration/surfaces/) supply Reach guidance; agents report observed facts and screenshots under PR evidence rules. Playwright remains the only committed automated browser regression layer.

Each surface file declares machine-readable **Owned paths**. The `verification-evidence` CI step maps the pull-request diff to those paths and checks the PR's `## Verification` table for every affected surface, its required rung, an evidence pointer, and incidents, plus a `Verified: <surface> rung <n>` or `Not verified: <surface> rung <n> — <reason>` line for each mapped surface at its required rung. Read-only changes require Rung 1, money-client changes require Rung 2, and action/calldata/confirm-step changes on confirm surfaces require Rung 3. The step is soft (`continue-on-error`) while the map is calibrated. A follow-up PR makes it hard after three consecutive mapped pull requests report no false-positive surface or rung; until then, a failure is a required handoff finding but does not block CI.

## Browser-test ladder boundary

The **Playwright rung** CI step compares `origin/<BASE_REF>...HEAD` with the pull-request body. A positive net count across all `apps/web/tests/browser/**/*.pw.ts` files of added minus removed `test(` or `test.describe(` declaration lines (including nested calls) requires a `Playwright-rung: <rung>` PR-body line, with a rung of `layout`, `scrolling`, `focus`, `history`, `persisted-state`, `media-query`, `hydration`, `dispatch`, or `journey`. Renaming or restructuring existing tests across browser files without a net-new declaration does not trigger the rung. The step checks the declaration, not whether the proposed rung is persuasive; review owns that judgment.

The **Playwright rung** step is hard (no `continue-on-error`): #779 (net zero), #757 (three net-new Playwright tests), and #784 (a file move) supplied three consecutive correct applicable outcomes. The hard **Failure cases** step runs on pull requests only and reads only the PR body. It requires exactly one well-formed `Failure-cases:` line across `## Test plan` sections, ignoring HTML comments and fenced code. Accepted forms are `Failure-cases: <tested>/<dependency calls>` (non-negative integers, tested no greater than calls), optionally followed by whitespace and a short note such as the calls counted, or `Failure-cases: N/A: <reason>` for docs-only and CI-only PRs. It does not judge whether the counts are true; review checks them against the diff under the [test policy](architecture.md#choose-the-case-then-the-layer). The hard **Caught-by PR body** step runs on pull requests only: for a scoped `fix(...)` title it requires exactly one distinct `Caught-by:` detector line in the body, ignoring HTML comments and fenced code; other titles pass. These steps read the title and/or body from the event that started the run, so after correcting PR metadata, push a commit to re-check it. They append their findings to the CI run summary. The seventeen invariants across `bun run gates` and `bun check` above are unchanged because these checks read PR metadata in CI rather than running in `bun check`.

The **PR closing link** job in the **PR metadata** workflow checks `feat`, `fix`, `test`, `ops`, `dx`, `docs`, and `chore` titles, scoped or unscoped, including breaking-change `!` titles. Their bodies need a visible line starting with a closing keyword (`close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, or `resolved`, case-insensitive), optionally followed by a colon. The keyword may follow indentation, a list marker, or a blockquote marker. Targets are positive issue numbers as `#<n>`, `jessepollak/home#<n>`, or `https://github.com/jessepollak/home/issues/<n>`; multiple targets may be comma-separated. Alternatively, use `No issue: <reason>` with a non-empty reason. Keywords within prose, HTML comments, and fenced code do not count; neither does `Refs #<n>` on an implementation title. `design` and `product` titles may use `Refs #<n>` instead and are exempt. This CI job runs on PR opens, edits, reopens, and branch updates; it is not yet a required branch-protection check.

## Story-test boundary

The blocking **story tests** job runs production component and journey stories in headless Chromium through `@storybook/addon-vitest` on every pull request and push to `main`; it excludes stories tagged `exploration`. The separate **exploration story tests** job includes only stories tagged `exploration`, runs on the same events, and uses `continue-on-error` so its failures are visible without failing CI. The audit reports findings rather than failing the job globally (`a11y.test: "todo"`) because owned components carry pre-existing violations that need a product decision; minimal workshop stories that are audit-clean opt into `a11y.test: "error"`. Neither job is part of `bun check`: run `bun run --cwd apps/web test:stories` for production stories and `bun run --cwd apps/web test:stories:explorations` for explorations. ## Fix-commit provenance

The repository gate checks commits after the pull request branch's merge-base with `main`; outside a pull request it checks `HEAD`. Every scoped `fix(...)` subject must name exactly one detector in its commit body with one of these trailers: `Caught-by: lint`, `Caught-by: bot`, `Caught-by: review`, `Caught-by: browser`, or `Caught-by: production`. Identical trailers count once, because a squash merge that records message bodies concatenates every inner commit's body and a multi-commit fix PR repeats the same detector once per commit; two different detectors in one body still fail, as does none. Earlier commits on `main` are grandfathered.
On `main`, a pushed pull request squash (a subject ending in `(#N)`) is exempt from the trailer check because some merge tools write only the title; the required **Caught-by PR body** check enforces its detector on the PR body before merge. Direct pushes to `main` still need the trailer.
A GitHub squash merge uses the pull request title as the commit subject; it writes the pull request body as the commit message only when the merge tool records one, so a title-only squash keeps no body. Therefore every scoped `fix(...)` PR must put its `Caught-by: <lint|bot|review|browser|production>` line in the visible PR body, even when the branch commits already have trailers; a branch-only trailer does not reach the squash commit on `main`. Identical lines count once, but multiple distinct detectors fail the PR-body gate. The **Caught-by PR body** check runs in the separate **PR metadata** workflow, which also runs when the title or body is edited, so the verdict always matches the current pull request title and body.

## Caught-by report

`bun run caught-by-report` (or `node scripts/gates/caught-by-report.mjs`) aggregates the `Caught-by` trailers from scoped `fix(...)` commits into a detector report. It defaults to `--since 30.days` on the current branch, accepts `--range <a..b>`, and prints JSON with `--json`. It is a report, not a gate: it always exits 0, so a broken or empty corpus never fails a build.

The report has three parts. **Detectors** counts every scoped fix commit by its `Caught-by` value and shows each detector's share. Identical trailers dedupe to one value (`browser`, `browser` counts as `browser`); a squash-merged body with two or more distinct values counts as `mixed`, which is what multi-commit fix PRs look like on `main`. For a post-policy title-only squash whose subject ends in `(#N)` and whose commit body has no valid trailer, the report looks up that pull request body and reads its visible lines using the same rule as the PR-body check (ignoring HTML comments and code fences). One detector is recovered, multiple distinct detectors count as `mixed`, and none count as `unknown`; an unavailable lookup also counts as `unknown` and is reported separately. Lookups share a bounded time budget; lookups past it count as unavailable. Fixes that do not descend from the trailer policy start (`226d2f26`, #709, 2026-09-21) are marked pre-policy and excluded from the detector and scope statistics, with the count stated in the report header. **By scope** breaks the same counts down by the `fix(<scope>)` token. **Rule candidates** lists every `review`, `bot`, and `production` fix (including recovered ones) with its sha, subject, and files touched; each row is a rule candidate for the gardener to triage under the [rule-first policy](operating-manual.md#delivery-loop), because a `home/*` lint rule could have caught it. The report caps the candidate list at 50 rows with 10 files each and truncates its body at 60,000 characters.

The **caught-by report** CI job writes the pull-request-range report to the run summary, and the **Caught-by weekly** workflow posts the trailing 7-day report as a comment on the open `Caught-by weekly report` issue, creating one when no open issue exists and pinning it when possible. The weekly report step supplies a pull-request read token for body lookup. Both are informational; neither fails a build.

## Storybook review links

The **Storybook review links** workflow (`.github/workflows/storybook-review-links.yml`) rewrites the Storybook links in a PR's `## Preview` for the current head when the `home-storybook` preview deployment succeeds and when the PR body changes ([Storybook links](ui-pr-previews.md#storybook-links)). It never checks out pull-request code: the script always comes from the default branch. For `deployment_status`, GitHub reads the workflow file at the deployed commit, so a branch that predates the workflow is updated only on body edits until it is rebased. It is informational: problems are warnings, never a red check.

## Browser-smoke boundary

The current **Chromium smoke** job runs the per-surface fixture-backed Playwright suite (`apps/web/tests/browser/*.pw.ts`, with shared responses under `fixtures/`) in GitHub Actions for every pull request and every push to `main`. It starts a CI-local fixture server; it does not exercise the hosted Vercel preview deployment.

A global setup requests the routes the admin smoke first visits so `next dev` compiles them before any test timer starts. CI still runs against `next dev` with unchanged timeouts and two retries for diagnostic traces. `failOnFlakyTests` makes the job fail when any test passes only on retry, rather than treating that run as green. The job prints each test's final outcome and per-attempt timing, plus flaky tests and the slowest tests. Traces and videos from failed attempts remain in the test results and upload with the existing failure artifact. Outside CI, smoke runs without retries.

The Jesse-locked [architecture](architecture.md#quality-bar) targets Playwright smoke on every hosted preview. That hosted-preview smoke target is not implemented yet; current PR/main fixture smoke must not be described as hosted-preview verification.

Deployment configuration, credentials, and production promotion remain operator decisions; a green local or CI run is not funded-wallet or production authorization.

For action changes, review the flow in [Actions](actions.md): server-authored calldata; verified scope; one action ID for provider idempotency; owner-generation fencing; provider and chain status.

## Wave 1 lint contracts

- `home/no-constant-pin` covers unit tests, `*.pw.ts`/`*.pw.tsx`, paths under `tests/` or `testing/`, `*test-harness.{ts,tsx}`, and `*smoke-fixture*.{ts,tsx}`. The shared lint override also lists `*.stories.*`, but this rule's filename guard excludes every story file, including stories under test paths. It rejects `expect(<actual>)` with a single chained `toBe`, `toEqual`, or `toStrictEqual` matcher (not `.not`, `.resolves`, `.rejects`, or a longer chain) when `<actual>` unwraps TypeScript assertion wrappers to an imported SCREAMING_CASE binding with at least one underscore and the expected argument is a scalar literal: a number, string, boolean, bigint, expression-free template, unary `+`/`-` on a number or bigint, or a finite numeric `+ - * / % **` fold of literals. Identity pins remain allowed for constant names ending `_CHAIN_ID`, `_NETWORK_ID`, `_ADDRESS`, `_ADDRESSES`, `_ENDPOINT`, `_ENDPOINTS`, `_URL`, `_URLS`, `_URI`, `_PATH`, `_PATHS`, `_HOST`, `_ORIGIN`, or `_VERSION`, and for literal values that are a 40-hex `0x` address, an `http`/`https`/`ws`/`wss` URL, a string starting `/`, or the numbers 8453/84532. A test proves a tuning knob by exercising the behavior it controls, not by restating its current value.
- `jsx-a11y/*` violations are errors, moving missing accessible names, roles, and ARIA contracts into the gate after the a11y-semantics fixes in `61e7e4d5`, `70b6f070`, and `1491b808`.
- Enabled `jsx-a11y` focus, labeling, role, heading, and anchor rules plus `react/no-array-index-key`, `react/no-unstable-nested-components`, and `react/jsx-no-constructed-context-values` enforce accessible controls and stable render identity; justified exceptions use a reasoned `oxlint-disable-next-line` directive. `jsx-a11y/prefer-tag-over-role` stays off for mostly legitimate roles, `jsx-a11y/no-autofocus` for deliberate first-field focus in sign-in/access steps, and `jsx-a11y/no-static-element-interactions` for dynamic-role globe/chart surfaces, the cash-overview Escape delegation wrapper, and the review canvas.
- `home/no-real-waits` covers unit tests and `*.pw.ts`, rejecting long timers, `Bun.sleep`, Playwright `page`/`frame.waitForTimeout`, promise-wrapped timers, overlong Testing Library waits, and wall-clock reads (`Date.now`, zero-argument `Date` calls/construction, and `performance.now`, including passed references). Inject a clock or use a fixed instant instead. Date reads are allowed file-wide when `setSystemTime(x)` or `useFakeTimers({ now: x })` pins the clock; in Playwright, `page.clock.install({ time: x })` or `page.clock.setFixedTime(x)`/`setSystemTime(x)` permits Date reads only inside page callbacks, not in Node-side fixtures. A pin argument must not itself read the wall clock, and the controlled-clock exemption is file-scoped. `performance.now()` is allowed for direct subtraction or a `const` start subtracted from a later `performance.now()` call; other justified reads need `// oxlint-disable-next-line home/no-real-waits -- <reason>`. A sleep encodes an unnamed precondition, so the fix is to name and poll that observable state, never to delete the wait or relax the assertion until it passes. The named precondition must be the state the sleep was waiting for, checked by asking what can still be in flight when the naive signal first appears: a balances entry existing, or storage staying unchanged over a brief window, is necessary but not sufficient while a throttled persistence write can still be pending, so the settle window must span `ownerQueryPersistThrottleMs`. This closes the Playwright scope gap identified in Codex PR #641 and the fix-corpus gate-browser-test bucket.
- `home/no-request-only-playwright` covers `*.pw.ts`/`*.pw.tsx`, rejecting a `test` (and `test.only`/`skip`/`fixme`/`fail`/`slow`) callback that destructures `request` without naming `page`, `context`, or `browser`, including with a rest binding; request-only checks belong in route or unit tests, keeping browser smoke for browser behavior. Aliased or `extend`ed test bindings are not detected; browser tests import `test` directly.
- `home/no-deferred-effect-setstate` rejects `queueMicrotask` and `Promise.resolve().then` setter callbacks inside client/component React effects, including local aliases; derive render values or move transitions to events, render-time adjustment, or an external-store clock instead.
- `home/no-silent-catch` rejects a catch when some path has no observable disposition: empty or comment-only bodies, bare returns, discard-only bodies, outer assignments of only `undefined`, and conditional handling with an unhandled fallthrough path. The same policy covers inline `.catch(handler)` and `.then(onFulfilled, onRejected)` rejection callbacks, including bracket-spelled static keys such as `run()["catch"](handler)`; dynamic keys are not analysed. Concise arrow bodies count as returned values, while `.cancel()` and `.return()` cleanup on a stream or iterator receiver (`reader`, `stream`, `iterator`, or a `*.body` stream) is exempt. Explicit return values, non-`undefined` assignments to outer bindings read after the try, throws, approved reporting and recovery calls, collection cleanup such as `pending.delete(key)`, `void reportClientError(...)` reporting calls, promise settlement, and aborts are dispositions. A call to a same-file helper that itself throws, reports, or sets outer state disposes, and a nested `try`/`catch` disposes when every arm returns, throws, or assigns outer state. A `try` whose `finally` block always throws disposes regardless of its `try`/`catch` arms, while a `finally` that only cleans up does not. A catch with no disposition of its own also preserves a disposition when its try assigns an outer `let` or `var` with a non-`undefined` initializer and that retained fallback is read after the try; inline promise handlers likewise preserve a fallback assigned by their inline success callback and read after the call. Fallback-value correctness belongs to `home/no-amount-fallback` and code review; this rule never asks code to be reshaped between `return x` and an outer assignment. Coverage includes `app`, `client`, `components`, `config`, `server`, `shared`, and root `instrumentation*.ts` files. The rule targets the state-and-cache failures represented by `a3efbae2`, `01042089`, and `14465e42`. An approved reporting helper counts only when its call resolves to an approved helper export imported from a configured `reportingModules` entry (`@/server/observability/log` or `@/client/observability/client-reporter`); an alias of an approved export counts, but a local function, parameter, or object method of the same name does not. `observeSafely(...)` additionally requires an inline callback that calls either `emitServerEvent`/`writeObservabilityEvent` imported from `@/server/observability/log`, `reportClientError` imported from `@/client/observability/client-reporter`, or a directly injected sink parameter, with an argument on every path; the telemetry call must itself be the callback's returned value without an enclosing `finally` between the return and callback boundary that can override or delay it (`return`, `await`, `for await`, `break`, `continue`, `throw`, or a `using`/`await using` declaration in the finalizer's own execution context), or an awaited operand that disposes immediately even with such a finalizer. The scan is syntactic and conservative: it recognizes only those constructs in enclosing explicit finalizers, so an exception from a call or property read, or an implicit disposal outside a finalizer, can still discard the returned promise — a call left in a statement, conditional, binding, or any other expression is not a disposition, because `observeSafely` can only consume a thrown error or a rejection from the callback's returned promise. Import aliases of those exact exports count, but arbitrary imports (including report builders), variable aliases, and parameters declared inside the callback do not. Returning, console logging, or throwing the caught error inside its swallowed callback does not count.
- `home/no-self-referential-expectation` rejects an `expect(...)` whose expected value uses an identifier imported from the module the test file names by path convention (`foo.test.ts` names `foo.ts`, and normalized names such as `next-config.test.ts` name `next.config`), imported through a relative path or the `@/` alias. Typed and non-null expressions, array and object values, templates, namespace members, and `index` imports from `.` are covered. Tests must assert a literal or an independently derived value; a same-named constant from another module is not a subject import.
- `home/isolate-instrumentation-calls` covers `app`, `client`, `components`, `config`, `lib`, `server`, `shared`, and `types`, plus root `instrumentation*.ts`, `next.config.ts`, and `proxy.ts`. Potentially failing calls imported from the tracked observability modules must be awaited inside `try/catch` or use `void promise.catch(...)`. The `safeHelpers` boundary contains only helpers whose implementation contains recorder or sink failure, or constructs a handler whose reporting path contains those failures; adding a module to tracking does not make all of its exports safe. `observeSafely` is in both boundaries: its implementation performs the sink call, drops a synchronous throw, and consumes a returned rejection, so a noncritical telemetry sink needs no call-site `try`/`catch`.
- `home/no-amount-fallback` rejects zero defaults for names ending in the money tokens `amount`, `balance`, `total`, `quantity`, `value`, `assets`, `shares`, `usd`, `fiat`, or `atomic`, including those tokens followed by `BaseUnits`, `Units`, `Wei`, `Wad`, `Atomic`, `Usd`, or `Fiat`. It covers shared formatting, money-modal, balances, and server-action paths, requiring null/unavailable propagation or fail-closed handling after the value-truth fixes in `6e566e44`, `a5781ae7`, and `088e407c`.

## Portfolio presentation boundary

`home/no-full-portfolio-presentation` keeps `presentBalances` out of production consumers except the named imports in `client/home/balances-panel.tsx`, which owns full list construction. Home and Cash use focused summary/cash presenters instead. The rule is an error in the normal lint and CI gate. It checks named imports and re-exports, aliases, relative and `@/` paths, extension variants, and statically composed dynamic imports and `require` calls. Runtime namespace/default imports and wildcard exports of the presenter module are rejected because they obscure which API is used; type-only imports/exports and named focused presenters are allowed. Tests, stories, testing helpers and explorations retain the existing non-production exclusions.

This boundary prevents known full-portfolio entry points from leaking into summary screens; it does not prove runtime complexity or 60 fps. Arbitrary computed module paths and values passed through function arguments are outside its analysis, and the allowed list owner still needs work-count/component tests proving that hidden panels do not construct rows. Review any new presenter or boundary exception for unnecessary sorting/formatting. Performance acceptance also requires large-wallet browser/device evidence; lint is not a timing benchmark.
