# In-app support

Home keeps one support conversation per customer. `020_support.sql` creates conversations, sent/draft/discarded messages, owner-verified context references, assistant run records, and one encrypted assistant credential. Conversation, message, and run records are deleted when the customer record is deleted. Bodies, previews, model output, provider credentials, and context IDs never enter logs, analytics, or client error reports. Only route, code, outcome, and assistant turn outcome (`replied`, `handoff`, `failed`, `discarded`) are emitted. Responses are private and no-store. The customer drawer is a deferred client chunk: Home's first paint ships neither the chat UI nor the model stream client. It opens a labelled loading drawer while that chunk downloads and offers `Try again` when it cannot load.

Operator settings domain `support-assistant` (schema v1) selects `operator`, `assistant`, or `hybrid`, an AI Gateway model ID, and up to 2,000 characters of instructions. The unrelated `support` email/URL domain is unchanged. The operator supplies a write-only AI Gateway key at `/api/admin/support/assistant/credential` (`GET`, `PUT`, `DELETE`); it is sealed at rest under `support-assistant-key` and bound to `ai-gateway`. Audit records contain only the last four key characters, and the audit feed presents them as `support.credential.update` and `support.credential.delete` on the `support-assistant-key` settings target, with the shared audit parser accepting both. If the mode, model, or usable sealed key is missing, the effective handler is operator; a pending customer message the assistant cannot serve persists an operator takeover so it stays in the operator queue, while answered or superseded messages leave the stored handler unchanged.

The model provider receives the last 30 eligible sent messages combined (customer messages through the claimed message and sent assistant/operator replies before claim time, ordered by creation time and ID), up to 20 read-only context summaries attached no later than the claimed customer message (funding order state, provider, amount and region; money action kind and presenter status — `pending`, `confirmed`, `failed` or `unknown` from the persisted outcome and receipt state), the fixed system prompt, and operator instructions; no other customer record fields or account-action tools. In hybrid, a customer or model may hand off to a person. A model failure, including an SDK timeout/abort without customer cancellation, also hands off in hybrid; in assistant mode it returns a retryable stream error. Customer cancellation may preserve text already produced. Provider-failed partial text is discarded and removed from the client stream, allowing a retry to regenerate. Operator reply takes over automatically; hand back requires an available assistant. An operator reply, an explicit take-over, and a customer or model handoff each clear the active assistant claim in the same conversation-locked transaction, so a superseded run cannot save even when the conversation is handed back before it finishes; resolving clears it too, and a run can only be claimed while the assistant is the effective handler. A resolved conversation resets its handler on the next customer message. Each claimed assistant run, including failed and cancelled runs, counts toward 40 per rolling 24 hours per conversation. Replays of the same customer message may claim at most 10 runs per rolling 10 minutes per conversation.

`POST /api/support/chat` accepts `{version:2,message:{id:<uuid>,text},context?}` and returns AI SDK UI-message SSE, ending with `data-support` containing `{handler,conversationId,discardedMessageId?,limited?:{retryAfter}}`. The browser sends only its newest message, not the transcript. A typed assistant-only limit shows "Too many messages. Try again later." without a regenerate action; the composer becomes available after `retryAfter`, while provider errors still offer retry. If an operator takes over, the provider fails, or the reply cannot be saved after text has already streamed, stream metadata names the discarded message for the client to remove; it never appears in stored/polled history. Replies stop streaming and stop the model at 2,000 characters. Each chat request may stream at most one assistant reply, for its own message only. A request claims only when that message is the latest customer message, has no sent or operator-takeover-discarded assistant reply linked by `in_reply_to`, no sent operator reply after it, and the assistant is effective with available budget. Older messages, including operator-answered messages after a hand-back, are never claimed. A pending message the assistant cannot serve (mode operator, missing key, unreadable settings, or an operator-handled conversation) persists an operator takeover and ends the turn with handler metadata; when the configuration read fails before the send, the send persists that takeover itself, so a cancelled or unstreamed turn cannot leave the message under the assistant. A reply-free assistant-only turn (a provider failure, an empty stream, or a claimed turn whose settings or key disappear) takes the operator over when the configuration is no longer usable. A replay of a message whose claim is active waits and rechecks for up to 35 seconds without a second model call. An answer or supersession returns handler metadata; a still-pending message returns a retryable stream error, including if the claim holder died or released an unanswered turn. If another message's run holds the claim, the request polls at roughly 500 ms intervals for up to 35 seconds, rechecking effective settings and key before each claim and once more after history and context load, immediately before the model call; an unavailable assistant releases that claim with no model call and hands the pending message to the operator. Once released, the request replies if its message is still latest and unanswered, returns only handler metadata if a newer message arrived, or emits a retryable stream error if the wait times out. Customer cancellation releases its claim; an abort during the claim database call still performs a pending-only handoff if the claim succeeds in hybrid, before reporting the persisted handler. Cancellation before text otherwise hands a pending hybrid message to the operator and leaves assistant-only retryable; the drawer then offers Try again for that turn. All automatic handoffs from a chat request, including claim and save budget, model tool calls, cancellation, and failure, are fenced to that request's latest unanswered customer message; a stale request cannot take over a newer turn, even after an operator resolves and the customer reopens. At claim-time budget or replay-limit exhaustion, hybrid hands off with current handler metadata and assistant mode emits typed `limited.retryAfter` stream metadata. `POST /api/support/handoff` accepts `{version:2}` and persists operator takeover even if assistant capability became unavailable between rendering and the request; unlike assistant-run handoffs, this explicit customer action is not fenced to a chat message. `GET /api/support` returns `{version:2,conversation,assistant:{available,handoff}}`; customer messages have `clientMessageId`. Operator list/detail expose effective `handler`; detail also exposes `handedOffAt` and `assistantAvailable`. `POST /api/admin/support/conversations/[id]/handler` accepts `{version:2,handler}`. Existing read/summary/status/reply endpoints remain; the former customer `POST /api/support/messages` is removed. All mutations require same-origin JSON, max 16 KiB, and customer or operator authentication. Customer/operator message limits remain database backed.
In assistant mode, retrying the latest customer message with the same ID reruns a failed assistant turn only when no sent reply or operator-takeover discard is associated with that message; provider-failed discarded output has no reply association and does not block regeneration. Completed or older turns do not regenerate.

Message history is served in newest pages of 50, oldest first, with `messagesNextCursor` for earlier pages, and at most 20 recent context refs; re-attaching a reference moves it to the current message. Opening or polling a conversation records one `customer.read` audit entry per operator and customer every 15 minutes. A resolved conversation shows no handoff control or person-will-reply notice until the customer writes again. The operator inbox marks a conversation `Needs reply` only when its latest message is from the customer. Read receipts advance only through the last observed message; resolving requires the operator's observed message ID, refuses a newer customer message, and advances the marker and clears any active assistant claim in the same conversation-locked transaction. A subsequent customer reopen restores fresh eligibility without reactivating the old run. Operator unread counts only operator-handled conversations with a customer message since the operator read marker. Customer unread counts sent operator and assistant replies since its read marker.

For credential-free browser replay, run the local fixture server with `HOME_PLAYWRIGHT_SMOKE=1` using the fixture session instructions in `docs/browser-validation.md`. Its local-only, non-production chat endpoint returns a deterministic canned reply in the same AI SDK UI stream format. The fixture `GET /api/support` advertises assistant availability; it does not call a provider, save messages, or authorize live operations. This fixture does not prove production authentication, persistence, or provider behavior.
