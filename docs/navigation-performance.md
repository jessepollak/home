# Warm navigation performance profile

Run against an isolated local production fixture build, with an unused loopback port. From the repository root:

```sh
bun run --cwd apps/web profile:navigation --out-dir /tmp/navigation-profile
# Compare another checkout (for example main) on the same machine against the committed baseline:
bun run --cwd apps/web profile:navigation --out-dir /tmp/navigation-main --label main --app-dir <main checkout>/apps/web
```

The command refuses to run if `--app-dir` contains any Next-loadable environment file (`.env`, `.env.local`, `.env.production`, `.env.production.local`); profile from a checkout without them (git worktrees do not copy these untracked files). It builds with `next build` directly (never `bun run build`, which migrates), then owns a `next start` child on `127.0.0.1:3199` and stops only that PID. The file check and clean fixture-only child environments prevent local credentials from entering the build or server; no database migration or provider traffic is intended. The build enables navigation sampling at 100%; the browser uses a signed-in synthetic session and intercepted APIs. Use `--skip-build` only if `.next` was built with `HOME_PLAYWRIGHT_SMOKE=1` and `NEXT_PUBLIC_HOME_INTERACTION_SAMPLE_RATE=1`. Options: `--app-dir` to profile another `apps/web` checkout (it needs its own installed dependencies; its `.next` is rebuilt), `--port` for another loopback port, `--sessions` (default 5, minimum 5), `--round-trips` (default 10, minimum 10), `--rows` (default 300; WebKit feed only—the Chromium fling always uses 300 rows), `--fling-repeat` (default 3), `--headed`, `--baseline` (default `scripts/performance/navigation-baseline.json`), `--update-baseline`, and `--label`. For quick harness checks, `--smoke --sessions 1 --round-trips 1 --fling-repeat 1` relaxes minimums but cannot update the baseline. `--update-baseline` writes a compact form (summary, environment, per-session durations for each leg in round-trip order, raw flings) to the baseline path; every other run compares against the baseline when one exists. Compare only runs with matching machine, build mode, row count, browser, and launch settings: the committed baseline is one machine's reference, not a portable threshold.
The `--fling-repeat` option runs inside an isolated Chromium worker with a 180 s parent deadline per attempt. A failed, hung, invalid-JSON, or structurally invalid result gets one fresh attempt (two attempts maximum). On teardown the worker's detached process group is signaled with SIGKILL (falling back to killing the worker if group signaling fails), and its pipes are destroyed; Playwright launches Chromium in a separate process group, so this signal alone does **not** kill its browser. Immediately after launch, the child lists processes once (`/bin/ps`, 5 s timeout), finds the `playwright_chromiumdev_profile` browser whose parent chain reaches its own PID, and reports that exact browser PID **and** its `--user-data-dir` profile directory on stderr. After a failed attempt, or a successful attempt whose Chromium close timed out, and worker teardown, the parent rechecks only the reported PID with one timed `ps` call and SIGKILLs it only if its process row still has that exact unique profile directory; other **live** Playwright browsers and non-Playwright browsers are never signaled. SIGINT/SIGTERM also kills the worker group, rechecks and reaps the reported browser using the same bounded exact-PID/profile check, then exits 2. If PID or profile resolution fails, the child reports an unknown identity and the attempt continues without reaping. A recheck failure is recorded on that attempt as `reapError` rather than bypassing retry bookkeeping. This best-effort reaping does not cover processes that disappear before rechecking. Only a validated successful attempt contributes fling data; partial attempts are never merged or averaged. The child enforces a 120 s Chromium launch deadline and a 240 s `runFeed` diagnostic deadline; the parent's 180 s per-attempt deadline dominates both the longer `runFeed` deadline and any remaining child stage work. If Chromium close exceeds its 5 s deadline **after** a completed fling, the timeout is logged on stderr with a `fling worker: close timed out` marker, its valid result is still written and accepted, and the parent still reaps the reported browser; failures before a result exists remain fatal. `results.json` records each attempt in `flingAttempts` (attempt number, success, exit code, duration, last ~2 kB of stderr, `strayChromiumReaped` count or null, and `reapError` when applicable); `strayChromiumReaped` is null if no reaping was attempted, including cleanly closed successful attempts and unknown browser identities. `fling` contains only the successful attempt, and `summary.md` names a failed attempt when a retry succeeds. The causes of intermittent hangs are not yet identified, and a fling failure still fails the run after both attempts, with both attempts named and the final stderr tail reported.
Mismatched run options (`rows`, `flingRepeat`, `headed`, `smoke`) or environment (`headless`, WebKit and Chromium versions, platform, CPU, cores) suppress the comparison tables and record `baselineComparable: false` and the mismatched fields in `results.json`; smoke runs never compare with a committed non-smoke baseline. Comparison is suppressed whenever **either** run used `--skip-build`, even when both did, with reason `options.skipBuild: unverified build provenance`. Different session and round-trip counts are allowed. The baseline is a like-for-like machine/build reference; profiling on a new machine requires `--update-baseline` to establish its reference.
A missing baseline is stated in `summary.md` and `results.json` (`baselineNote`); a partial or unknown baseline suppresses deltas with field-named reasons in `baselineMismatches`, while an unreadable or invalid-JSON baseline fails the run.
With `--skip-build`, `summary.md` warns that the existing `.next` build's provenance is unverified despite the recorded checkout SHA, and `--skip-build --update-baseline` is rejected.

Each fresh **desktop WebKit** context fills Home's synthetic Activity feed (`--rows`, default 300), warms Home → Cash → Home and Home → Invest → Home, then measures three round trips per iteration: Cash and return, Invest and return, and Cash followed by browser Back to Home. A report from the client `home-navigation` recorder must arrive within 15 seconds for each leg; measured legs must have the expected route, source, and trigger and `retained` cache. After every report the runner waits two animation frames (5 s in-page deadline plus a 6 s host-side evaluation timeout) and 75 ms before the next action. Each WebKit session has a 300 s deadline, and WebKit close has a 60 s deadline; failures stop the server and exit 2. Its duration starts when navigation begins and ends at the recorder's destination after-paint callback, quantized by the wire parser to 10 ms; it is not a click-to-network or compositor-presented measurement. To collect more than ten reports per page load, the harness intercepts the single matching Next.js recorder chunk, verifies exactly one navigation-cap guard, and changes only `>=10` to `>=1e6` **in the served script**. Product source and the on-disk build are unchanged; a missing or duplicate guard fails the run. Report arrival order is retained.

`results.json` contains the environment and SHA, dirty flag, browser versions, rAF calibration intervals, every navigation sample, raw fling entries, and `flingAttempts` diagnostics. If both fling attempts fail, `results.json` records the start time, environment (with `chromium: null` because no valid fling result was obtained), completed WebKit sessions, and both attempt diagnostics with `fling: null` and `baselineComparable: false`; no fling summary is written. `summary.md` includes pooled p50/p95/max and per-session p95. Report-only gates compare pooled p95 to 100 ms for both Cash legs (`home-cash`), both Invest legs (`home-invest`), and the **history** return leg (`back`); `all-gated` combines those five legs, omitting the in-app Cash leg of Back. A separate mobile **Chromium** 300-row feed fling uses the same CPU 4× scenario as `perf:budget`; its p95 frame interval, share over 33.4 ms, dropped-frame percentage, and blocking-duration medians appear alongside raw flings. A comparable baseline, if available, adds group p95 deltas, baseline label, and SHA. Gate breaches alone do not change the completed-run exit status; browser, fixture, recorder, and server failures exit 2.

Headless WebKit rAF cadence must be checked in `sessions[].rafIntervals` before interpreting low-duration samples. A local smoke run gave a 17 ms median (14–19 ms range), so headless was usable there; if it is irregular or quantized on another runner, rerun with `--headed` on a display and use headed WebKit for comparisons. Headless and headed runs are not interchangeable. rAF callbacks do not prove compositor presentation. The Chromium fling runs in a separate local harness process: closing WebKit and opening Chromium in the same Bun process can stall the browser driver. That child launches the same Playwright `chromium` channel as the other local harnesses, so it needs the standard Playwright browsers directory; it does not read `PLAYWRIGHT_BROWSERS_PATH`. The synthetic feed and clean loopback APIs isolate shell rendering, not live network/provider latency, production sessions, or real Safari hardware. Chromium's CDP CPU throttle and synthetic gesture are not a physical device.

## Results

Recorded for #1342 on one Apple Silicon laptop (16 cores), headless WebKit 26.0 and Chromium 140, 300 rows, 5 sessions × 10 round trips of each kind, headless rAF median 17 ms in every session. Both builds came from the same application commit, because this change adds only the harness; the pair is therefore a same-machine noise check as well as the head/main comparison. Pooled p95 in milliseconds (samples):

| Build | Home↔Cash (100) | Home↔Invest (100) | Back (50) |
|---|---:|---:|---:|
| head (baseline) | 30 | 40 | 30 |
| main | 30 | 30 | 30 |

Every group is within the 100 ms gate. Destination legs (Cash, Invest) were 10–20 ms; the return paint of Home, which carries the 300-row feed, was 20–40 ms. Fling medians over three flings (head → main): p95 frame interval **27.3 → 27.2 ms** and long-animation-frame blocking **0 → 0 ms** were unchanged; share over 33.4 ms fell **3.28% → 2.06%**; dropped frames rose **17.16% → 17.3%** (+0.14 percentage points). The per-fling range across both runs was 16.24–22.63%, so this ungated headless metric shows no regression beyond run-to-run variance. The fling runs on this profiler's sampling build, not the CI budget build with sampling off, so compare it only with this profiler's own runs. Raw head samples are in `apps/web/scripts/performance/navigation-baseline.json`.
