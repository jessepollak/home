# Operator fee records

A fee-bearing confirmed trade writes one normalized `operator_fee_records` row in the same transaction as confirmation. Its unique `action_id` references the action record; confirmation replay does not add another row. Zero-fee trades and other actions do not write fee records. A configured destination equal to the trading smart account is treated as no fee, because the transfer would be a self-transfer; the trade omits the fee leg and writes no record. The row preserves the fee's USDC base units, token identity, basis points, recipient, collection method, action kind, and recording time. It does not duplicate the action's transaction hash or outcome.

The operator revenue query joins fee records to actions. `collectedBaseUnits` counts only actions with a `succeeded` outcome, across all time. UTC daily totals count succeeded fees on the action's `outcome_recorded_at` date, falling back to the fee's `recorded_at`; the selected date range ends today and includes zero-filled days. Amounts remain exact decimal base-unit strings.

A `succeeded` outcome means Home attributed the submitted batch to the action's owner. Totals are therefore *expected* fees from succeeded actions, not a reconciliation against the chain: Home does not yet read the USDC `Transfer` log to the fee recipient, and an owner who dispatches the confirmed calls themselves without the fee leg, then reports that transaction, would count here. Treat the totals as an operator-facing estimate and the movement transaction links as the on-chain record. Verifying each recorded fee against its transfer log is follow-up work.

## Admin → Money movements and export

Admin → Money also shows the USDC balance and address of the revenue destination (fee settings) and the payout account (growth settings), read from Base with `balanceOf` at the latest block, and one list of Home-authored movements. A movement is one fee record joined to its action, so a confirm replay, a wallet decline followed by retry, a revert or an unknown result never adds a second row. Each row carries the fee's `recorded_at` time (UTC), category, exact amount, the fee rate in basis points as recorded, the paying customer's id, the action's current transaction hash, and its status read from the action: `succeeded`, `reverted`, `not_submitted`, or `unresolved` when no outcome is stored. Only `succeeded` rows count toward the overview's expected fees. Payout addresses stay empty for fee rows; reward payouts, the payer's network fees and goodwill credits join this list when they exist (#913). The page shows 100 rows at a time, newest first, with Older and Newest links whose cursor carries the boundary row's `(recorded_at, id)` values, so deleting that row does not strand the link. The export returns the whole list or an inclusive UTC date range (years 2000–2999) on `recorded_at` as CSV with the same columns. One REPEATABLE READ transaction selects the rows, writes the `money.export` audit entry with exactly that row count, and commits before the buffered file is returned, so the file and its audit record always describe the same snapshot. An export is capped at 25,000 rows (about 4.4 MB at the longest row, under the platform's 4.5 MB response limit); a larger request returns 422 `EXPORT_TOO_LARGE` (“Export a shorter range”) and writes no audit entry, and every movement stays exportable by range. Rolling the app back past this change after a `money.export` entry exists breaks the earlier audit reader, which rejects the `money` target; roll forward instead.

`POST /api/admin/money/export` takes `{version: 1, from, to}` (`YYYY-MM-DD` or `null`) from an allowlisted administrator only; a payout signer who is not an administrator, and customers, get `OPERATOR_FORBIDDEN`. It first pins the newest matching record and counts the rows, then appends one `money.export` entry to `admin_audit_log` with the actor, range and row count before it sends any row, so an export that cannot be audited returns nothing. Rows recorded after that point are not included. CSV cells that start with `=`, `+`, `-`, `@`, tab or carriage return are prefixed with `'` so a spreadsheet does not evaluate them; cells with commas, quotes or line breaks are quoted. Migration `029_admin_money_export_audit.sql` only widens the audit log's action, target-kind and shape checks for this entry.
