# Ripio funding adapter

Reference adapter for AR wARS and CO wCOP. It uses raw HTTP through the bounded provider context, one country-specific credential pair per binding, a shared webhook verification secret, quotes, email-based customer creation, terms acceptance, optional KYC fields, order creation, polling, and webhook verification. A binding remains inert until all environment variables in its manifest are set.

## Confirm against your API

1. **Origin, OAuth, and credentials.** Confirm production origin `https://skala.ripio.com`, token endpoint `POST /oauth2/token/`, HTTP Basic authentication with the country-specific client ID and secret, form body `grant_type=client_credentials`, and response fields `access_token` plus numeric `expires_in`. Argentina uses `RIPIO_CLIENT_ID_AR` / `RIPIO_CLIENT_SECRET_AR`; Colombia uses `RIPIO_CLIENT_ID_CO` / `RIPIO_CLIENT_SECRET_CO` ([client.ts lines 140–188](client.ts#L140-L188), [manifest.ts lines 31–59](manifest.ts#L31-L59)). The adapter has no sandbox origin.
2. **Terms.** Confirm `GET /api/v1/termsAndConditions/` returns a UUID as top-level `termsId` or `id`, a `{ results: [{ id }] }` collection, or a top-level array of `{ id }`. Home then calls `POST /api/v1/customers/{customerId}/acceptTerms/` with `{ termsId }`; an unrecognized terms shape fails closed ([client.ts lines 288–292](client.ts#L288-L292), [adapter.ts lines 251–263](adapter.ts#L251-L263)).
3. **Customer and KYC.** Confirm `POST /api/v1/customers/` accepts `{ email, type: "INDIVIDUAL" }` and returns UUID `customerId` plus `createdAt`. Home then submits the remaining manifest fields to `POST /api/v1/customers/{customerId}/kyc/`: `firstName`, `lastName`, `birthDate`, `documentType` (`national-id` or `passport`), and `documentNumber` ([client.ts lines 226–235](client.ts#L226-L235), [293–296](client.ts#L293-L296), [adapter.ts lines 26–40](adapter.ts#L26-L40), [manifest.ts lines 7–17](manifest.ts#L7-L17)).
4. **Base network catalogs.** Confirm `GET /api/v1/depositNetworks/?include_currency=true` and `GET /api/v1/withdrawalNetworks/?include_currency=true` return either an array or `{ networks: [...] }`. The adapter requires a network whose `network_name` or `networkName` is exactly `BASE`, with an asset whose `name` is exactly `wARS` or `wCOP` and whose `contract_address` / `contractAddress` matches Home's registered Base address ([client.ts lines 236–259](client.ts#L236-L259), [492–507](client.ts#L492-L507)).
5. **Quote and order.** Confirm `POST /api/v1/quotes/` accepts `fromCurrency`, `toCurrency`, `fromAmount`, `chain: "BASE"`, and `paymentMethodType`, and returns the quote, decimal amount/rate fields, expiry, and fee fields parsed by Home. Confirm `POST /api/v1/onramp/` accepts `customerId`, `quoteId`, `depositAddress`, and `externalRef`; Home sends its UUID `homeOrderId` as `externalRef` and validates all available transaction binding echoes before showing instructions ([client.ts lines 236–277](client.ts#L236-L277), [315–390](client.ts#L315-L390), [adapter.ts lines 42–102](adapter.ts#L42-L102)). Home accepts a quote only when the returned `finalFromAmount` equals the requested `fromAmount` exactly and `expiration` is in the future; quote economics that change the fiat debit are rejected before any order exists ([core service lines 180–181](../../core/service.ts#L180-L181)).
6. **Country rails and instructions.** Confirm Argentina exposes `bank_transfer` for wARS and returns CVU/optional alias. Confirm Colombia exposes `bank_transfer`, `breb`, `r2p_bancolombia`, and `r2p_nequi` for wCOP, returning the corresponding payment URL, Bre-B key, or Nequi phone number ([manifest.ts lines 31–59](manifest.ts#L31-L59), [adapter.ts lines 172–190](adapter.ts#L172-L190)). There is no Brazil binding on `main`; Brazil remains held on the Pix order contract in [#199](https://github.com/jessepollak/home/issues/199).
7. **Status and refund priority.** Confirm transaction status vocabulary: `CREATED`, `PENDING`, `AWAITING_PAYMENT`; `PAYMENT_RECEIVED`, `ONRAMP_PAYMENT_RECEIVED`; `CONVERTING`, `PROCESSING`, `SENDING`, `ONRAMP_CRYPTO_BUY_IN_PROGRESS`; `COMPLETED`, `SUCCESS`, `ONRAMP_CRYPTO_SENT`; `CANCELLED`, `ONRAMP_CANCELED`; `EXPIRED`; `REFUNDED`, `REFUND_COMPLETED`, `ONRAMP_REFUNDED`; and `FAILED`, `SERVICE_UNAVAILABLE`, `ONRAMP_FAILED`. A `latestRefund.status` of `COMPLETED`, `REFUNDED`, or `SUCCESS` takes terminal refunded priority over the transaction status ([adapter.ts lines 192–206](adapter.ts#L192-L206)).
8. **Webhook.** Confirm Ripio signs the raw body with HMAC-SHA256 using shared `RIPIO_WEBHOOK_SECRET`, sends `sha256=<64 hex characters>` in `http-x-wh-signature-256`, and supplies `eventType`, parseable `issueDatetime`, and `transactionObject.transactionId`. Home strips the `sha256=` prefix before constant-time comparison and receives the event at `POST /api/funding/webhooks/ripio` ([adapter.ts lines 133–140](adapter.ts#L133-L140), [231–245](adapter.ts#L231-L245), [manifest.ts line 29](manifest.ts#L29)). Ripio must document how the production webhook secret is provisioned.
9. **Ripio handoff.** Ripio must confirm the complete production request/response schema above, whether Brazil is available through this API and which Pix order contract applies, and that `https://skala.ripio.com` remains production-only with no sandbox. Confirm whether Ripio requires the end user's IP address or a completion return URL: Home resolves both but transmits neither to Ripio today (the create body is only `customerId`, `quoteId`, `depositAddress`, `externalRef`, and optional `extraData`).

## Runthrough tiers

Run the tiers in order and stop at each boundary until the named authority approves the next one. The adapter has no sandbox mode: every configured binding points at production `https://skala.ripio.com`, so tiers 4 and 5 create real provider records.

1. **Local synthetic validation (no credentials, no network).** From the repository root run `bun test apps/web/server/funding/providers/ripio/`. Every request and response is a synthetic fixture or test double; this is the only tier CI runs.
2. **Credential presence (no provider call).** Copy `.env.example` to `apps/web/.env.local` and set the AR or CO client ID/secret pair plus shared `RIPIO_WEBHOOK_SECRET`, then `FUNDING_QUOTE_SECRET` and `DATABASE_URL` per the [issuer guide](../../../../../../docs/integrations/README.md). Never print or commit values. Restart `bun dev`; the binding appears under **Add money** for its country only when every manifest variable is set.
3. **Read-only provider confirmation (no durable record created).** With credentials set, walk checklist items 1 and 4 against production: `POST /oauth2/token/`, `GET /api/v1/depositNetworks/`, `GET /api/v1/withdrawalNetworks/`, and `GET /api/v1/termsAndConditions/`. Record the observed shapes (no credentials, no PII) against the checklist.
4. **Order-creating test (Jesse's explicit go for this specific action; no funds move).** Complete checklist items 2, 3, 5, and 6 through one AR or CO order: customer creation, terms acceptance, KYC submission, quote, and `POST /api/v1/onramp/`. Keep the Add money screen open so status polling progresses; a local webhook needs an external tunnel, so `POST /api/funding/webhooks/ripio` is expected to stay unmatched locally. An uncertain create response parks the order in `dispatch-ambiguous` and it is never retried automatically.
5. **Funded test (separate explicit authorization; real money moves).** Pay the tier-4 instructions from a real ARS or COP account and watch the order reach `sent-unverified` and then `received` on exact Base receipt evidence. Reconcile the provider transaction, webhook event, and Base Transfer log before closing the runthrough.

All automated coverage uses synthetic responses and test doubles. No live provider call or funded flow has ever been run with this adapter; the checklist above is the production handoff boundary.
