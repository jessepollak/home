# Ripio funding adapter

Reference adapter for AR wARS and CO wCOP. It uses raw HTTP through the bounded provider context, one country-specific credential pair per binding, a shared webhook verification secret, quotes, email-based customer creation, terms acceptance, optional KYC fields, order creation, polling, and webhook verification. A binding remains inert until all environment variables in its manifest are set.

## Confirm against your API

1. **Origin, OAuth, and credentials.** Confirm production origin `https://skala.ripio.com`, token endpoint `POST /oauth2/token/`, HTTP Basic authentication with the country-specific client ID and secret, form body `grant_type=client_credentials`, and response fields `access_token` plus numeric `expires_in`. Argentina uses `RIPIO_CLIENT_ID_AR` / `RIPIO_CLIENT_SECRET_AR`; Colombia uses `RIPIO_CLIENT_ID_CO` / `RIPIO_CLIENT_SECRET_CO` ([client.ts lines 140–188](client.ts#L140-L188), [manifest.ts lines 23–40](manifest.ts#L23-L40)). The adapter has no sandbox origin.
2. **Terms.** Confirm `GET /api/v1/termsAndConditions/` returns a UUID as top-level `termsId` or `id`, a `{ results: [{ id }] }` collection, or a top-level array of `{ id }`. Home then calls `POST /api/v1/customers/{customerId}/acceptTerms/` with `{ termsId }`; an unrecognized terms shape fails closed ([client.ts lines 284–295](client.ts#L284-L295), [adapter.ts lines 250–261](adapter.ts#L250-L261)).
3. **Customer and KYC.** Confirm `POST /api/v1/customers/` accepts `{ email, type: "INDIVIDUAL" }` and returns UUID `customerId` plus `createdAt`. Home then submits the remaining manifest fields to `POST /api/v1/customers/{customerId}/kyc/`: `firstName`, `lastName`, `birthDate`, `documentType` (`national-id` or `passport`), and `documentNumber` ([client.ts lines 225–235](client.ts#L225-L235), [adapter.ts lines 26–39](adapter.ts#L26-L39), [manifest.ts lines 7–17](manifest.ts#L7-L17)).
4. **Base network catalogs.** Confirm `GET /api/v1/depositNetworks/?include_currency=true` and `GET /api/v1/withdrawalNetworks/?include_currency=true` return either an array or `{ networks: [...] }`. The adapter requires a network whose `network_name` or `networkName` is exactly `BASE`, with an asset whose `name` is exactly `wARS` or `wCOP` and whose `contract_address` / `contractAddress` matches Home's registered Base address ([client.ts lines 236–259](client.ts#L236-L259), [492–506](client.ts#L492-L506)).
5. **Quote and order.** Confirm `POST /api/v1/quotes/` accepts `fromCurrency`, `toCurrency`, `fromAmount`, `chain: "BASE"`, and `paymentMethodType`, and returns the quote, decimal amount/rate fields, expiry, and fee fields parsed by Home. Confirm `POST /api/v1/onramp/` accepts `customerId`, `quoteId`, `depositAddress`, and `externalRef`; Home sends its UUID `homeOrderId` as `externalRef` and validates all available transaction binding echoes before showing instructions ([client.ts lines 245–276](client.ts#L245-L276), [315–389](client.ts#L315-L389), [adapter.ts lines 42–90](adapter.ts#L42-L90)).
6. **Country rails and instructions.** Confirm Argentina exposes `bank_transfer` for wARS and returns CVU/optional alias. Confirm Colombia exposes `bank_transfer`, `breb`, `r2p_bancolombia`, and `r2p_nequi` for wCOP, returning the corresponding payment URL, Bre-B key, or Nequi phone number ([manifest.ts lines 23–40](manifest.ts#L23-L40), [adapter.ts lines 171–188](adapter.ts#L171-L188)). There is no Brazil binding on `main`; Brazil remains held on the Pix order contract in [#199](https://github.com/jessepollak/home/issues/199).
7. **Status and refund priority.** Confirm transaction status vocabulary: `CREATED`, `PENDING`, `AWAITING_PAYMENT`; `PAYMENT_RECEIVED`, `ONRAMP_PAYMENT_RECEIVED`; `CONVERTING`, `PROCESSING`, `SENDING`, `ONRAMP_CRYPTO_BUY_IN_PROGRESS`; `COMPLETED`, `SUCCESS`, `ONRAMP_CRYPTO_SENT`; `CANCELLED`, `ONRAMP_CANCELED`; `EXPIRED`; `REFUNDED`, `REFUND_COMPLETED`, `ONRAMP_REFUNDED`; and `FAILED`, `SERVICE_UNAVAILABLE`, `ONRAMP_FAILED`. A `latestRefund.status` of `COMPLETED`, `REFUNDED`, or `SUCCESS` takes terminal refunded priority over the transaction status ([adapter.ts lines 191–205](adapter.ts#L191-L205)).
8. **Webhook.** Confirm Ripio signs the raw body with HMAC-SHA256 using shared `RIPIO_WEBHOOK_SECRET`, sends `sha256=<64 hex characters>` in `http-x-wh-signature-256`, and supplies `eventType`, parseable `issueDatetime`, and `transactionObject.transactionId`. Home strips the `sha256=` prefix before constant-time comparison and receives the event at `POST /api/funding/webhooks/ripio` ([adapter.ts lines 133–140](adapter.ts#L133-L140), [230–243](adapter.ts#L230-L243), [manifest.ts line 47](manifest.ts#L47)). Ripio must document how the production webhook secret is provisioned.
9. **Ripio handoff.** Ripio must confirm the complete production request/response schema above, whether Brazil is available through this API and which Pix order contract applies, and that `https://skala.ripio.com` remains production-only with no sandbox.

All automated coverage uses synthetic responses and test doubles. No live provider call or funded flow has ever been run with this adapter; the checklist above is the production handoff boundary.
