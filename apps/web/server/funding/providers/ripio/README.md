# Ripio funding adapter

Reference adapter for AR wARS, BR wBRL, and CO wCOP. It uses raw HTTP through the bounded provider context, one country-specific credential pair per binding, a distinct webhook verification secret per country account, quotes, email-based customer creation, terms acceptance, Ripio-hosted KYC, order creation, polling, and webhook verification. A binding remains inert until all environment variables in its manifest are set.

- **Environment and hazards:** Ripio has no sandbox. Schema/catalog reads require operator authorization; customer, terms, KYC, quote, and order calls are production writes; payment is separately funded. CI runs no provider call.
- **Owners and approvals:** the adapter owner maintains conformance; the operator owns country credentials and production probes; Jesse explicitly approves each bounded hosted funded rail plan.
- **Stop and recovery:** follow the linked playbook and stop on ambiguity, schema/economic mismatch, unexpected instruction, or approval-bound breach. Never retry an uncertain write; reconcile the durable customer/order and provider status first.
- **Evidence:** retain the playbook's redacted phase evidence per rail, environment, and approver; omit credentials, customer/KYC data, IDs, addresses, amounts, instructions, hashes, provider text, and payloads from logs.
- **Current claim (September 18, 2026):** `in-build` for AR, BR, and CO, matching `apps/web/config/coverage.ts`; no sandbox, live, hosted-funded, or production acceptance is claimed.

## Confirm against your API

1. **Origin, OAuth, and credentials.** Confirm production origin `https://skala.ripio.com`, token endpoint `POST /oauth2/token/`, HTTP Basic authentication with the country-specific client ID and secret, form body `grant_type=client_credentials`, and response fields `access_token` plus numeric `expires_in`. Argentina uses `RIPIO_CLIENT_ID_AR` / `RIPIO_CLIENT_SECRET_AR`; Brazil uses `RIPIO_CLIENT_ID_BR` / `RIPIO_CLIENT_SECRET_BR`; Colombia uses `RIPIO_CLIENT_ID_CO` / `RIPIO_CLIENT_SECRET_CO` ([client.ts lines 151–223](client.ts#L151-L223), [manifest.ts lines 31–70](manifest.ts#L31-L70)). The adapter has no sandbox origin.
2. **Terms.** Confirm `GET /api/v1/termsAndConditions/` returns a UUID as top-level `termsId` or `id`, a `{ results: [{ id }] }` collection, or a top-level array of `{ id }`. Home then calls `POST /api/v1/customers/{customerId}/acceptTerms/` with `{ termsId, ipAddress }`, where `ipAddress` is the address Home observed on the request; the call is required to carry it, loopback and private addresses are accepted by the provider, and a request with no observable address fails closed rather than sending a substitute. An unrecognized terms shape fails closed ([client.ts lines 297–301](client.ts#L297-L301), [adapter.ts lines 263–275](adapter.ts#L263-L275)).
3. **Customer and hosted KYC.** The public Ramps API documents `POST /api/v1/customers/` with `{ email, type: "INDIVIDUAL" }` and a response carrying the UUID `customerId`; Home parses that ID only and ignores other provider response fields. One Home action reserves `funding_provider_customers`, creates the customer when absent, persists `customerId`, then CAS-claims verification before terms or KYC writes. For the documented Ripio-hosted flow, `POST /api/v1/customers/{customerId}/kyc/` receives exactly `{ redirectUrl }`, where Home authors `/fund?return=verification`; partner-collected KYC fields and optional `kycProviderShareToken` are out of scope. The successful response is bounded and parsed only for its `providerUrl`, and extra provider fields are ignored. `GET /api/v1/customers/{customerId}/kycSubmissions/` must echo the customer UUID and a bounded status: only exact `COMPLETED` verifies and exact `FAILED` rejects; `IN_REVIEW`, every other status, 404, malformed/contradictory bodies, and transport/HTTP uncertainty leave the row pending. Home never repeats an ambiguous write.
4. **Base network catalogs.** Confirm `GET /api/v1/depositNetworks/?include_currency=true` and `GET /api/v1/withdrawalNetworks/?include_currency=true` return either an array or `{ networks: [...] }`. The adapter requires a network whose `network_name` or `networkName` is exactly `BASE`, with an asset whose `name` is exactly `wARS`, `wBRL`, or `wCOP` and whose `contract_address` / `contractAddress` matches Home's registered Base address ([client.ts lines 244–267](client.ts#L244-L267), [531–545](client.ts#L531-L545)).
5. **Quote and order.** Confirm `POST /api/v1/quotes/` accepts `customerId`, `fromCurrency`, `toCurrency`, `fromAmount`, `chain: "BASE"`, and `paymentMethodType`, and returns the quote, decimal amount/rate fields, expiry, and fee fields parsed by Home. Confirm `POST /api/v1/onramp/` accepts `customerId`, `quoteId`, `depositAddress`, and `externalRef`; Home sends its UUID `homeOrderId` as `externalRef` and validates all available transaction binding echoes before showing instructions ([client.ts lines 244–284](client.ts#L244-L284), [316–399](client.ts#L316-L399), [adapter.ts lines 42–103](adapter.ts#L42-L103)). Ripio prices a quote against the customer, so Home sends the `customerId` returned by customer creation and never asks for a quote before that customer exists; a quote echoing a different `customerId` is treated as ambiguous rather than retried. Home accepts a quote only when the returned `finalFromAmount` equals the requested `fromAmount` exactly and `expiration` is in the future; quote economics that change the fiat debit are rejected before any order exists ([core service lines 180–181](../../core/service.ts#L180-L181)).
6. **Country rails and instructions.** Confirm Argentina exposes `bank_transfer` for wARS and returns CVU/optional alias. Confirm Brazil exposes one-off `pix` for BRL → wBRL and returns `fiatPaymentInstructions.brCode`; Home validates its TLV shape, Pix GUI, CRC checksum, and amount tag `54`, which must equal the quote's `finalFromAmount` exactly, before mapping it to the shared QR instruction. Optional HTTPS `paymentUrl` is validated but never surfaced, and optional Pix expiry can shorten the stored quote expiry. Brazil has no deposit account, session, or widget. Confirm Colombia exposes `bank_transfer`, `breb`, `r2p_bancolombia`, and `r2p_nequi` for wCOP, returning the corresponding payment URL, Bre-B key, or Nequi phone number ([manifest.ts lines 31–70](manifest.ts#L31-L70), [client.ts lines 400–412](client.ts#L400-L412), [Pix parser lines 502–529](client.ts#L502-L529), [adapter.ts lines 173–194](adapter.ts#L173-L194)). The Brazil binding implements the product decision in [#199](https://github.com/jessepollak/home/issues/199), but the provider must still confirm the Brazil KYC/CPF requirements and exact Pix response/status schema.
7. **Transaction polling, status, and refund priority.** Home polls `GET /api/v1/transactions/{transactionId}/` using the `transactionId` returned at create. Confirm the response always carries the UUID `transactionId` and a `status` string, and may carry `customerId`, `quoteId`, `externalRef`, `source`, `fromCurrency`, `toCurrency`, `chain`, `paymentMethodType`, `depositAddress`, `amount`, `txnHash`, and `latestRefund`; Home requires `source` to be `ON_RAMP`, `txnHash` to be a `0x`-prefixed hash with 64 hexadecimal digits or `null`/absent, and `amount` to be a decimal. On every poll Home requires the echoes `customerId`, `quoteId`, `externalRef` (Home's order UUID), `depositAddress`, `source: "ON_RAMP"`, `chain: "BASE"`, the ARS/wARS, BRL/wBRL, or COP/wCOP pair, and `paymentMethodType` to be present and equal to the create-time values; `amount` is the token amount (wARS/wBRL/wCOP) and must equal the quote's `finalToAmount` exactly. A missing or mismatched echo fails the poll closed and never advances the order ([client.ts lines 286–291](client.ts#L286-L291), [345–399](client.ts#L345-L399), [adapter.ts lines 105–131](adapter.ts#L105-L131)). Confirm transaction status vocabulary: `CREATED`, `PENDING`, `AWAITING_PAYMENT`; `PAYMENT_RECEIVED`, `ONRAMP_PAYMENT_RECEIVED`; `CONVERTING`, `PROCESSING`, `SENDING`, `ONRAMP_CRYPTO_BUY_IN_PROGRESS`; `COMPLETED`, `SUCCESS`, `ONRAMP_CRYPTO_SENT`; `CANCELLED`, `ONRAMP_CANCELED`; `EXPIRED`; `REFUNDED`, `REFUND_COMPLETED`, `ONRAMP_REFUNDED`; and `FAILED`, `SERVICE_UNAVAILABLE`, `ONRAMP_FAILED`. A `latestRefund.status` of `COMPLETED`, `REFUNDED`, or `SUCCESS` takes terminal refunded priority over the transaction status ([adapter.ts lines 204–222](adapter.ts#L204-L222)).
8. **Webhook.** Confirm each Ripio country account signs the raw body with HMAC-SHA256 using its distinct `RIPIO_WEBHOOK_SECRET_AR`, `RIPIO_WEBHOOK_SECRET_BR`, or `RIPIO_WEBHOOK_SECRET_CO`, sends `sha256=<64 hex characters>` in `http-x-wh-signature-256`, and supplies `eventType`, parseable `issueDatetime`, and `transactionObject.transactionId`. Home strips the `sha256=` prefix before constant-time comparison and receives the event at `POST /api/funding/webhooks/ripio` ([adapter.ts lines 134–141](adapter.ts#L134-L141), [243–260](adapter.ts#L243-L260), [manifest.ts line 29](manifest.ts#L29)). Configure the same `POST /api/funding/webhooks/ripio` URL in each AR, BR, and CO dashboard and place each generated secret in its matching Vercel variable; there is no shared fallback. When migrating from the former shared `RIPIO_WEBHOOK_SECRET`, set all three suffixed Vercel variables before deploying this code or removing the shared variable, or bindings and open orders can become inert during the rename.
9. **Ripio handoff (acceptance playbook Phase 1).** Ripio must confirm the complete production request/response schema above, Brazil KYC/CPF requirements, the Pix order/status schema, and the registered Base wBRL address `0xD76f5Faf6888e24D9F04Bf92a0c8B921FE4390e0` with 18 decimals before any Home write (playbook Phase 2) or any funded test (Phase 5), and that `https://skala.ripio.com` remains production-only with no sandbox. Ripio requires the end user's IP address: it is a required field on `acceptTerms` (confirmed against production, which accepts private and loopback addresses), and Home now transmits the address it observed. A completion return URL is still resolved but not transmitted (the create body is only `customerId`, `quoteId`, `depositAddress`, `externalRef`, and optional `extraData`). Ripio must also confirm the remaining Phase 1 questions: the exact redirect origins for Colombia `bank_transfer` and `r2p_bancolombia`; that `breb` returns `brebKey` and `r2p_nequi` returns `phoneNumber` rather than substituting a payment URL; the quote TTL behind `expiration`; that the onchain `Transfer` amount equals the quote's `finalToAmount` exactly; the expiry/cancel behavior of an order that is never paid; duplicate email/KYC behavior (checklist item 3); and webhook retry counts and callback registration limits.

## Acceptance diagnostics

Ripio adapter failures emit closed, scrubbed JSON events to the local server console and hosted logs. Filter for `"provider":"ripio"`. Adapter cause events distinguish `FUNDING_PROVIDER_CONFIGURATION`, `PROVIDER_HTTP_4XX`, `PROVIDER_HTTP_5XX`, `PROVIDER_TRANSPORT`, `PROVIDER_INVALID_RESPONSE`, `QUOTE_ECHO_MISMATCH`, `ORDER_ECHO_MISMATCH`, and `STATUS_ECHO_MISMATCH`; the core separately owns the single `ORDER_AMBIGUOUS` lifecycle outcome after its durable transition. A verified webhook matched to a known order emits `WEBHOOK_MATCHED` with only the provider and verified two-letter region. Events never include order or transaction IDs, raw bodies, credentials, KYC fields, payment instructions, amounts, addresses, or provider error text. Client-facing errors, webhook `202` responses, status-refresh behavior, and no-retry semantics remain unchanged.

## Acceptance runthrough

Run the phases in order and stop at each boundary until the named authority approves the next one. The full phase-by-phase playbook — checkbox gates with owners and approvers, roles, recovery checklists, evidence template, and claim semantics — lives beside this adapter in [`ACCEPTANCE.md`](ACCEPTANCE.md) ([#512](https://github.com/jessepollak/home/issues/512)). Summary:

- **Local development (playbook Phases 0–4).** Synthetic tests with no network (`bun test apps/web/server/funding/providers/ripio/`), then read-only provider schema confirmation outside Home. Customer creation and verification start are explicit writes; quote creation is allowed only for a durably verified customer. An uncertain customer, verification, quote, or order create is never retried automatically and recovery runs through the playbook checklist. A local webhook tunnel is permitted only on a Ripio dev account, or for a country account before its permanent callback is registered: in this run the per-country callbacks are already registered and are never hijacked.
- **Hosted final proof (playbook Phases 5–6).** Provider constraints require sequential funded tests on Home's protected production alias, one funded order per rail at provider minimum. Jesse explicitly approves the exact bounded plan; one approval may cover its complete listed sequence until a stop condition occurs. This is the only path to this playbook's hosted validated claim; local completion proves only the local path exercised.

All automated coverage uses synthetic responses and test doubles. No live provider call or funded flow has ever been run with this adapter, and no live or funded validation is claimed until evidence is recorded in a playbook run.

## Customer and hosted verification

Ripio implements the explicit provider-customer capability behind one Home action. Home reserves and, if necessary, creates and durably records the customer first, then claims the row before terms acceptance and hosted KYC submission. The hosted KYC request is exactly `{ redirectUrl }`; the response is bounded and parsed only for its `providerUrl`; no provider payloads or submission identifiers are stored. The hosted URL must be HTTPS at the exact `https://kyc.ripio.com` origin, with no credentials or fragment and a 4096-character bound. Its query is treated as a bearer credential: it is returned once from verification start, never persisted, and never returned by customer status reads. The server-authored callback is `/fund?return=verification`.

Implementation source: the public [Ripio Ramps API](https://docs.ripio.com/ramps-api/overview/introduction), especially its hosted-KYC submit and latest-submission GET contracts. Production behavior remains unverified: hosted origin/query preservation, duplicate-email behavior, repeated terms/KYC safety, account enablement, and quote/order behavior require separately authorized acceptance. Public documentation is sufficient for this implementation; no live acceptance is claimed. Coinbase Embedded and IDRX QRIS are explicitly outside this lifecycle and retain their direct order flows.
