# Ripio funding adapter

Reference adapter for AR wARS, BR wBRL, and CO wCOP. It uses raw HTTP through the bounded provider context, one country-specific credential pair per binding, a distinct webhook verification secret per country account, quotes, email-based customer creation, terms acceptance, optional KYC fields, order creation, polling, and webhook verification. A binding remains inert until all environment variables in its manifest are set.

## Confirm against your API

1. **Origin, OAuth, and credentials.** Confirm production origin `https://skala.ripio.com`, token endpoint `POST /oauth2/token/`, HTTP Basic authentication with the country-specific client ID and secret, form body `grant_type=client_credentials`, and response fields `access_token` plus numeric `expires_in`. Argentina uses `RIPIO_CLIENT_ID_AR` / `RIPIO_CLIENT_SECRET_AR`; Brazil uses `RIPIO_CLIENT_ID_BR` / `RIPIO_CLIENT_SECRET_BR`; Colombia uses `RIPIO_CLIENT_ID_CO` / `RIPIO_CLIENT_SECRET_CO` ([client.ts lines 151–223](client.ts#L151-L223), [manifest.ts lines 31–70](manifest.ts#L31-L70)). The adapter has no sandbox origin.
2. **Terms.** Confirm `GET /api/v1/termsAndConditions/` returns a UUID as top-level `termsId` or `id`, a `{ results: [{ id }] }` collection, or a top-level array of `{ id }`. Home then calls `POST /api/v1/customers/{customerId}/acceptTerms/` with `{ termsId }`; an unrecognized terms shape fails closed ([client.ts lines 297–301](client.ts#L297-L301), [adapter.ts lines 263–275](adapter.ts#L263-L275)).
3. **Customer and KYC.** Confirm `POST /api/v1/customers/` accepts `{ email, type: "INDIVIDUAL" }` and returns UUID `customerId` plus `createdAt`. Home then submits the remaining manifest fields to `POST /api/v1/customers/{customerId}/kyc/`: `firstName`, `lastName`, `birthDate`, `documentType` (`national-id` or `passport`), and `documentNumber` ([client.ts lines 234–243](client.ts#L234-L243), [302–306](client.ts#L302-L306), [adapter.ts lines 26–40](adapter.ts#L26-L40), [manifest.ts lines 7–17](manifest.ts#L7-L17)). Home remembers the returned `customerId` only once an order is reserved (the `funding_orders` row written when the user confirms the deposit): abandoning or retrying **Get quote** before an order is reserved repeats the customer creation, terms acceptance, and KYC writes with the same email. Ripio must confirm duplicate-email behavior for `POST /api/v1/customers/` (idempotent return of the existing customer, or the documented error) and that repeated terms/KYC writes are safe ([core service lines 168–172 and 220](../../core/service.ts#L168-L172), [store.ts lines 137–140](../../core/store.ts#L137-L140)).
4. **Base network catalogs.** Confirm `GET /api/v1/depositNetworks/?include_currency=true` and `GET /api/v1/withdrawalNetworks/?include_currency=true` return either an array or `{ networks: [...] }`. The adapter requires a network whose `network_name` or `networkName` is exactly `BASE`, with an asset whose `name` is exactly `wARS`, `wBRL`, or `wCOP` and whose `contract_address` / `contractAddress` matches Home's registered Base address ([client.ts lines 244–267](client.ts#L244-L267), [531–545](client.ts#L531-L545)).
5. **Quote and order.** Confirm `POST /api/v1/quotes/` accepts `fromCurrency`, `toCurrency`, `fromAmount`, `chain: "BASE"`, and `paymentMethodType`, and returns the quote, decimal amount/rate fields, expiry, and fee fields parsed by Home. Confirm `POST /api/v1/onramp/` accepts `customerId`, `quoteId`, `depositAddress`, and `externalRef`; Home sends its UUID `homeOrderId` as `externalRef` and validates all available transaction binding echoes before showing instructions ([client.ts lines 244–284](client.ts#L244-L284), [316–399](client.ts#L316-L399), [adapter.ts lines 42–103](adapter.ts#L42-L103)). Home accepts a quote only when the returned `finalFromAmount` equals the requested `fromAmount` exactly and `expiration` is in the future; quote economics that change the fiat debit are rejected before any order exists ([core service lines 180–181](../../core/service.ts#L180-L181)).
6. **Country rails and instructions.** Confirm Argentina exposes `bank_transfer` for wARS and returns CVU/optional alias. Confirm Brazil exposes one-off `pix` for BRL → wBRL and returns `fiatPaymentInstructions.brCode`; Home validates its TLV shape, Pix GUI, CRC checksum, and amount tag `54`, which must equal the quote's `finalFromAmount` exactly, before mapping it to the shared QR instruction. Optional HTTPS `paymentUrl` is validated but never surfaced, and optional Pix expiry can shorten the stored quote expiry. Brazil has no deposit account, session, or widget. Confirm Colombia exposes `bank_transfer`, `breb`, `r2p_bancolombia`, and `r2p_nequi` for wCOP, returning the corresponding payment URL, Bre-B key, or Nequi phone number ([manifest.ts lines 31–70](manifest.ts#L31-L70), [client.ts lines 400–412](client.ts#L400-L412), [Pix parser lines 502–529](client.ts#L502-L529), [adapter.ts lines 173–194](adapter.ts#L173-L194)). The Brazil binding implements the product decision in [#199](https://github.com/jessepollak/home/issues/199), but the provider must still confirm the Brazil KYC/CPF requirements and exact Pix response/status schema.
7. **Transaction polling, status, and refund priority.** Home polls `GET /api/v1/transactions/{transactionId}/` using the `transactionId` returned at create. Confirm the response always carries the UUID `transactionId` and a `status` string, and may carry `customerId`, `quoteId`, `externalRef`, `source`, `fromCurrency`, `toCurrency`, `chain`, `paymentMethodType`, `depositAddress`, `amount`, `txnHash`, and `latestRefund`; Home requires `source` to be `ON_RAMP`, `txnHash` to be a `0x`-prefixed hash with 64 hexadecimal digits or `null`/absent, and `amount` to be a decimal. On every poll Home requires the echoes `customerId`, `quoteId`, `externalRef` (Home's order UUID), `depositAddress`, `source: "ON_RAMP"`, `chain: "BASE"`, the ARS/wARS, BRL/wBRL, or COP/wCOP pair, and `paymentMethodType` to be present and equal to the create-time values; `amount` is the token amount (wARS/wBRL/wCOP) and must equal the quote's `finalToAmount` exactly. A missing or mismatched echo fails the poll closed and never advances the order ([client.ts lines 286–291](client.ts#L286-L291), [345–399](client.ts#L345-L399), [adapter.ts lines 105–131](adapter.ts#L105-L131)). Confirm transaction status vocabulary: `CREATED`, `PENDING`, `AWAITING_PAYMENT`; `PAYMENT_RECEIVED`, `ONRAMP_PAYMENT_RECEIVED`; `CONVERTING`, `PROCESSING`, `SENDING`, `ONRAMP_CRYPTO_BUY_IN_PROGRESS`; `COMPLETED`, `SUCCESS`, `ONRAMP_CRYPTO_SENT`; `CANCELLED`, `ONRAMP_CANCELED`; `EXPIRED`; `REFUNDED`, `REFUND_COMPLETED`, `ONRAMP_REFUNDED`; and `FAILED`, `SERVICE_UNAVAILABLE`, `ONRAMP_FAILED`. A `latestRefund.status` of `COMPLETED`, `REFUNDED`, or `SUCCESS` takes terminal refunded priority over the transaction status ([adapter.ts lines 204–222](adapter.ts#L204-L222)).
8. **Webhook.** Confirm each Ripio country account signs the raw body with HMAC-SHA256 using its distinct `RIPIO_WEBHOOK_SECRET_AR`, `RIPIO_WEBHOOK_SECRET_BR`, or `RIPIO_WEBHOOK_SECRET_CO`, sends `sha256=<64 hex characters>` in `http-x-wh-signature-256`, and supplies `eventType`, parseable `issueDatetime`, and `transactionObject.transactionId`. Home strips the `sha256=` prefix before constant-time comparison and receives the event at `POST /api/funding/webhooks/ripio` ([adapter.ts lines 134–141](adapter.ts#L134-L141), [243–260](adapter.ts#L243-L260), [manifest.ts line 29](manifest.ts#L29)). Configure the same `POST /api/funding/webhooks/ripio` URL in each AR, BR, and CO dashboard and place each generated secret in its matching Vercel variable; there is no shared fallback. When migrating from the former shared `RIPIO_WEBHOOK_SECRET`, set all three suffixed Vercel variables before deploying this code or removing the shared variable, or bindings and open orders can become inert during the rename.
9. **Ripio handoff (acceptance playbook Phase 1).** Ripio must confirm the complete production request/response schema above, Brazil KYC/CPF requirements, the Pix order/status schema, and the registered Base wBRL address `0xD76f5Faf6888e24D9F04Bf92a0c8B921FE4390e0` with 18 decimals before any Home write (playbook Phase 2) or any funded test (Phase 5), and that `https://skala.ripio.com` remains production-only with no sandbox. Confirm whether Ripio requires the end user's IP address or a completion return URL: Home resolves both but transmits neither to Ripio today (the create body is only `customerId`, `quoteId`, `depositAddress`, `externalRef`, and optional `extraData`). Ripio must also confirm the remaining Phase 1 questions: the exact redirect origins for Colombia `bank_transfer` and `r2p_bancolombia`; that `breb` returns `brebKey` and `r2p_nequi` returns `phoneNumber` rather than substituting a payment URL; the quote TTL behind `expiration`; that the onchain `Transfer` amount equals the quote's `finalToAmount` exactly; the expiry/cancel behavior of an order that is never paid; duplicate email/KYC behavior (checklist item 3); and webhook retry counts and callback registration limits.

## Acceptance diagnostics

Ripio adapter failures emit closed, scrubbed JSON events to the local server console and hosted logs. Filter for `"provider":"ripio"`. The code distinguishes `FUNDING_PROVIDER_CONFIGURATION`, `PROVIDER_HTTP_4XX`, `PROVIDER_HTTP_5XX`, `PROVIDER_TRANSPORT`, `PROVIDER_INVALID_RESPONSE`, `QUOTE_ECHO_MISMATCH`, `ORDER_ECHO_MISMATCH`, `STATUS_ECHO_MISMATCH`, and `ORDER_AMBIGUOUS`. A verified webhook matched to a known order emits `WEBHOOK_MATCHED` with only the provider and verified two-letter region. Events never include order or transaction IDs, raw bodies, credentials, KYC fields, payment instructions, amounts, addresses, or provider error text. Client-facing errors, webhook `202` responses, status-refresh behavior, and no-retry semantics remain unchanged.

## Acceptance runthrough

Run the phases in order and stop at each boundary until the named authority approves the next one. The full phase-by-phase playbook — checkbox gates with owners and approvers, roles, recovery checklists, evidence template, and claim semantics — lives beside this adapter in [`ACCEPTANCE.md`](ACCEPTANCE.md) ([#512](https://github.com/jessepollak/home/issues/512)). Summary:

- **Local development (playbook Phases 0–4).** Synthetic tests with no network (`bun test apps/web/server/funding/providers/ripio/`), then read-only provider schema confirmation outside Home — Home's **Get quote** is already a write sequence (customer creation, terms acceptance, KYC submission, and quote creation) — then local live adapter iteration, polling-only, with every **Get quote**/Confirm writing production records on the no-sandbox API. An uncertain create response parks the order in `dispatch-ambiguous`; it is never retried, and recovery runs through the playbook checklist. A local webhook tunnel is permitted only on a Ripio dev account, or for a country account before its permanent callback is registered: in this run the per-country callbacks are already registered and are never hijacked.
- **Hosted final proof (playbook Phases 5–6).** After merge, sequential funded tests on Home's protected production alias, one funded order per rail at provider minimum, each payment explicitly approved by Jesse. This is the only path to a validated claim; local completion never is.

All automated coverage uses synthetic responses and test doubles. No live provider call or funded flow has ever been run with this adapter, and no live or funded validation is claimed until evidence is recorded in a playbook run.
